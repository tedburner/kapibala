## 1. codex-host「多任务派发」机制梳理

codex-host 的 Cross-Agent Collaboration 由以下部分组成（按 kapibala 视角归纳）：

### 1.1 派发链路

1. **Skill 注入**：向 `~/.agents/skills/` 与 `~/.claude/skills/` 安装 `codexhost-delegation` Skill（版本号 + 历史 digest 管理覆盖更新，冲突不覆盖），教会任意 Harness 的 agent「可以委派、怎么委派」；Skill 指向 `codexhost delegate` CLI，help-first，不内嵌命令清单。
2. **CLI 面**：`delegate start --harness <id> --task-name <名> --task <正文> [--parent-thread <id>]`，配套 `thread read / wait / send / cancel / list / watch` 与 `harness list / inspect`。
3. **协调器**（`HarnessDelegationCoordinator`）：
   - **父身份解析**：显式参数 → 子会话注入的环境变量（`CODEXHOST_DELEGATION_THREAD_ID`，支持嵌套委派）→ 唯一活动 Turn 自动推断；推断不出即报错，不猜。
   - **命名**：子会话名固定为「子任务名 · 父会话名」，子任务名在前（侧栏从末尾截断时兄弟任务仍可区分）；创建时写入，后续不联动改名。
   - **幂等**：显式 `requestId` 精确去重（同 requestId 不同配置报错，相同则返回原子会话）+ 无 requestId 时 30 秒窗口内按 `sha256(task+cwd+model+thinking)` 摘要隐式去重。
   - **事务性创建**：线程记录 + 委派记录先建，失败即回滚（关会话、删记录）；`executionPolicy: "unattended-full-access"` 以无人值守模式拉起目标 Harness。
4. **watch 通知**（`DelegationWatchService`）：被观察线程到达终态（completed/failed/interrupted）后，向父线程**投递一条通知消息**（即父线程新增一个 Turn），父 agent 无需轮询；投递失败按 permanent/rejected/unknown 三级处理，unknown 不重试（防重复 Turn）；内存态，不跨重启。
5. **子会话地位**：委派目标是**出现在会话列表里的独立原生会话**——用户可随时打开看进度，终态后可直接接续聊天；父 agent 通过 read/wait 拿结果，或让它跑在后台。

### 1.2 与 kapibala 的概念映射

| codex-host 概念 | kapibala 对应物 | 现状 |
|:---|:---|:---|
| 目标 Harness（Claude Code / Pi / …） | 模型 Profile（`BUILTIN_PROFILES` + 场景路由角色） | ✅ 已有 `modelOverride` / `preferredRole` |
| 独立原生会话（Thread） | `SessionManager.create` 独立 Store 会话 | ✅ 子代理已隔离；❌ 跑完即毁、用户不可见 |
| `delegate start` CLI | `spawn_agent` 工具（受理即闭合 + SpawnAgentReceipt） | ✅ 异步派发已是现状 |
| `thread send`（续聊） | — | ❌ 缺失（子会话生命周期 = 单任务） |
| `thread read / wait / cancel / list` | `list_agents / wait_agent / cancel_agent` + `subscribeTaskChanges` | ✅ 已有（agent 内部视角） |
| watch 终态通知 | `SubagentOutbox → SessionInbox` 背景消息 | ✅ 已有且更强（持久化、at-least-once、eventId 幂等） |
| requestId / 摘要去重 | 本地宿主协议层「操作 ID 去重」（v0.0.9） | ⚠️ 工具层未暴露给模型 |
| 「子任务名 · 父会话名」命名 | 会话标题 | ❌ 子代理无面向用户的标题 |
| 嵌套父解析（环境变量注入） | `AgentTaskOrigin`（rootTaskId / depth / generation） | ✅ 已有任务树，无需环境变量 |
| `#agent` 提及（用户发起） | — | ❌ 缺失 |

## 2. 结论：差距在哪

kapibala 的异步派发**内核**（受理即回执、独立 Store、任务树、outbox 可靠通知、只收紧策略、租约协调）已经齐备，且可靠性设计（outbox 幂等、canonical 历史闭合）不弱于 codex-host。真正缺的是三件事：

1. **委派会话不是一等会话**：子代理会话对用户不可见，终态即销毁（`subagent-runner.ts` 的 `destroy() + release()`），没有「打开看进度 / 事后接续聊天」。
2. **没有续聊语义**：无法对已派发会话追加消息（codex-host 的 `thread send`）。
3. **没有用户级入口**：派发只能由模型经 `spawn_agent` 发起，用户不能直接说「把这个任务派给 X 模型」。

外加两个小项：工具层幂等去重、面向用户的委派命名。

## 3. 版本规划

### 3.1 v0.1.0（进行中）：不加范围

设计 004 §1.2 已明确排除「可视化多代理编排、子代理审批冒泡、任务树分层 Token 账本」，维持不变。v0.1.0 只需保证两点为 v0.1.1 留好钩子（现有设计已满足）：

- 多会话与句柄预算（§D09、§203）天然容纳「委派子会话作为一种会话条目」；
- `task-observation.ts` / `subscribeTaskChanges` 已把任务状态送进宿主，桌面只需消费。

### 3.2 v0.1.1「多任务派发」：建议作为 v0.1.0 之后的下一个版本的阶段重点

**主题**：把子代理任务升级为**用户可见、可续聊的一等委派会话**，并提供用户级派发入口。交付分三段，Core → CLI → 桌面，任一段独立可用。

#### 阶段 D1（Core：委派会话生命周期）

- **保留型委派会话**：`spawn_agent` 新增 `mode: 'ephemeral' | 'detached'`（默认 `ephemeral` 保持现行为）。`detached` 子会话终态后不销毁 Store，登记标题（「子任务名 · 父会话名」规则，子任务名 ≤ 120 字符、总长有界）与父会话引用，进入可查询、可恢复列表。
- **续聊 `send_agent`**：对**空闲**的 detached 子会话追加新任务轮次（busy 即拒绝，不排队）；运行语义 = 新一轮 `AgentSession.run`，历史闭合不变量天然满足（独立 Store 内自闭合）。父会话侧同 spawn：受理即闭合 + outbox 通知。
- **工具层幂等**：`spawn_agent` / `send_agent` 接受可选 `requestId`，协调器按 requestId 精确去重返回原任务；无 requestId 时不做隐式去重（与 codex-host 的 30 秒摘要窗不同——kapibala 的调用方是模型与宿主，显式幂等更可控，隐式窗容易误伤「故意重跑同一任务」）。
- **保留预算**：detached 会话设上限（数量 + 闲置天数），超限 LIFO 清理；清理只删会话文件与索引，不动父历史中的通知记录。
- `read_agent`（可选，视工作量）：返回子会话终态摘要 + 状态，替代「父模型只能等 outbox」的单通道。

#### 阶段 D2（CLI：用户级派发入口）

- `/delegate <任务描述>` 命令族：用户直接以指定 profile / 角色派发 detached 任务（策略从当前会话只收紧派生）；`/tasks` 面板列出 detached 任务（复用 v0.0.8 `TaskObservationHost` 聚合），支持查看状态、取消、恢复为当前会话接续聊天。
- 状态栏现有「🤖 子代理: N 个运行中」扩展区分 detached 任务。
- 全部经现有权限系统裁决，不新增绕过 Core 的执行入口。

#### 阶段 D3（桌面：委派会话可见化）

- 侧栏会话列表显示 detached 委派会话（父会话分组或徽标 + 命名规则），点击即以普通会话视图打开（复用 v0.1.0 多会话能力），流式看进度，终态后可直接输入接续（等价 `send_agent`）。
- 父会话卡片显示委派状态与终态通知（消费 outbox / `subscribeTaskChanges`，走既有快照-增量协议）。
- composer 内用户直接派发（`#模型` 提及或按钮）：**列为 D3 的可选项**，D1+D2 稳定后再决定是否纳入。

### 3.3 明确非目标（本版不做）

- **跨 Harness 派发**（把 Claude Code / Codex 等 CLI 作为派发目标嵌入）：与「所有宿主通过同一 AgentSession 复用同一 Harness」的定位冲突，属全新维度。列入后续版本探索项（若未来作为次版本主题再评估），不承诺。
- 可视化编排画布、任务树分层 Token 账本、子代理审批冒泡：v0.1.0 已排除者继续后置。
- Git Worktree 并行物理隔离（`isolation: 'worktree'` 字段已预留未实现）：与多任务派发天然相关（并行写冲突），但建议单独评估排期，不绑定 v0.1.1。
- 嵌套委派的环境变量父注入：kapibala 用 `AgentTaskOrigin` 任务树表达，不引入 codex-host 的环境变量机制。

## 4. 核心不变量映射（实现时逐条对照）

| 不变量 | 落点 |
|:---|:---|
| 历史闭合 | detached 子会话独立 Store 自闭合；`send_agent` 只在空闲时开新轮，不触碰已闭合事务；父侧受理即闭合模式不变 |
| 消息级落盘 | 委派会话全程 `MessageStore.append`；outbox 通知仍以背景消息入父历史 |
| Core Headless | 派发编排留在 Core `AgentRuntime`；CLI/桌面只经 `AgentSession` / `SessionEvent` / `subscribeTaskChanges` 消费 |
| 显式工作区身份 | detached 子会话沿用 `task.workspaceRoot`，禁止 `process.cwd()`（架构门禁） |
| 写租约 | 子会话共用宿主 `WorkspaceLeaseCoordinator`（subagent-runner 已校验父子协调器一致），detached 不豁免 |
| 权限只收紧 | detached 会话策略仍由父 `effectivePolicy` 快照派生；用户 `/delegate` 时从当前会话模式派生 |
| 公开 API 面 | 新工具与选项须同步 `scripts/check-public-api.ts` fixtures 与 `docs/sdk-compatibility.md` |

## 5. 验证与门禁

- `pnpm verify` 常规门禁 + `check-architecture` / `check-cli-boundary`；
- 专项：spawn/send 的 requestId 幂等与崩溃恢复（outbox 已有 at-least-once 断言可扩展）、detached 保留预算清理、并发 send 的 busy 拒绝、桌面多会话下委派条目快照一致性；
- `verify:soak` 分档：detached 任务 + 续聊纳入 PR/nightly 档断言；
- 发布走既有 `pnpm release` + 证据预检流程，文档四件套（发布说明 / 验收 / 迁移 / SDK 兼容）照常。

## 6. 开放问题（实施前需用户拍板）

1. detached 默认值：新任务默认 detached 还是 ephemeral？（建议：模型经 `spawn_agent` 默认 ephemeral，用户 `/delegate` 默认 detached——用户显式要的才占保留预算。）
2. detached 会话是否计入桌面「已打开运行时会话 / 并行 run」预算（设计 004 §203 的 8/4 上限），还是单列委派预算？（建议单列，避免委派挤占交互会话。）
3. `read_agent` 是否进 D1，还是先靠 outbox + `/tasks` 面板覆盖。
4. v0.1.1 是否捆绑 Worktree 隔离（若捆绑则本版实质超出补丁位主题版本的常规规模，需重新评估版本号与阶段重排）。
