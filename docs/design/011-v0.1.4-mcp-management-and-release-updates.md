# 011 — v0.1.4 MCP 管理与分发更新

> 状态：**终审稿**（2026-11-20 随[版本设计 014](014-v0.1.4-version-design.md)收敛）。2026-11-16 维护者决策：MCP 管理与分发更新统一并入 v0.1.4（第四主题），
> 与 008（watch）/ 009（技能）/ 010（会话看板）并列为四主题；排期裁决与依赖见 §5。
> 分发更新明确**不走签名链路**（未签名个人自用版定位延续），更新通道只用 GitHub Releases。

## 0. 两块能力的共同语境

- **MCP 管理**：`/mcp` 命令族（v0.0.6）只有运行时观测与会话内启停，配置级增删改只能手编 `mcp.json`；本主题把 MCP 配置管理升级为命令与桌面界面能力，并与 009 的「从其它 Harness 导入」框架对齐。
- **分发更新**：v0.1.0 起自动更新被显式排除、各版悬空；本主题接球，定位是**未签名自用版的轻量更新检查**，不做静默安装链路。

## 1. MCP 管理（M = mcp）

### 现状核实

- 配置真源：`~/.kapibala/mcp.json`（全局）+ `<projectRoot>/.kapibala/mcp.json`（项目级）；
- `/mcp` / `/mcp tools / reconnect / enable|disable`：观测与纯内存启停，不写磁盘；
- **配置事务已存在**：`packages/host/src/host/resource/mcp-config.ts:216-301` 的 `mutateGlobalMcpConfig` 已实现加锁、校验与 tmp/rename 原子写；本主题的增删改**复用它**，不另起写路径；
- **桌面 MCP 区块已存在**：`packages/desktop/src/renderer/settings-dialog.tsx:1279-1390` 已有全局服务清单、增删改与启停，项目级只读；M1.1 是增量补齐而不是新建分区；
- 写回纪律：配置写路径必须走既有配置事务模式（对齐 `mutateGlobalSettings` 的事务边界），禁止散落写 JSON。

### 任务拆解

| ID | 任务 | 说明 | 验收 |
|---|---|---|---|
| M0.1 | CLI 配置命令（复用既有事务） | 在 `mutateGlobalMcpConfig` 之上补 `/mcp add <name> --transport stdio|http ...`、`/mcp remove <name>`、`/mcp edit <name>`；全局默认，`--project` 显式切换；项目级写入仅限已信任项目；非法 JSON 中止不落盘 | 命令族覆盖增删改；与手编文件互不踩踏；`/mcp` 列表即时反映；未信任项目写项目级被拒 |
| M0.2 | 从其它 Harness 导入 | 对齐 009 导入框架：Claude Desktop / Claude Code / Cursor 的 MCP 配置读取、transport 字段转换、同名冲突默认跳过、导入预览；只承诺这三种可验证格式，不扩未核实来源；溯源复用 009 的 `.imported-from.json`（同一格式，不另立字段）；一次性拷贝不自动同步 | 三种源格式用例通过；冲突跳过与溯源文件正确 |
| M0.3 | 逐服务器批准与配置摘要 | 新增 per-server 批准记录（键 = 作用域 + server 名 + 配置摘要）；启动/重连 server 前必须已批准且摘要一致；`add` / `edit` / 导入产生的新配置或任何字段变化一律回到待批 | 未批准 server 不启动；改一个环境变量即重新待批；批准界面不打印密文 |
| M1.1 | 桌面 MCP 区块补齐 | 在既有区块（`:1279-1390`）上补：项目级只读视图 → 受信项目可写、「从其它工具导入」入口、逐服务器批准状态、连接状态与 `/mcp` 同口径 | 界面与命令写同一配置事务，无第二真源；未信任项目无写入口；待批 server 有明确批准入口 |

### 服务器批准（D4，2026-11-20 拍板）

项目信任解决的是「这个仓库的代码我可以跑」，而 MCP server 是**配置驱动的常驻进程**，可在任意时刻
联网、读环境变量、执行命令。两者爆炸半径不同，不共用一把钥匙：

- **逐服务器批准**：首次启用或启动前必须由用户明确批准；批准记录按「作用域 + server 名」保存。
- **配置摘要**：批准绑定当时的配置摘要（命令 / 参数 / 环境键值 / URL / headers 全量）。任一字段
  变化即视为新配置，批准失效并回到待批；启动/重连前校验摘要一致。
- **不自动启动**：未批准的 server 不出现在可用工具集里，也不后台拉起；UI 只显示「待批准」。
- **秘密不落界面**：批准界面只展示键名与值的脱敏形式，不打印密文。
- 依据：活跃仓没有完整先例（Claude-Code 快照只有 per-server approval 形状），本项按本项目权限
  模型论证，**不写成「业界做法」**。

### 明确不做

- 不做 MCP 服务器市场/远程目录；不做 OAuth 流程的服务器；不改 MCP 子进程生命周期模型；
- 会话内 enable/disable 仍保持纯内存语义，不与配置级 enabled 混用。

## 2. 分发更新（U = update）

### 定位决策（维护者 2026-11-16）

- **不签名**：延续未签名个人自用版口径，签名与公证不进入本版，不作为更新前置；
- **因此不做静默安装**：electron-updater 的静默替换在 macOS 无签名时不可用（Squirrel 校验签名失败），统一降级为「检查 → 下载 → 提示手动安装」三步，三平台一致。

### 任务拆解

| ID | 任务 | 说明 | 验收 |
|---|---|---|---|
| U0.1 | 版本检查通道 | 读 GitHub Releases 最新 release（`releases/latest`），按桌面 target 匹配安装包资产；semver 与 `app.getVersion()` 比较（桌面**不用** `readWorkspaceVersion`，那是构建期脚本）；网络失败静默降级为「未知」不弹错 | 单元用例覆盖比较与资产匹配三分支（命中 / 无匹配资产 / 仅有源码包）；离线不阻塞启动 |
| U0.2 | 下载与打开 | 下载到系统下载目录后 `shell.openPath` 提示手动安装（保留 macOS quarantine 右键/xattr 提示文档口径）；不做差分包、不做强制更新 | 下载可取消、失败可重试；安装包 SHA256 与 `SHA256SUMS.txt` 严格一致才打开（见 §2.1 裁决）；文档显式声明未签名 |
| U1.1 | 设置页更新区块 | 「关于」分区：当前版本、检查更新按钮、新版本条目（版本号 + release 链接 + 下载进度）；不弹系统级打扰 | 区块随设置弹窗主题令牌走；与既有分区同层级结构 |

### 2.1 校验与资产匹配裁决（2026-11-20 版本设计 014 定）

- **摘要缺失即拒绝**：Release 没有 `SHA256SUMS.txt`，或其中没有目标安装包条目 → 拒绝下载并说明原因，不提供「跳过校验」开关（对齐 PiDeck `installerDownload.ts:31` 先取摘要再下载、`:43` 校验失败即拒）。
- **摘要只证明完整性**：`SHA256SUMS.txt` 与安装包同源，只能防传输损坏，不能证明来源或防替换。
  本版无签名链路，Release 与文档必须显式声明「Unsigned / 未公证」，不得宣称可防替换。
- **资产矩阵显式**：按平台与架构列固定匹配表（darwin-arm64 / darwin-x64 / linux-x64 / win32-x64），未知 target 返回「无匹配资产」，不做模糊猜测（对齐 PiDeck `releaseSelection.ts:31-45` 的平台解析）。
- 更新检查**只由用户动作触发**（按钮 / 菜单），启动时不自动联网。

### 2.2 明确不做（更新）

- 不做签名/公证/公证簿（维护者决策，未签名自用）；
- 不做静默安装、自动重启安装、delta 更新、多更新通道（stable/beta）、强更弹窗；
- 不做 CLI 的自更新（`kpbl` 走 npm，包管理器负责）。

## 4. wire / 门禁影响

- MCP 配置命令若补宿主协议方法，随 v0.1.4 的整数协议版本 2 与能力名 `mcp-config`（当前计划走
  既有宿主 / 桌面 IPC 面，不新增 wire 方法）；桌面 `.strict()` 快照要求版本严格相等，不承诺旧客户端兼容（014 §2.2）；
- `check-desktop` 不新增规则；桌面更新相关代码只允许进 main/preload 进程，renderer 仅消费 view-model 投影。
