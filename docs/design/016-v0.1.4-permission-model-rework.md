# 016 · v0.1.4 权限模型重做（三档语义、风险分级与硬禁区）

> 状态：**已评审（2026-11-21）**，按 §13 专项评审决议实施。
> 维护者 2026-11-20 三次选型：① 边界用轻围栏，不上 OS 级沙箱；② 界面保留三个预设，两轴不暴露；③ 并入 v0.1.4，作为第七个主题。
> 评审结论：方向可实施；但 shell 写硬禁区、读命令越界、自写脚本执行三处必须在 P0 先补（§13）。
> 阶段口径：P0 完成即可宣称「权限判定与硬禁区已重做」；P1 未完成前 Release 不得宣称存在规则页；P2 顺延 v0.1.5。
> 对标：codex 的 `SandboxMode` × `AskForApproval` 两轴模型（`app-server-protocol/src/protocol/v2/shared.rs:216,345`）、`ApprovalsReviewer.auto_review` 子代理预审；opencode 的 `Permission.Rule{action,resource,effect}` 规则集（`schema/src/permission.ts`）。
> 依赖：[014](014-v0.1.4-version-design.md) §4.7 共享文件与合并顺序；与 013 同为 Core 侧改动，但本主题改 `core/types` 与公共 API 快照，**必须排在 M0 之前或与之同批**。

## 0. 一句话定义

三档权限从「询问频率」重定义为**「沙箱边界 × 询问策略」的预设组合**；命令分级从按程序名查白名单改为按**风险类别**判定；新增不可由工具写入的**硬禁区**与**项目级审批记忆**，使自主模式在 workspace 内的常规开发命令真正不再打断人。

## 1. 与相邻能力的分界

| 能力 | 语义 | 现有实现 | 本主题的关系 |
|---|---|---|---|
| Plan 档 | 编辑前先出计划（工作流） | `permissions.ts:126-133` | 不动。它是工作流档位，不是审批强度 |
| PathSandbox | 文件访问的词法 + 物理边界 | `security/sandbox.ts` | 扩展 `protectedPaths`，工作区内再加一层禁区 |
| 技能拒绝通道 | 技能未声明能力时硬拒 | `hardDenial`（`session/index.ts:897`） | 复用同一通道，不新建裁决口 |
| 审批通道 | 取得人工选择 | `security/approval.ts` + CLI/桌面各自 UI | 只改策略与传入信息，不改通道契约 |
| **本主题** | **何时问人、问了能不能记住、哪些无论如何不问** | — | 见 §3–§6 |

## 2. 现状核实（实测，非推断）

### 2.1 真实命令集的分级结果

用仓库现有 `classifyShellCommandSafety` 对 27 条 kapibala 日常命令实测（`.workbuddy/probe-auto-approval.mts`，可复跑）：

| 分级 | 条数 | 典型命令 | Auto 裁决 |
|---|---|---|---|
| `safe` | 8 | `git status/diff/log`、`rg`、`ls`、`cat`、`find` | 放行 |
| `unknown` | 15 | `pnpm build/verify/test/install`、`npx biome`、`tsc --noEmit`、`git add/commit`、`docker compose`、`gh pr list`、`./scripts/dev.sh`、`cd x && pnpm build`、`echo $PATH` | 全部 ask |
| `unsafe` | 4 | `node scripts/dev.mjs`、`curl`、`rm -rf`、`pnpm test > log` | 全部 ask |

**Auto 仍需人工审批 19/27（70%）**；Approval 档 27/27 全问。

结论不是「问得多」，而是**放行面选错了**：自动放行的 8 条恰好是零风险只读命令，而构建、测试、校验、依赖、版本控制这些占满日常的命令全部落回人工。

### 2.2 根因（三条，均有代码位置）

**① shell 没有沙箱，安全只能由审批独自承担。**
`run_command` 的工具描述自己写着「The file tool PathSandbox does not isolate this process or its network access」（`capabilities/shell/tool.ts:372`）。既然没有内核边界，任何命令都必须逐条判；逐条判只能靠静态表；静态表不可能覆盖真实命令集。

**② 静态表按程序名列，不按风险形态列。**

- `POSIX_SAFE` 只有 50 个程序（`command-safety.ts:15-65`），`pnpm` / `npm` / `npx` / `tsc` / `docker` / `gh` 全不在表内 → `unknown`；
- `node` / `python` / `sh` / `bash` 被硬编码进 `POSIX_UNSAFE`（`:72-113`），导致「跑自己仓库的构建脚本」被判为最危险；
- 工作区内、已入库、内容可审计的脚本（`scriptDigest` 已知）在 `:212` 被一律判 `unknown`；
- 任何含 `$` 的命令在 `:308` 判 `unknown`；任何 `>` 重定向在 `:306` 判 `unsafe`（理由是「重定向不受 PathSandbox 约束」）。

**③ Auto 的保护对象反了。**
Auto 下 `fs:read` 与 `fs:read+fs:write` 自动放行（`permissions.ts:171-181`），而 `.git/hooks/post-checkout`、`.git/config`、`.env`、`.kapibala/permissions.json` 都在 workspace 内，PathSandbox 一律放行（实测 `isPathInside` 全为 true）。于是：

> 模型可以不问就写 git hook（下次 git 操作即任意代码执行）、改 remote 指向、覆盖 `.env`；而 `pnpm test` 要弹窗。

### 2.3 另外两个边界缺陷

- **FullAccess 并非全放行**：`capabilities.length === 0` 的裁决在 `:152` 先于 FullAccess 分支 `:170`，这类工具在完全访问下仍会 ask。
- **审批记忆沉淀不下来**：`SessionApprovalCache.key` 把完整 `input` 纳入哈希（`approval.ts:54-67`），参数一变即失效；`allow_session` 名义上「本次会话内允许」，实际只对逐字相同的命令生效。

## 3. 三档新语义（保留三个预设，内部两轴）

对外仍是 `Approval | Auto | FullAccess`（`SessionMode` 不改，wire 不加值），内部按两轴组合：

| 档位 | 边界（轴一） | 询问（轴二） | 行为 |
|---|---|---|---|
| **变更前确认** `Approval` | workspace-write | `untrusted` | 读文件、只读命令不问；**写文件、写类命令一律问** |
| **自主** `Auto` | workspace-write，网络受限 | `on-request` | 边界内不问（含构建/测试/校验/版本控制）；网络、危险、越界、未知才问 |
| **完全访问** `FullAccess` | danger-full-access | `never` | 不问；硬禁区仍拒（§5） |

三档形成明确梯度（以 §2.1 的 27 条计）：Approval 放行 8 条，Auto 放行约 17 条，FullAccess 放行全部但拦住硬禁区。

**为什么 Approval 也要放行只读命令**：当前 Approval 对 `ls` 都要弹窗，这是纯噪声——只读命令没有副作用，且 `fs:read` 在本档本来就自动放行，对 shell 的只读命令另眼相待没有依据。

**为什么 Auto 的网络类仍要问**：用户选的是轻围栏，没有内核网络隔离（§11）。网络类命令（`pnpm install` 的 postinstall、`npx` 拉包、`curl`）会执行**从外部取得的代码**，与「执行用户自己仓库里的代码」不是同一类风险，不能因为都在 workspace 里就一起放行。

## 4. 风险分级重做

### 4.1 词表不变，内部加一层类别

`ShellCommandSafety` 是公开类型且在公共 API 快照内，**保持 `safe | unsafe | unknown` 三值不变**，避免 wire 与快照破坏。内部新增 `ShellCommandClass`，再单向映射到三值：

| `ShellCommandClass` | 含义 | 映射到 | Auto | Approval |
|---|---|---|---|---|
| `read` | 只读程序，无副作用 | `safe` | 放行 | 放行 |
| `workspace-write` | 在 workspace 内构建/测试/格式化，执行的是仓库内代码 | `safe` | 放行 | 询问 |
| `vcs-write` | 仓库内版本控制写操作（非破坏） | `safe` | 放行 | 询问 |
| `network` | 拉取或执行外部代码、出站连接 | `unsafe` | 询问 | 询问 |
| `destructive` | 破坏性、提权、不可逆 | `unsafe` | 询问 | 询问 |
| `escape` | cwd 越界、读命令显式路径越界、写硬禁区（含 shell 可识别形态）、重定向越界 | `unsafe` | 询问 | 询问 |
| `unknown` | 无法静态判读 | `unknown` | 询问 | 询问 |

映射后 `safe` 的含义从「绝对只读」放宽为「在 workspace 边界内可控」，因此 **Approval 档不能复用 `safe` 判断，必须额外看 `class === 'read'`**。这一点写进策略分支，不能靠注释约定。

### 4.2 类别判定规则（替换程序白名单）

| 程序 | 判定 |
|---|---|
| `pnpm` / `npm` / `yarn` | 子命令 `run/build/test/lint/format/typecheck` → `workspace-write`；`install/add/remove/update/publish/link` → `network` |
| `npx` / `pnpm dlx` | 目标包已在 `node_modules/.bin` → `workspace-write`；否则 `network`（会下载并执行） |
| `tsc` / `biome` / `vitest` / `tsup` / `eslint` / `prettier` / `make` | `workspace-write` |
| `node` / `python` / `tsx` / `deno` | 目标是 workspace 内已存在文件 → `workspace-write`；`-e` / `-c` / 标准输入 → `unknown` |
| `git` | `add/commit/switch/checkout/stash`（无 `-f`）→ `vcs-write`；`push/fetch/pull/clone/submodule` → `network`；`reset --hard/clean -fd/push --force/restore -- <path>/checkout -- <path>/stash drop|clear/branch -D` → `destructive`；只读子命令保持现状 |
| `docker` | `compose up/down/run`、`build`、`pull/push/login` → `network`；`ps/logs/images` → `read` |
| `gh` | 全部 `network`（一律走 API） |
| `curl` / `wget` / `nc` / `ssh` / `scp` / `rsync` | `network` |
| `rm` / `mv` / `dd` / `mkfs` / `chmod` / `chown` / `sudo` / `kill` | `destructive` |
| 工作区直引脚本（`./scripts/dev.sh`，`scriptDigest` 已知） | `workspace-write`（当前误判为 `unknown`） |
| 重定向 `>` 目标在 workspace 内 | 不单独降级，按该段类别判定；目标越界 → `escape` |
| 含 `$` 变量 | `unknown` 不变（展开结果不可知） |
| `cd` | 目标在 workspace 内且为静态路径 → 不降级；越界 → `escape` |
| 只读程序（`cat`/`head`/`rg` 等）带显式路径参数 | 路径解析到 workspace 外 → `escape`；无路径参数（如 `git status`）保持 `read` |
| `find -exec`、`xargs`、`eval`、`bash -c`、`sh -c`、`sed -i` | `unknown`（可执行任意命令或原地改写，不能按程序名放行） |
| 写 `.github/workflows/**`、`.npmrc`、`.netrc`、`.git-credentials` | `escape`（Auto/Approval 询问；FullAccess 放行但审计） |
| 重定向 / `tee` / `cp` / `mv` / `sed -i` 目标命中硬禁区 | 直接 `deny`（三档一致，不经审批） |
| Auto 下执行脚本与包脚本（`node <file>`、`./x.sh`、`pnpm run/test/build`） | 目标脚本与 `package.json` 相对 HEAD 干净（`scriptDigest` 命中且未修改）才放行；脏或未跟踪 → `unknown` |

判定顺序：`escape` → `destructive` → `network` → `workspace-write` / `vcs-write` / `read` → `unknown`。**多段命令取最严**，保持现有 `classifyShellCommandSafety` 的聚合语义。

### 4.3 实现落点

新增 `packages/core/src/capabilities/shell/command-class.ts`（纯函数、无 IO），`command-safety.ts` 改为它的薄封装：

```ts
export type ShellCommandClass =
  | 'read' | 'workspace-write' | 'vcs-write'
  | 'network' | 'destructive' | 'escape' | 'unknown';

/** 类别裁决；rootDir 仅用于越界判定，不读取任何外部状态。 */
export function classifyShellCommandClass(
  shell: ShellScope,
  rootDir: string,
): ShellCommandClass;

/** 三值映射；公开 API 与审计字段沿用原词表。 */
export function toShellCommandSafety(cls: ShellCommandClass): ShellCommandSafety;
```

`PermissionPolicy.decide` 的入参增加**可选** `commandClass`，缺省时按 `shellSafety` 走现有逻辑——保证旧调用方（含测试）不破。

## 5. 硬禁区（Auto 与 FullAccess 也不放行）

工作区内不等于可写。以下路径由 PathSandbox 在 `write`/`edit` 解析后拒绝，**不进入审批流程**（问也不该给，因为一次写入即不可逆）：

| 路径 | 理由 |
|---|---|
| `.git/hooks/**` | 写入即获得下次任意 git 操作的代码执行 |
| `.git/config`、`.git/modules/**` | 可改 remote 指向、注入 `core.hooksPath` |
| `.env`、`.env.*` | 密钥覆盖与窃取前置；**豁免** `.env.example` / `.env.sample` / `.env.template` |
| `.kapibala/**`（含 `permissions.json`、`mcp.json`） | **规则/MCP 配置被工具写入 = 自我提权或自我扩权** |
| `~/.kapibala/**`、`~/.ssh/**` | 已由 workspace 外边界拦住，作为纵深兜底 |

实现：`SandboxConfig` 增加 `protectedPaths?: readonly string[]`，在 `resolveSafePath` 的物理检查之后追加判定，命中抛 `ToolError('Access denied: protected path')`。错误码沿用 `PERMISSION_DENIED` 前缀，审计记 `decision: 'deny', decisionSource: 'protected_path'`。

**shell 同样受硬禁区约束**：`run_command` 不经过 PathSandbox，因此 `command-class` 必须解析可识别的写入形态（`>`/`>>`/`tee`/`cp`/`mv`/`sed -i`/`find -delete`）的目标；命中硬禁区直接判 `deny`，不进入审批。含变量、`eval`、`bash -c` 等不可解析写法归 `unknown`，保守询问，并在 §11 记录残余风险。

**不变量**：规则文件只能由宿主的显式命令（`/permissions allow …`、桌面设置页）写入，任何工具（含 MCP 提供的工具）都不得写。这条要有单测，不能只靠文档。

## 6. 审批记忆三级

现状只有 `once` 与 `session`，且 `session` 键过细。改为：

| 级别 | 生效范围 | 存储 | 键 |
|---|---|---|---|
| `once` | 本次调用 | 内存 | — |
| `session` | 本会话 | 内存 | **规则键**（见下），不再是完整输入 |
| `project` | 该 workspace 长期，**需项目已信任 + 文件摘要确认** | `<workspace>/.kapibala/permissions.json` | 规则键 |
| `global` | 所有 workspace | `~/.kapibala/permissions.json` | 规则键 |

**项目规则的加载门槛（评审决议）**：项目未信任时规则文件视为不存在；首次加载与内容变更都要用户按文件摘要显式确认；项目规则 `maxClass` 不得高于 `workspace-write`，`network` / `destructive` 的 `allow` 只能来自全局规则。项目规则文件本身属于 §5 硬禁区，工具不可写。

规则形态对齐 opencode，但增加风险类约束：

```ts
interface PermissionRuleEntry {
  action: string;        // 工具名，如 run_command / write_file
  resource: string;      // 资源模式：'pnpm test*'、'git status*'、'src/**'
  effect: 'allow' | 'deny';
  /** 该规则只对不高于此风险类的命令生效。 */
  maxClass: ShellCommandClass;
}
```

**关键不变量**：命中 `allow` 规则时，若当前命令的 `class` 比 `maxClass` 更危险，规则**不生效**，回落到正常裁决。否则 `pnpm:*` 会把 `pnpm publish` 一起放过——这是前缀匹配最典型的越权路径。

规则键的 `resource` 只允许「程序 + 子命令前缀」或「workspace 内路径模式」，**不允许裸程序名扩展到网络/破坏类**。校验在写入侧做（`validatePermissionRules` 同款强制），拒绝含糊规则。

## 7. 落盘与不变量

- 规则文件是**宿主本地配置**，不进会话历史、不上 wire、不进 `presentation`——否则模型可伪造或读取他人规则。
- 审批决策继续走 `audit('tool.decided')`，`decisionSource` 增加 `'rule_project'` / `'rule_global'` / `'protected_path'` 三值，便于事后归因「为什么没问」。
- 不新增会话控制记录类型（与 010/012/013 同口径），规则在会话开始时读入，运行期只读。
- 规则文件变更后，**当前会话立即重新加载**（不做进程级缓存），避免「改了配置要重启」。

## 8. 协议与兼容

| 面 | 变更 | 兼容性 |
|---|---|---|
| `SessionMode` | 不变（四值） | 协议整数版本 2 不加值；不承诺旧 `{major,minor}` 客户端兼容 |
| `ShellCommandSafety` | 不变（三值） | 公共 API 快照不变 |
| `PermissionDecision.source` | 新增 3 个枚举值 | 快照变更，需登记；属向后兼容的联合扩展 |
| `PermissionRequest` | 新增可选 `commandClass` | 可选字段，旧调用方不破 |
| `ApprovalRequest` | 新增可选 `impact?: { writes: string[]; network: boolean }` | 可选字段；CLI/桌面可忽略 |
| 规则文件 | 宿主本地，不上 wire | 无兼容问题 |

公共 API 快照按既有规则处理：小增量手工逐条插入 `current.json` / `migration.json`，**不用 `--update` 整文件重排**。

| 用例 | 断言 |
|---|---|
| §2.1 的 27 条命令回归表 | Auto 放行率从 30% 提升到 ≥60%；`safe` 判定的每条都确有工作区内前提 |
| 硬禁区写入 | 三档均抛 `PERMISSION_DENIED`，且**不产生审批请求**（不是「问了被拒」） |
| 规则自我提权 | 尝试用 `write_file` 写 `.kapibala/permissions.json` 必败 |
| 跨风险类规则 | `pnpm:*` allow 规则对 `pnpm publish` 不生效，仍询问 |
| 规则漂移 | 脚本内容变更（`scriptDigest` 变化）后旧会话批准失效 |
| 命令替换 / 变量 | `$(...)`、`$VAR` 仍 `unknown`，不因新表被误放行 |
| 越界 | cwd 越界、重定向目标越界均判 `escape` |
| Approval 回归 | 只读命令放行；`pnpm build` 仍询问（与 Auto 拉开梯度） |
| 读越界 | `cat ~/.ssh/id_rsa`、`rg secret /home` 在 Auto 下询问，不进放行集 |
| shell 写硬禁区 | `echo x > .git/hooks/pre-commit`、`cp x .env`、`tee .kapibala/permissions.json` 三档均 `deny`，且无审批请求 |
| 自写脚本 | 未跟踪/已修改脚本与 `package.json` 在 Auto 下询问；干净脚本仍放行 |
| vcs 破坏性 | `git restore -- .`、`stash drop`、`branch -D` 在 Auto 下询问 |
| 项目规则门槛 | 未信任不加载；摘要变更需重新确认；`network` allow 的项目规则写入即拒 |
| 非交互 | CLI `-p` / 无 TTY 下 `ask` 解析为 `deny`，不挂死 |
| 审计 | 每类 `decisionSource` 都能在 `/logs` 里归因 |

## 11. 明确不做与已知限制

**不做**：OS 级沙箱（macOS seatbelt / Linux landlock+seccomp / Windows AppContainer）、内核网络隔离、按进程的资源限额、子代理预审的默认开启。

**已知限制（写进文档，不得宣称已解决）**：

1. **「网络受限」是声明式的，不是强制隔离。** 轻围栏只能做到「可识别的网络程序必须询问」；`pnpm install` 的 postinstall、脚本内部发起的连接，拦不住。Release 与文档不得表述为「网络已隔离」。
2. **脚本内部作恶拦不住。** `pnpm build` 放行的前提是「执行仓库内代码」，若该脚本本身被污染（例如依赖投毒），轻围栏不提供保护。这是不上 OS 沙箱的直接代价。
3. **风险分级仍是启发式。** 新的类别表比程序白名单覆盖更广，但误判必然存在；因此 `unknown` 的默认处置保持 fail-closed（询问），并用 P2 的子代理预审判定，而不是放宽成放行。
4. **硬禁区是清单制。** 新增敏感路径需要同步维护；清单外的路径仍按工作区边界处理。
5. **shell 硬禁区只覆盖可解析写法。** `eval`、变量展开、`bash -c "$(…)"` 等无法静态归因，按 `unknown` 询问；FullAccess 下这类写法仍可能绕过清单。
6. **读命令越界只做静态路径识别。** `cat $(find / -name id_rsa)` 这类组合无法可靠拦截，归 `unknown`。
7. **项目规则依赖用户确认，不是安全边界。** 用户确认了宽规则就等于接受风险；规则页只负责可见与可撤销。

## 12. 术语

| 术语 | 含义 |
|---|---|
| 两轴 | 沙箱边界（能力上限）× 询问策略（何时找人），三档是两者的预设组合 |
| 风险类别 `ShellCommandClass` | 内部七值分类，单向映射到公开的三值 `ShellCommandSafety` |
| 硬禁区 | 即使完全访问也不可写的路径，由 PathSandbox 拒绝，不进入审批 |
| 规则键 | 审批记忆的匹配依据（程序 + 子命令前缀 / 路径模式），取代完整输入哈希 |
| `maxClass` | 规则生效的风险上限，防止前缀匹配跨类别越权 |

## 13. 专项评审决议（2026-11-21）

评审对象为本文件初稿；结论：**方向可实施**，两轴 + `maxClass` + 硬禁区与 Codex/Claude 的收敛方向一致，但初稿漏掉三类可验证的攻击面，已按下列决议回写正文。

### 13.1 决议

| # | 问题 | 决议 |
|---|---|---|
| 1 | 读命令不受 PathSandbox 约束 | `read` 类带显式路径参数且解析到 workspace 外 → `escape`（Auto/Approval 询问）；无路径参数保持放行 |
| 2 | 自写脚本执行 | Auto 放行前校验清洁度：目标脚本与 `package.json` 相对 HEAD 干净才放行；脏/未跟踪 → `unknown`，按规则键记忆一次批准 |
| 3 | 硬禁区与凭据文件 | `.env*` 豁免 `example/sample/template`；`.kapibala/**` 整根硬拒；`.github/workflows/**`、`.npmrc`、`.netrc`、`.git-credentials` 归 `escape`（询问，不硬拒） |
| 4 | 项目级规则 | 未信任不加载；首次与内容变更按摘要确认；`maxClass ≤ workspace-write`，危险类 allow 仅限全局 |
| 5 | shell 写硬禁区 | 可识别的写入形态（重定向 / `tee` / `cp` / `mv` / `sed -i` / `find -delete`）命中硬禁区 → `deny`，三档一致；不可解析归 `unknown` |
| 6 | vcs 破坏性 | `restore --`、`checkout --`、`stash drop` / `stash clear`、`branch -D`、`clean` 归 `destructive` |
| 7 | 非交互 | 无 TTY / `-p` 单次问答下 `ask` 解析为 `deny`，不得挂起 |
| 8 | 求值语义 | 规则冲突取最严（deny > ask > allow），不采用「最后匹配优先」 |

### 13.2 开源对照（仅取与本主题相关部分）

| 项目 | 与本稿的关系 |
|---|---|
| Codex CLI | 两轴模型（沙箱 × 审批）与「冲突取最严」已被本稿采纳；其项目规则需 `trust_level=trusted` 才加载，对应决议 4 |
| Claude Code | deny→ask→allow 与 `disableBypassPermissionsMode` 的收口思路一致；但其 Bash 前缀白名单已被证明可绕过，本稿用 `maxClass` + argv 判定替代 |
| opencode | `Permission.Rule{action,resource,effect}` 的规则形态被采纳；**不采纳**其「最后匹配优先」 |
| Gemini CLI | 非交互 `ask_user` 视为 deny，对应决议 7；其 policy priority 叠加不引入 |
| Cline / Roo | 按类别自动批准会退化成「模型判定」，不采纳；只借其分类维度 |
| goose / crush / aider | 工具级 allow/deny 粒度不足，本稿保持「工具 + 资源模式 + 风险上限」 |
