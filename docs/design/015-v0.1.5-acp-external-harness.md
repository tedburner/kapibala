# 015 · v0.1.5 外部 Agent Harness（ACP）与多任务会话（设计）

> 状态：**规划定稿**（2026-11-20 维护者定向 v0.1.5；2026-11-23 确认对标 T3 Code 开放第三方 ACP 生态接入）。
> 本文只做版本级方案与任务拆解，A0 实测通过前不承诺任何具体 Harness 已可用。
> 前置：v0.1.4 已于 2026-11-24 发布并交付整数协议版本 2 + 能力集合（014）。本版从 v0.1.4 发布后的 main 起分支 `v0.1.5`，
> 不把 wire 2 / 3 两次变更塞进同一版本。
> 外部证据：`codex-host` 本地文档 `docs/architecture/acp-implementation-research.md` 与
> `docs/architecture/acp-layer-follow-up.md`（固定提交 `26c3460`）；
> [T3 Code](https://github.com/pingdotgg/t3code)（`makeAcpAdapterV2` / `AcpAdapterV2Flavor` / `Local ACP command` / `ACP Registry`，基线提交 `1f698f0`）；
> 官方 [ACP Registry](https://github.com/agentclientprotocol/registry)。外部项目结论只作架构依据，
> 不代表本仓库已具备同等能力。

## 0. 一句话定义与版本承诺

v0.1.5 = **对标 T3 Code，在宿主层新增开放的「外部 Agent Harness（ACP）」独立会话域**：基于通用
ACP（Agent Client Protocol）客户端底座 + 极薄 Flavor 适配层，支持接入**任意遵循 ACP 协议的第三方或自研
Agent 进程**（自带订阅 / 本地认证 BYOS），把流式消息、思考、工具、计划与审批投影为与本地会话同构的只读视图，
支持同一宿主内多任务并行、任务列表与可验证的恢复；ACP 类型不进入 Core、公共协议或渲染层。

**承诺**

- 新增 `GenericAcpAdapter` + `AcpHarnessFlavor` + `ExternalSessionService` 领域，位置在 `packages/host`，**Core 零改动**；
- **三层接入形态（对标 T3 Code `Providers` 分层，M2 首版同批可用）**：
  1. **内置 Flavor 预设**：覆盖适配器接入型（Claude Code `claude-agent-acp`、Codex `codex-acp`）与原生内置 ACP Server 型（Antigravity `agy acp` 控制组、OpenCode `opencode acp`、Gemini CLI、Qwen Code 等，最终已验证名单以 A0 实测为准）；未安装或未登录时明确显示「未安装 / 需登录」，不伪造可用；
  2. **任意第三方 `Local ACP Command` 自定义接入（首版核心入口）**：对标 T3 Code `Local ACP command`，桌面设置页与 CLI `/external` 首版即支持添加任意本地 ACP 可执行程序（显示名 + 命令路径 + 逐行字面参数数组 + `envFrom` 环境变量名白名单 + 一键握手测试），复用外部工具自身登录态，不存 API Key；
  3. **官方 ACP Registry 只读模板预填**：内置源于官方 ACP Registry 的主流第三方 ACP 模板目录，新建时可一键预填推荐命令、参数与自备安装说明，**不静默后台下载或自动执行安装器**；
- 至少一条**真实 ACP Harness**完成「启动 → 单轮 Prompt → 流式更新 → 工具调用 → 审批 →
  取消 → 退出清理」闭环，并有可复核的运行证据；
- **Windows 第三方生态无 Shell 安全兼容**：保持 `shell: false` 禁止命令行拼接，对 Windows 下 npm 全局安装生成的标准 `.cmd` shim 做静态入口解包，改由显式 `node.exe <entry.js>` 直接拉起；
- 多任务：同一宿主内可并行运行多个外部会话（跨工作区优先；同工作区并行与文件检查点排入 v0.1.6 Git Worktree 专项），有任务列表、完成通知、取消与关闭；不把多个 Agent 编排成一个共享计划；
- 审批透传：ACP `session/request_permission` 原样展示选项，超时/取消默认拒绝；
  Kapibala 的 Auto / FullAccess **不**自动批准外部审批；
- 外部会话恢复仅在通过持久身份门禁时声明 `resumable`；未通过时明确不可恢复，不猜 ID、
  不伪造历史；
- 本地 wire 由整数 **`2` 升至 `3`**，新增能力 `external-session`；同版本配对，旧客户端握手即失败。

**不承诺**

- 不做 Git Worktree 自动分支隔离与 Shadow Git 文件级检查点回滚（整体排入 **v0.1.6**，同时服务本地 `/delegate` 与外部 ACP）；
- 不做外部会话的 fork / rollback / 会话导入导出 / 跨 Harness 历史迁移；
- 不做多会话共享一个 ACP 进程（v1 默认每会话独立进程）；
- 不实现 ACP 的 `fs/write_text_file`、`terminal/*`、`elicitation/create` 客户端方法（`fs/read_text_file` 默认关闭，仅在 A0 证实主流第三方 ACP 强依赖时才允许走 `PathSandbox` 只读受控评估）；
- 不做外部 Agent 之间的消息路由、共享任务清单或自动编排；
- 不替外部 Agent 提供沙箱、网络隔离或写租约；不宣称 Kapibala 的 PathSandbox 覆盖外部工具；
- 不自动下载安装第三方 ACP 适配器或 Registry 包，不内置 API Key，不做远程 / SSH Harness；
- 不做桌面 mention 语法与外部任务结果自动注入父会话（后置）。

## 1. 与现有委派的分界

| 能力 | 执行者 | 会话归属 | 权限 | v0.1.5 处置 |
|---|---|---|---|---|
| `/delegate`（v0.1.3） | 本仓库 Core 子代理 | 同一 `SessionManager` 的 detached 会话 | 继承父会话并只收紧；走 `WorkspaceLeaseCoordinator` | **不扩展**为外部 Harness；语义不同，避免把两种生命周期混成一种 |
| 外部 Agent 会话（本文） | 外部原生命令 / ACP 适配器 | 宿主外部域独立登记，不进入 Core 会话树 | 由外部 Agent 自身决定；Kapibala 只透传审批 | 新增 `/external` 与桌面「外部代理」 |
| 远期多 Agent 编排 | 多个本地 / 外部会话 | 共享计划与任务分派 | 另立设计 | 不在本版 |

`/delegate` 的 outbox 完成通知、保留上限与父子审计不能被外部会话复用：外部会话没有
Core `runId`、没有 `parentId`、也不会自动向父会话写背景消息。两者的相似点只在 UI 列表，
不在执行契约。

### 2.2 外部实现与 T3 Code 对标拆解

codex-host：

- 接入结构是 `Host Runtime → HarnessAdapter / HarnessSession → 具体 Adapter → ACP Transport →
  @agentclientprotocol/sdk → 原生 ACP 进程`，ACP 类型与 `_meta` 留在各 Adapter 内；
- 8 个 ACP 接入（Antigravity、Grok、Kimi Code、Kiro CLI、Cursor CLI、Devin、CodeBuddy、
  WorkBuddy；WorkBuddy 复用 CodeBuddy 实现），可写会话默认每会话独立 Transport / 进程；
- Antigravity 的只读池是「跨历史会话串行读取复用」，不是多个可写会话共享连接；
  其 2 个合成会话并发实验只覆盖文本 Prompt，不能推广为共享写连接已成立；
- 持久身份门禁要求：Native Session ID 跨重启稳定、每个 User Turn 有持久 opaque Turn key、
  实时与恢复后的 Snapshot 引用一致、Snapshot 来自 Harness 权威历史；任一不满足，
  不得声称可靠恢复。

T3 Code（本版重点参考的产品与架构模型）：

- **三层外部代理入口（`Settings → Providers`）**：
  1. **内置一等预设（Built-in Flavors）**：底层共用 `makeAcpAdapterV2` + `AcpSessionRuntime`，各 Agent 的细微差异（如 Prompt 组装 `buildPrompt`、工具调用归一 `normalizeToolCall`、权限选项筛选 `answerablePermissionOptions`、认证错误提示）通过极薄的 `AcpAdapterV2Flavor` 声明式钩子表达，避免每接一家重写全套会话状态机；
  2. **Local ACP command（任意本地第三方命令）**：用户直接填写显示名、可执行文件名/路径与逐行字面参数数组（不拼 shell），即可挂载任何社区或自研的 ACP 兼容二进制/包装器；凭证与订阅登录态（如 `claude auth login`、`codex login`、OAuth）完全归属本地外部 CLI（BYOS），宿主零代管 Token；
  3. **ACP Registry 目录发现**：依托官方 `agentclientprotocol/registry`（`registry.json` 定义 `binary` / `npx` / `uvx` 三种标准分发描述），降低用户手查第三方启动命令的门槛；
- **进程与并发边界**：`supportsMultipleProviderThreadsPerSession` 在通用 ACP、Claude、Cursor 等均为 `false`，通用 ACP 仍是每会话独立 Runtime / 进程；T3 Code 支持同仓库多 Agent 并行的前提是绑定 **Git Worktree 隔离 + Checkpoint Diff**（本仓库拆分为 v0.1.5 先交付 ACP 独立会话域，v0.1.6 紧接交付 Worktree 隔离与文件检查点）。

结论：**共享的是通用 ACP 状态机、Flavor 差异钩子与视图投影，不是原生进程**。v0.1.5 完整吸收 T3 Code 的「通用底座 + 薄 Flavor + 首版开放 Local ACP Command + Registry 模板目录」分层，后置共享连接与 Worktree。

## 3. 目标架构

```text
Desktop renderer / CLI
  -> 宿主公共方法（wire 3 external/*）
    -> ExternalSessionService（状态机、注册簿、审批、并发）
      -> GenericAcpAdapter + AcpHarnessFlavor（通用 ACP 会话运行时 + 可选轻量差异钩子）
        -> AcpConnection（JSON-RPC 2.0 over stdio，窄子集）
          -> 外部 ACP 进程（内置预设 / Registry 模板 / 任意第三方 Local ACP Command）
```

放置：

- 新域：`packages/host/src/host/external/`（含 `acp/`、`flavors.ts`、`registry-templates.ts`）；
- 视图：`packages/host/src/view-model/external.ts`（只含展示类型，不含 ACP 类型）；
- 协议：`packages/host/src/protocol/` 增量；契约快照 `scripts/fixtures/protocol/v3/contract.json`；
- CLI：`packages/cli/src/commands/external.ts` 与命令目录；
- 桌面：`agent-host/desktop-host.ts` 装配、`renderer/external-*.tsx`、侧栏「外部代理」分组与设置页「外部代理」管理面板；
- Core：**零改动**；不新增 `SessionRecordType`；不新增 npm 发布包；`packages/host` 仍为私有。

为什么不是 Core 能力：外部进程启动、审批转发、任务列表都是宿主职责；Core 必须保持
Headless、零外部运行时依赖，且不能读取 `process.cwd()` / 启动子进程。外部会话也不进入
Core 的消息历史与压缩链路，避免两套历史互相污染。

## 4. 领域模型

### 4.1 Harness 定义与三层来源

```ts
/** 一条可启动的外部 Harness 定义；command/args 只描述启动方式，不承载密钥。 */
export interface ExternalHarnessDefinition {
  id: string;
  name: string;
  command: string;
  /** 逐项字面参数数组（绝不经 shell 拼接），对标 T3 Code Local ACP command 的逐行参数。 */
  args: readonly string[];
  /** 可选绑定的内置 Flavor 键（缺省走标准 ACP v1 默认行为）。 */
  flavor?: string;
  /** 若由官方 ACP Registry 模板创建，记录来源模板 id 供安装指引与排障展示。 */
  registryId?: string;
  /** 显式附加的非敏感环境变量；密钥请使用 envFrom 从父进程按名转发。 */
  env?: Readonly<Record<string, string>>;
  /** 从宿主进程环境按名转发的变量；只保存名字，不保存值。 */
  envFrom?: readonly string[];
  /** 内置预设标记；用户自定义 Local ACP Command 定义恒为 false/缺省。 */
  builtin?: boolean;
  enabled?: boolean;
}
```

- **三层来源统一收敛为同一 `ExternalHarnessDefinition`**：
  1. **内置 Flavor 预设**（代码侧提供，不物化进用户配置文件；用户覆盖同 `id` 时以用户定义为准）：首批包含原生 ACP 类（`opencode`、`gemini`、`qwen-code`、`agy` 控制组）与官方适配器类（`claude-code` → `claude-agent-acp`、`codex` → `codex-acp`），实际默认展示列表与启动参数由 A0 实测锁定；未安装或握手失败时 `available: false` 并给出清晰安装/登录指引，不自动下载；
  2. **官方 ACP Registry 只读模板（`ACP_REGISTRY_TEMPLATES`）**：随宿主静态内置一份经审核的官方 ACP Registry 元数据快照（含名称、推荐 `command/args`、自备安装命令说明），用户在桌面「从 ACP 目录添加」或 CLI 选择模板时只预填表单，保存后落为用户定义；
  3. **自定义 `Local ACP Command`（M2 首版即开放 UI 与测试连接）**：面向不在预设与模板内的任意第三方或自研 ACP Agent，用户直接填写名称、`command`、逐行 `args` 与可选 `envFrom`，保存前/后均可一键执行 `inspect` 握手验证。

### 4.2 会话状态

```ts
/** 外部会话的宿主状态；ended 是终态，failed 保留最近错误供列表解释。 */
export type ExternalSessionStatus =
  | 'starting'
  | 'idle'
  | 'running'
  | 'waiting_approval'
  | 'cancelling'
  | 'ended'
  | 'failed';

/** 宿主登记的外部会话；nativeSessionId 是不透明原生身份，禁止拼路径或当授权凭据。 */
export interface ExternalSessionRecord {
  id: string;
  harnessId: string;
  workspaceRoot: string;
  /** 从首轮输入首行生成，最长 80 字符并已脱敏；不保存完整 Prompt。 */
  title: string;
  status: ExternalSessionStatus;
  nativeSessionId?: string;
  /** 仅当持久身份门禁通过且 Harness 声明 load 能力时为 true。 */
  resumable: boolean;
  createdAt: number;
  updatedAt: number;
  lastError?: string;
}
```

### 4.3 通用 Adapter 与轻量 Flavor 钩子

参考 T3 Code 的 `makeAcpAdapter` + `Flavor` 分层与 codex-host 的窄接口原则，**不为每个第三方 Agent 单独维护一套会话状态机**——所有 ACP 目标共用同一个 `GenericAcpAdapter`，厂商差异收敛在纯声明式的 `AcpHarnessFlavor`：

```ts
/** 针对特定 ACP Agent 的可选轻量差异钩子；自定义第三方命令缺省使用标准默认实现。 */
export interface AcpHarnessFlavor {
  readonly id: string;
  /** 工具调用标题或分类的微调归一（不改变审批选项与原始入参）。 */
  normalizeToolTitle?(rawName: string, input?: Record<string, unknown>): string | undefined;
  /** 将常见认证缺失或适配器缺失 stderr 翻译为可操作的中文登录/安装提示。 */
  diagnoseFailure?(info: { code?: number; message: string; stderrTail: string }): string | undefined;
  /** 是否通过持久身份门禁（默认 false，仅 A0 实测通过四项门禁的 Flavor 允许开启）。 */
  readonly verifiedResumable?: boolean;
}

/** 适配器对外声明的能力；未声明即不支持，不做猜测式降级。 */
export interface ExternalCapabilities {
  /** 协议支持 session/load；具体会话能否恢复仍由持久身份门禁逐会话判定。 */
  load: boolean;
  /** 会发起 session/request_permission；不保证每次工具都询问。 */
  approvals: boolean;
  plans: boolean;
  usage: boolean;
}

/** 具体 Harness 的适配面；事件通过异步迭代器向上游投影，不把 ACP 对象泄漏出去。 */
export interface ExternalHarnessAdapter {
  readonly harnessId: string;
  inspect(): Promise<{ available: boolean; version?: string; reason?: string }>;
  open(input: {
    workspaceRoot: string;
    cwd: string;
    /** 仅恢复路径使用；提供时必须走 session/load，不允许伪装成新建。 */
    nativeSessionId?: string;
    signal: AbortSignal;
  }): Promise<{ nativeSessionId?: string; capabilities: ExternalCapabilities }>;
  prompt(sessionId: string, text: string, signal: AbortSignal): AsyncIterable<ExternalEvent>;
  /** 回复挂起的 ACP 审批；optionId 必须来自该请求，未知或过期一律拒绝。 */
  respondPermission(sessionId: string, approvalId: string, optionId: string): Promise<void>;
  cancel(sessionId: string): Promise<void>;
  close(sessionId: string): Promise<void>;
}
```

- `inspect` 执行可执行文件解析 + 短超时 `initialize` 探针握手（创建零会话后立即关闭），真实确认目标确实说标准 ACP 协议而非仅存在于 `PATH`；
- `open` 负责 `initialize` + `session/new`（或 `session/load`）；`nativeSessionId` 允许缺失；
- `prompt` 的迭代器在轮次 settle 后结束；审批请求经 `approval_requested` 事件上报，
  服务层等待用户选择后调用 `respondPermission`，适配器才向 ACP 回包；取消通过
  `session/cancel` 与 AbortSignal 双路径；
- `close` 必须可重复调用；失败不吞掉，由服务层记录为 `failed`。

### 4.4 事件归一

`ExternalEvent` 只表达展示与状态，不携带 ACP 原始 JSON：

| 事件 | 来源 | 去向 |
|---|---|---|
| `text_delta` / `thought_delta` | `agent_message_chunk` / `agent_thought_chunk` | 复用 `ViewBlock` |
| `tool_started` / `tool_updated` / `tool_finished` | `tool_call` / `tool_call_update` | 复用 `ViewTool`（含 status、input、result） |
| `plan_updated` | ACP plan update | 映射为 `ViewTodoState`，只用于外部任务视图，**不合并**到当前本地会话的 todos |
| `mode_updated` / `model_updated` | ACP mode / model 通知 | 只显示，不改变 Kapibala 设置 |
| `approval_requested` / `approval_closed` | `session/request_permission` | 外部审批面（见 §6） |
| `notice` | ACP notice / 适配器诊断 | `ViewNotice`（已脱敏） |
| `turn_settled` / `process_exited` | Prompt 终态 / 进程退出 | 更新会话状态与完成通知 |

非文本内容（图片、音频、资源链接）v1 只显示占位，不下载、不执行；避免把外部内容当成
本地文件或 HTML 预览。

### 4.5 持久身份门禁

只有同时满足以下四项，`ExternalSessionRecord.resumable` 才能为 `true`：

1. Native Session ID 在宿主重启后保持稳定；
2. 每个 User Turn 有持久、opaque、唯一的 Native Turn key；
3. 实时 `turn_settled` 的引用与重新 `session/load` 后 Snapshot 的引用完全相同；
4. Snapshot 来自 Harness 的权威历史，不是适配器在内存里维护的第二份 Transcript。

禁止把随机 UUID、`replay-1` / 数组下标、仅当前进程存在的请求 ID、消息正文或时间戳
当作持久 Turn key。若 Harness 没有稳定 ID，适配器必须返回 `resumable: false`，不得
在恢复时猜测。该门禁直接沿用 codex-host 的接入 Gate；v0.1.5 不实现 Fork / Rollback，
Turn key 只用于去重、排序与恢复一致性校验。

### 4.6 持久化与恢复

- 新文件 `~/.kapibala/external/sessions.json`：只存会话元数据（`ExternalSessionRecord`），
  不存消息正文、不存工具结果、不存密钥；权限 0600，写事务同 MCP 配置（锁 + 重读 + 校验 + 原子替换）；
- **不新增 Core 落盘记录类型**，不写会话 sidecar，不参与压缩与历史闭合；
- 宿主重启后：读取登记簿，能 `session/load` 且门禁通过的外部会话可重新附加；
  否则标记 `ended` 并说明「原始 Harness 不支持恢复」，不展示伪造历史；
- 进程存活期间，视图状态在宿主内存中维护；桌面重连从宿主快照重建，不依赖 renderer 缓存；
- 关闭会话只结束进程并保留元数据；删除会话才移除登记（A3 提供手动删除）。

## 5. ACP 传输与进程

### 5.1 协议子集

v1 只实现客户端侧所需的窄子集：

| 方向 | 方法 | v1 |
|---|---|---|
| 客户端 → Agent | `initialize` | 支持（版本、能力协商） |
| 客户端 → Agent | `authenticate` | 按 Harness 声明调用；通常由外部 CLI 自行登录 |
| 客户端 → Agent | `session/new` | 支持 |
| 客户端 → Agent | `session/load` | 仅当 Harness 声明支持；否则 `resumable: false` |
| 客户端 → Agent | `session/prompt` | 支持（流式最终响应） |
| 客户端 → Agent | `session/cancel` | 支持（通知） |
| 客户端 → Agent | `session/set_mode` | v1 不主动调用；只显示当前 mode |
| Agent → 客户端 | `session/request_permission` | 支持，映射为外部审批 |
| Agent → 客户端 | `fs/read_text_file` | 默认**不支持**（返回 method not found）；A0 专项评估第三方原生 ACP 依赖度，仅当主流目标强依赖时才在宿主侧挂接 `PathSandbox` 只读受控桥接 |
| Agent → 客户端 | `fs/write_text_file` | **不支持**，返回 method not found |
| Agent → 客户端 | `terminal/*` | **不支持** |
| Agent → 客户端 | `elicitation/create` | **不支持** |
| Agent → 客户端 | `session/update` 通知 | 支持并归一 |

明确不实现 `fs/write_text_file` / `terminal/*` 的原因：这些写操作与终端执行若搬回 Kapibala 宿主，
既绕过 Core 的 PathSandbox 与审批，也显著扩大攻击面。外部 Agent 应使用自己的执行工具与权限模型；
对于 `fs/read_text_file`，A0 Spike 将实测 `opencode acp`、`gemini` 等代表性第三方原生 ACP 在空
`clientCapabilities: {}` 下是否完全自洽——若均自带读工具则维持全关，若确有主流编辑器向第三方 ACP
强依赖客户端读文件，也仅开放经 `fs.realpathSync.native` 与工作区边界校验的只读读取（单文件大小设上限、
排除硬禁区敏感文件），绝不放开写入或命令执行。

`initialize` 的客户端能力声明必须与实现严格一致：默认只声明 `session/request_permission` 所需的
客户端能力，**不声明**文件系统写入与终端能力；`session/new` / `session/load` 的 `mcpServers`
固定为空数组，v1 不把 Kapibala 的 MCP 工具注入外部 Harness，也不把外部 Harness 的 MCP
配置带回本地设置。`session/prompt` 的文本由适配器封装为 ACP content block，宿主不拼接
额外系统提示。

### 5.2 编解码与依赖

- 新建 `AcpConnection`：JSON-RPC 2.0 over stdio，按 LF 分帧，支持双向请求、通知、取消与超时；
- **不新增 `@agentclientprotocol/sdk` 依赖**：v1 只覆盖上表子集，内置实现规模可控，便于
  固定帧预算、错误分类与安全边界；codex-host / T3 使用官方 SDK 不构成本仓库必须引入的理由；
- 复用 `JsonlDecoder` 的「按字节限帧、UTF-8 fatal、超帧即断开」原则，但另写 ACP 编解码，
  不把本地 wire 的 `WireMethod` / `RpcPeer` 混入；
- 帧预算：单帧 8 MiB；超限终止会话并记录 `EXTERNAL_FRAME_LIMIT`，不截断后继续；
- 请求超时：`initialize` 15s，`session/new` / `session/load` 60s，`session/prompt` 无固定上限
  （由会话级取消与空闲终止控制），其余 30s；超时取消对应 Promise 并关闭连接。

若 A0 证明官方 SDK 在双向请求、版本协商或取消语义上明显降低风险，A1 可重新评估引入；
引入即成为宿主运行时依赖，必须单独评审许可证、体积与升级策略，不静默夹带。

### 5.3 进程监督与 Windows npm Shim 无 Shell 解包

- `spawn(resolvedCommand, resolvedArgs, { cwd: workspaceRoot, env: externalLaunchEnv(...), stdio: pipe, shell: false })`；
- 可执行解析：显式绝对路径或 `PATH` 查找；拒绝目录、非普通文件、无执行权限；
- **严禁 `shell: true` 或命令行字符串拼接**；`args` 始终以数组原样传递；
- `externalLaunchEnv()` 使用白名单（`PATH`、`HOME` / `USERPROFILE`、`TMPDIR` / `TEMP`、
  `SHELL`、`LANG` / `LC_ALL`、`TERM`、`XDG_CONFIG_HOME` / `XDG_CACHE_HOME`、Windows 的
  `SystemRoot` / `ComSpec` / `PATHEXT` / `APPDATA` / `LOCALAPPDATA` 等），再合并 Harness
  定义的 `env`，最后按 `envFrom` 从父进程取值；绝不整体继承 `process.env`，
  `NODE_OPTIONS`、`ELECTRON_RUN_AS_NODE` 等注入变量不会进入外部进程；
- **Windows `.cmd` 入口无 Shell 安全兼容（2026-11-23 修正）**：在 Windows 生态中，通过 npm / pnpm
  全局安装的第三方 ACP 适配器与 CLI（如 `claude-agent-acp`、`codex-acp`、`gemini`、`qwen`）在 `PATH`
  下暴露的几乎全是 npm 生成的 `.cmd` shim；若一刀切拒绝 `.cmd`，Windows 桌面端将无法接入绝大多数 npm
  分发的第三方 ACP。因此宿主 `external/process.ts` 采用**静态入口解包 + `shell: false`**：
  1. 原生可执行文件（`.exe`，含 `agy.exe`、`opencode.exe`、`uvx.exe` 等）直接 `spawn(..., { shell: false })`；
  2. 命中 `.cmd` 时，静态匹配标准 npm/pnpm shim 模板，提取其指向的受管 `.js` / `.mjs` / `.cjs` 入口脚本并校验物理文件存在，改用显式解析到的系统 `node.exe` 执行 `[entryScript, ...args]`（全程 `shell: false`）；
  3. 非标准自定义 `.cmd` / `.bat`（含任意批处理分支或无法静态提取唯一脚本入口）一律拒绝，并返回可读诊断引导用户直接填写目标 `.exe` 或解释器绝对路径；
- stderr 只保留有界环形缓冲（32 KiB），展示前脱敏；进程退出映射为 `process_exited`，
  非零退出附退出码与安全摘要，不把完整 stderr 写日志；
- 关闭：先 `SIGTERM`，宽限 5s 后 `SIGKILL`；POSIX 使用进程组，Windows 使用 `taskkill /T`；
  必须回收后代进程。宿主退出时统一关闭所有外部会话，失败记录 `cleanup: failed`，
  不宣称已回收。

### 5.4 预算

| 预算 | 值 | 说明 |
|---|---:|---|
| 活跃外部会话 | 4 | 与 `maxConcurrentRuns` 同量级；超出返回 `EXTERNAL_CAPACITY` |
| 每个会话活动 Prompt | 1 | 第二个 Prompt 直接拒绝，不排队 |
| 已登记外部会话 | 50 | 超出要求先删除；不自动淘汰运行中的会话 |
| 单会话工具输出展示 | 64 KiB | 仅展示截断，不写第二份历史 |
| 单帧 | 8 MiB | 超限终止会话 |
| 空闲进程回收 | 30 分钟 | 关闭进程但保留元数据；再次 Prompt 时尝试恢复 |

同一工作区默认只允许 1 个处于 `running` / `waiting_approval` / `cancelling` 的外部会话；
空闲（`idle`）会话可以并存，但同一时刻仍只能有一个 Prompt 进入运行。跨工作区可并行。
该限制是**外部域内部**的保守策略，不声称协调了本地会话与外部 Harness 的写冲突（见 §11）。

## 6. 审批与安全

### 6.1 审批透传

```ts
/** 外部审批选项原样来自 ACP；宿主不重新解释 allow_always 的业务范围。 */
export interface ExternalApprovalOption {
  optionId: string;
  label: string;
  kind: 'allow_once' | 'allow_always' | 'reject_once' | 'reject_always';
}
```

- 收到 `session/request_permission` 时生成 `ViewExternalApproval`，包含工具名、目标与**完整选项**；
- 用户选择必须命中该请求实际提供的 `optionId`，服务端复核；不允许客户端伪造选项或改写参数；
- 超时（默认 120s，与本地审批一致）或会话取消 → 选择 reject 类选项；没有 reject 选项时
  关闭连接并标记失败，不默认允许；
- Kapibala 的 `Approval` / `Plan` / `Auto` / `FullAccess` 模式只作用于本地会话，
  **不能**自动批准外部审批；UI 必须显示「外部代理」标识；
- 审批决定记录元数据（会话、工具名、选项、时间），不记录原始命令/参数正文。

### 6.2 安全边界

- **外部 Agent 的权限模型不属于 Kapibala**：它可能在自己的配置下自动执行工具，甚至不发起
  审批；UI 不得暗示「Kapibala 已批准 / 已沙箱」。首次创建外部会话时显示一次性风险说明；
- 工作区必须已信任（`isProjectTrusted`）；未信任项目不提供外部会话入口；
- 启动环境显式构造；`envFrom` 只转发用户点名的变量，配置文件不保存密钥值；
- 外部输出按不可信文本处理：沿用宿主 `redactText`、ANSI 清理与长度预算；Markdown 渲染
  复用现有安全管线，不开启原始 HTML；
- ACP 请求的 `fs/write_text_file` / `terminal/*` / `elicitation/create` 一律拒绝（`fs/read_text_file` 默认拒绝，按 §5.1 A0 实测结论严格受控）；
- 外部进程工作目录固定为工作区根，不支持 per-harness 覆盖；进程继承的 cwd 不读取
  `process.cwd()`（宿主必须显式传入绝对路径）；
- 同一工作区多个外部写任务可能互相覆盖，宿主不提供跨域写租约；v1 以默认单外部会话 +
  显式警示收敛，同仓库并行 Worktree 隔离与文件检查点统一排入 v0.1.6。

## 7. 配置、发现与信任

- 新文件 `~/.kapibala/external/harnesses.json`：`{ version: 1, harnesses: ExternalHarnessDefinition[] }`；
- 写事务：独占锁 + 重读 + 全量 schema 校验 + 原子替换 + 0600；损坏时拒绝写入，不静默重建；
- 内置 Flavor 预设与官方 ACP Registry 只读模板只存在于代码，不物化到用户文件；用户保存模板或自定义 `Local ACP Command` 后写入 `harnesses.json`，覆盖同 `id` 时以用户定义为准；
- `inspect` 结果不落盘，按需探测（可执行路径解析 + 短超时 `initialize` 握手）；探测失败展示原因（未找到、非标准批处理包装器、握手失败、版本不兼容、需登录）；
- 不自动安装、不自动更新、不静默运行 `npx` / `uvx` 下载远程包；模板与预设提供清晰的自备安装命令说明；
- 认证优先使用外部 CLI 自身登录态（BYOS）；需要环境变量透传时由用户显式设置 `envFrom`，Kapibala
  不接管密钥存储；
- 项目信任沿用 `loadSettings` / `isProjectTrusted`；外部配置是全局的，但会话只能在已信任工作区根下运行。

### 8.2 视图模型

```ts
/** 可下发的外部会话摘要；不含 nativeSessionId、进程句柄或登记文件路径。 */
export interface ViewExternalSession {
  id: string;
  harnessId: string;
  harnessName: string;
  workspaceRoot: string;
  title: string;
  status: ExternalSessionStatus;
  resumable: boolean;
  createdAt: number;
  updatedAt: number;
  lastError?: string;
}

/** 外部审批卡；选项顺序即 Harness 提供顺序，宿主不重排。 */
export interface ViewExternalApproval {
  approvalId: string;
  sessionId: string;
  toolName?: string;
  target?: string;
  options: readonly ExternalApprovalOption[];
  expiresAt?: number;
}

/** 外部会话的只读展示；消息与工具复用本地会话的 ViewMessage / ViewTool。 */
export interface ViewExternalSnapshot {
  session: ViewExternalSession;
  sequence: number;
  messages: readonly ViewMessage[];
  pendingMessages: readonly ViewMessage[];
  operation?: ViewOperation;
  approvals: readonly ViewExternalApproval[];
  plan?: ViewTodoState;
  notices: readonly ViewNotice[];
}
```

- `ViewTodoState` 复用 013 的类型；外部 plan 只属于该外部会话，不与当前本地会话合并；
- `ViewMessage` / `ViewTool` 复用可保证桌面渲染、折叠、代码块与工具详情不需要第二套实现；
- `nativeSessionId` 只用于宿主恢复，**不下发到 renderer**；如需排障，显示短哈希而不是原值。

### 8.3 兼容

  若 `ViewExternalSnapshot` 进入公共 view-model 导出，逐条登记。

新增命令组 `/external`，不改变 `/delegate` 语义，并在首版直接支持第三方自定义 ACP 管理：

## 10. 桌面

1. **侧栏「外部代理」分组**：列出运行中 / 最近的外部会话，行内显示 Harness、工作区、状态、

4. **计划与工具**：ACP plan 映射为任务进度（复用 013 的 pill / 浮层或右侧 dock 的只读列表）；
   工具行复用 `ViewTool`，失败态与耗时同本地一致。

## 11. 多任务语义与并发

- **多任务 = 多个独立外部会话**，不是多个 Agent 共享一个计划；每个会话有自己的进程、
  原生 Session、审批队列与状态；
- 默认每会话独立进程，不做共享连接；即使未来共享，也只是连接复用，不是历史合并；
- 同一工作区默认只允许 1 个运行中的外部会话；跨工作区可并行；超出返回
  `EXTERNAL_WORKSPACE_BUSY`，UI 提示而不是静默排队（同仓库并行由 v0.1.6 Git Worktree 隔离解决）；
- 外部会话与本地会话可同时运行，但**不共享** `WorkspaceLeaseCoordinator`；
  本地写租约不能约束外部 Agent。UI 在外部会话运行时对同工作区本地运行给出警示，
  发布说明明确该边界；
- 外部会话完成后不自动唤醒父会话；用户通过列表 / `show` / 桌面视图读取结果；
- 关闭应用：先取消所有运行中轮次，再关闭进程；未通过身份门禁的会话标记不可恢复；
- 不做跨会话任务聚合、自动重试、自动重启或熔断后的静默重放。

#### 探针规范

- 一次性 NDJSON 客户端（Node 22+，零依赖）：spawn 目标、分帧、请求关联、响应 agent→client
  的 `session/request_permission`，并把 `session/update` 按到达顺序记入 transcript。
- 启动环境显式白名单：`PATH` / `HOME`（Windows 含 `USERPROFILE` / `SystemRoot` / `APPDATA` / `LOCALAPPDATA`） / `TMPDIR` / `LANG` / `LC_ALL` / `TERM` + 显式认证变量；
  禁止展开 `process.env`。`NODE_OPTIONS` 与 `ELECTRON_RUN_AS_NODE` 必须缺席（探针可打印子进程
  env 的**键名集合**自检，不打印值）。
- 记录项：命令行、版本、cwd、方法序列、每帧方向与时间戳、是否收到 `fs/*` / `terminal/*` 反向调用、错误码、退出码 / 信号、
  stderr 尾部（≤ 4 KiB）、退出后进程树检查。
- 脱敏：API Key / OAuth token / 邮箱 / 用户名；文本 chunk 截断到 2 KiB 并标记；提交样本不含密钥。
- 初始帧只报稳定 v1，不启用 v2 草案：

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{},"clientInfo":{"name":"kpbl-acp-spike","version":"0.0.0"}}}
```

> `clientCapabilities` 先留空：验证外部 Agent 是否完全使用自带工具执行；若目标发出 `fs/read_text_file`
> 请求，探针如实记录请求载荷与返回 `Method not found` 后的降级行为，作为 A0.5 边界决策依据。

- 审批回传选择既有选项；取消是通知，不是请求：

```json
{"jsonrpc":"2.0","id":42,"result":{"outcome":{"outcome":"selected","optionId":"<allow_once 的 optionId>"}}}
{"jsonrpc":"2.0","method":"session/cancel","params":{"sessionId":"<sessionId>"}}
```

#### 场景脚本（S1–S7）

| ID | 操作 | 断言 | 失败时记录 |
|---|---|---|---|
| S1 | `initialize` | `protocolVersion === 1`；`agentInfo` / `agentCapabilities` / `authMethods` 原样入档 | 错误码、stderr、协商版本 |
| S2 | `session/new`（cwd = 临时目录，`mcpServers: []`）→ `session/prompt`「只回复 DONE，不调用工具」 | 返回 `sessionId`；至少 1 个 `agent_message_chunk`；`stopReason` 为 `end_turn` | 方法序列、超时点 |
| S3 | 审批允许：prompt 要求在 cwd 创建 `kpbl-acp-proof.txt`（内容 `OK`） | 收到 `session/request_permission`；回 `allow_once`；工具执行成功；文件存在；`tool_call` / `tool_call_update` 可投影 | 选项 kind / optionId、工具状态 |
| S3T | 审批超时：收到 `session/request_permission` 后不响应，客户端按约定超时（如 30s）回 `cancelled` | 超时后工具**不**执行；轮次以取消 / 明确失败结束；无隐式允许 | 超时点、取消后的 `stopReason` |
| S4 | 审批拒绝：同一 prompt 在全新目录执行 | 回 `reject_once`；文件**不**存在；轮次正常结束或明确失败，不静默放行 | 拒绝后的 `stopReason`、错误 |
| S5 | 取消：prompt 要求执行长任务（如 `sleep 60` 后回复），收到首个 update 后发 `session/cancel` | `session/prompt` 以 `stopReason: "cancelled"` 结束；取消后不再执行新工具 | 取消后仍到达的 update（记录保真度，不隐去） |
| S6 | 重启与 `session/load`：结束进程后重启，若声明 `loadSession` 则加载同一 `sessionId` | 重放消息 / 工具 / 计划可核对；ID 与顺序稳定；否则记 `resumable: false` | load 错误、重放差异 |
| S7 | 退出清理：关闭 stdin | 10s 内退出；退出码 / 信号入档；无孤儿进程 | 残留进程树、stderr 尾部 |

- S5 若目标拒绝执行 shell，可改用长生成 prompt；记录实际触发方式，不把「没触发」当通过。
- S3 / S3T / S4 必须使用默认权限模式：不得给 `agy acp` 加 `--dangerously-skip-permissions`，
  也不得用适配器的自动批准开关，否则审批链路未被验证。若目标默认**不发起**审批（直接执行写操作），
  如实记「不发起审批」——这是安全边界事实，不得记成审批通过。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Claude / Codex 适配器版本漂移或缺少运行时 | 单一厂商适配器受阻 | A0 硬门禁；依托 `GenericAcpAdapter` + 原生第三方 ACP 预设 + `Local ACP Command` 保证开放生态独立成立，受阻厂商明确标注「需适配器 / 需登录」 |
| Windows npm 全局 `.cmd` shim 无法在 `shell: false` 下直跑 | Windows 用户接不进 npm 第三方 ACP | `external/process.ts` 静态解包标准 npm/pnpm shim 至 `node.exe <entry.js>`，拒绝非标批处理，不开 `shell: true` |
| 部分第三方 ACP 请求 `fs/read_text_file` | 空能力下读不到文件 | A0.2 实测主流第三方原生 ACP；若确有强依赖，仅提供 `PathSandbox` 管控的只读读取，写与终端仍硬拒 |
| 外部 Harness 不发起审批 | 用户误以为 Kapibala 已管控 | 首次风险说明 + 常驻「外部代理」标识 + 文档明确边界 |
| `session/load` 身份不稳定 | 恢复后历史错位 | 四项门禁；不通过即 `resumable: false`，不猜 ID |
| 进程泄漏 / 孤儿 | 资源与安全风险 | 进程组 / 树回收；宿主退出统一关闭；失败可见 |
| `process.env` 泄漏 | 凭证进入第三方进程 | 白名单 + `envFrom` 显式点名；静态单测拦截全量继承 |
| 同工作区写冲突 | 文件被覆盖 | v0.1.5 默认单外部会话 + 显式警示；同仓库并行 Worktree 隔离排入 v0.1.6 |
| ACP 版本 / 能力漂移 | 适配器失效 | `initialize` 协商；不支持即拒绝；A0 固定版本记录；不静默降级 |
| 渲染层被外部内容拖垮 | XSS / 卡顿 | 复用安全 Streamdown Markdown、长度预算、无原始 HTML、非文本占位 |
| 多任务 UI 膨胀 | 误认会话树 | 外部任务独立分组；不复用本地会话父子关系；不自动注入历史 |

## 15. 已定口径与待 A0 决定

**已定（2026-11-20 规划锁定，2026-11-23 对标 T3 Code 增补确认）**

1. v0.1.4 已于 2026-11-24 冻结收口发布；v0.1.5 唯一主题 = **第三方 ACP 外部 Agent Harness 开放接入 + 多任务会话**。
2. ACP 是第一传输；外部域在 `packages/host`（`GenericAcpAdapter` + 薄 `AcpHarnessFlavor`），**Core 零改动**。
3. 对标 T3 Code 提供三层入口：**内置 Flavor 预设**（含原生 ACP CLI 与适配器型 CLI）、**官方 ACP Registry 只读模板预填**、以及**首版 M2 必达的任意第三方 `Local ACP Command` 自定义接入 UI 与 CLI**。
4. Windows 下保持 `shell: false`，通过静态解包标准 npm `.cmd` shim 至显式 `node.exe <entry.js>` 兼容第三方 npm ACP 工具。
5. 每会话独立进程；不做共享连接；多任务 = 多会话，不是多 Agent 编排。
6. v0.1.5 不做 Git Worktree 与 Shadow Git 文件检查点（整体排入 **v0.1.6**），不做 fork / rollback / 会话导入导出 / `fs/write_text_file` / `terminal/*` / elicitation。
7. 审批原样透传、超时拒绝、全局模式不自动批准；外部 Harness 的权限模型不被 Kapibala 替代，凭证走外部 CLI 自有登录态（BYOS）与 `envFrom` 变量名转发。
8. 不新增 npm 发布包；默认不引入 ACP SDK，使用内置窄实现。
9. wire 升至整数 **`3`**，能力 `external-session`；版本严格相等。
10. 外部元数据写 `~/.kapibala/external/sessions.json` 与 `harnesses.json`，不新增 Core 记录类型。
11. 同工作区默认只允许 1 个运行中的外部会话；跨工作区并行。

**待 A0 决定（不阻塞本文架构）**

- 首批内置 Flavor（`agy` / `opencode` / `gemini` / `claude-agent-acp` / `codex-acp` 等）的实测启动命令、版本下限与认证方式；
- 第三方原生 ACP 在 `clientCapabilities: {}` 下是否完全自洽，是否需要只读 `fs/read_text_file` 受控桥接；
- 各目标 Harness 的身份门禁结果与 `resumable` 结论；
- 平台实测矩阵（Windows `.cmd` shim 解包与 macOS 进程回收实测结果）；
- 官方 SDK 是否在 A1 改判引入（默认否，需单独评审）。

## 16. 明确不做（v0.1.5）

- Git Worktree 自动分支隔离与 Shadow Git 文件级检查点回滚（排入 **v0.1.6**）；
- 多 Agent 共享计划、互相发消息、自动分工与编排画布；
- 外部会话的 Fork / Rollback / 会话导入导出；
- 共享 ACP 进程或多会话复用一条写连接；
- ACP 客户端文件写入（`fs/write_text_file`） / 终端（`terminal/*`） / `elicitation` 能力；
- 自动下载 / 安装 / 更新第三方 Harness、Registry 包或适配器；
- 外部 Agent 的模型目录与 Kapibala 模型设置统一；
- 外部结果自动注入本地会话历史或自动唤醒父会话；
- 把 Kapibala 自身反向暴露为 `kpbl acp` Server（排入 **v0.1.8+**）；
- 远程 / SSH / 云端 Harness，桌面 mention，跨设备同步。
