# 008 · v0.1.4 会话级监视（watch）设计

> 状态：规划中（v0.1.3 之后的下一版本候选主题）
> 依赖：v0.1.3 交付的 `SubagentOutbox` / `SessionInbox` 通知通道与 `send_agent` 续聊语义
> 范围：Core 控制记录与投递、宿主触发源、CLI `/watches`、桌面徽标

## 1. 定位

让模型或用户在当前会话内登记一个**外部条件监视**（进程退出、文件变化、端口就绪），本轮正常结束；条件命中（或超时）后，由宿主以背景消息落盘并**自动续跑一轮**，让对话继续。

这与三类相邻能力的分界：

| 能力 | 执行体 | 生命周期 | 触发源 |
|---|---|---|---|
| 子代理（`spawn_agent`） | 独立 `AgentSession` | 有 run、有终态 | 子代理自身结束 |
| 委派会话（v0.1.3 detached） | 独立 `AgentSession` | 终态保留、可续聊 | 用户或父模型发起 |
| **监视（本文）** | **无执行体** | 只是一条控制记录 | **外部条件** |
| `Schedule`（平台定时任务） | 宿主外部 | cron 周期 | 时间 |

结论：它是**会话级异步唤醒**，不是第四种 agent，也不复用 `Schedule` 的 cron 语义。

## 2. 现状核查

已实现：

- `spawn_agent`（`packages/core/src/runtime/agent/tools.ts:31`）
- `SubagentOutbox`（`packages/core/src/runtime/agent/outbox.ts:111`）：JSONL 持久化 + `eventId` 幂等
- `SessionInbox`（同文件 `:228`）：回读父历史按 `payload.subagentSource.eventId` 去重，写 `role: 'user'` 背景消息
- 全局控制记录机制（`session-store.ts:26`、`:53`）

**未实现**（本版要补）：

- 没有任何 `watch` / `wait_for` 工具或命令（全仓检索无命中）
- 没有 watcher 的落盘类型，也没有「外部条件 → 会话消息」的触发源
- 通知通道目前只有「子代理终态」一个触发源

所以这是全新能力，且刻意放在 v0.1.3 之后：v0.1.3 正在把 detached 续聊接入同一通知通道，同版本再改通道会互相干扰。

## 3. 为什么不做模型侧轮询

| 打法 | 问题 |
|---|---|
| 模型自调 `sleep` + `check` | 每轮烧 token 与上下文，轮次上限先到，跨小时不可行 |
| 工具内阻塞等待 | 占住一整轮 run，取消/超时语义难做，且无法跨重启 |
| **事件驱动续跑（本文）** | 零空转，可跨小时与跨进程，复用既有幂等通道 |

## 4. 领域模型

```ts
export type WatchKind = 'file_change' | 'process_exit' | 'port_ready';

/** 一条监视的规格；deadlineAt 必填，杜绝无限期监视。 */
export interface WatchSpec {
  kind: WatchKind;
  /** file_change: 工作区相对路径；process_exit: 本会话启动的进程句柄；port_ready: 端口号 */
  target: string;
  /** 轮询间隔，仅 file_change / port_ready；下限 2000ms，默认 5000ms */
  intervalMs?: number;
  /** 截止时间；到期投递 timeout 通知并关闭监视 */
  deadlineAt: number;
}

/** 监视状态；作为 watch_state 控制记录的载荷。 */
export interface WatchState {
  watchId: string;
  spec: WatchSpec;
  state: 'armed' | 'fired' | 'timeout' | 'cancelled' | 'orphaned';
  /** 触发序号，参与 eventId 组装；同一 watch 至多触发一次 */
  seq: number;
  /** 登记时的分支；通知必须落回该分支 */
  branchId: string;
  armedAt: number;
  closedAt?: number;
}
```

## 5. 触发源（v1 三类）

- **`file_change`**：轮询 `stat` 的 `size + mtimeMs`，变化后计算内容哈希确认；忽略 `.git`、`node_modules` 与 dist 产物。测试成本最低，作为 W1 首个落地源。
- **`process_exit`**：只允许监视**本会话工具启动的子进程**（运行时维护 childPid 表），禁止任意 pid；进程已不存在时直接 `fired`。
- **`port_ready`**：`TCP connect 127.0.0.1:<port>` 成功即 `fired`；仅 localhost，禁止外网地址。

v1 不做：webhook 回调（需要公网暴露）、CI/远端状态（需要 provider 适配，留 v2）。

## 6. 落盘与重建（关键约束）

新增全局控制记录 `watch_state`，**必须五处同步**，漏任一处会静默丢状态（`archived` / `pinned` 各踩过一次，见 AGENTS.md）：

1. `SessionRecordType` 联合（`session-store.ts:26`）
2. `SessionStore` 内的全局类型集合
3. `isGlobalControlRecordType`（`session-store.ts:53`）
4. `SessionManager.buildMetadata` 的元数据重建（`session-manager.ts:763` 附近）
5. `CrossProjectSessionCatalog` 的内联扫描（`catalog.ts`）

约束：`watch_state` 的 `parentId` 为 `null`，**不推进上下文叶子，也不改会话活动时间**；多次变更以「同 `watchId` 追加新记录、读时取最后一条」为准，不改写历史。

## 7. 投递与续跑

触发后：

1. 生成 `WatchNotification { eventId: `${watchId}:${seq}`, watchId, kind, target, state, seq }`
2. 以 `role: 'user'` 背景消息落盘到 `branchId`，正文为 `<watch-event watch=... kind=... state=... seq=...>` 结构化标签 + 人类可读摘要
3. 消息级元数据 `watchSource`（与 `subagentSource` 同层，不进 Provider wire），去重靠回读 `payload.watchSource.eventId`

**串行化**：`SessionInbox` 的去重与并发合并逻辑抽成共享 helper（`consumeBackgroundMessage`），`SessionInbox.consume` 对外行为不变，`WatchInbox` 复用同一实现，避免两套去重逻辑漂移。

**投递时机**（防与用户输入竞争）：

- 仅在会话**空闲**（无在途 run、无待审批）时投递并自动续跑；
- 有在途 run 时进入 pending 队列，`run_finished` 后 flush；
- 每会话每分钟最多 1 次自动续跑，超出只落盘不续跑（防止文件频繁变动造成风暴）。

**超时与取消**：`deadlineAt` 到期投递 `state: 'timeout'`；`watch_cancel` 投递 `cancelled`；两者都是终态，不再触发。

**跨重启**：`watch_state` 恢复后重新布置触发源；`process_exit` 因进程句柄失效标记 `orphaned` 并投递一次说明，**不静默丢弃**。

## 8. 工具与命令面

| 面 | 入口 | 说明 |
|---|---|---|
| 模型 | `watch_start` / `watch_cancel` | 参数即 `WatchSpec`；受权限与数量上限约束 |
| 用户 | `/watches` | 列表（监视中/已触发/已超时/已取消/已失联）、`cancel <watchId>` |
| 协议 | `watch/list`、`watch/cancel` | 需同时改 `protocol/types.ts`、`schema.ts`、`results.ts` 与桌面 `preload` |

术语遵循设计 007 §11：叫「监视」，状态词固定为**监视中 / 已触发 / 已超时 / 已取消 / 已失联**；不得称「定时任务」（与 `Schedule` 冲突）或「后台任务」。

工具显示名（别名）优化已移交 v0.1.3（[设计 007 §5.4](007-v0.1.3-cross-session-reference-and-delegation.md)），本版的 `watch_start` / `watch_cancel` 直接复用该投影层，不再各端单独实现。

## 9. 权限与安全

- 路径目标必须 `fs.realpathSync.native` 后在会话工作区根内（AGENTS.md 已记录两次短名失配）
- 端口仅 `127.0.0.1`
- `process_exit` 只接受本会话启动的进程句柄，禁止任意 pid
- 数量上限：每会话 8 个、全局 32 个；超限直接拒绝，不排队
- 所有 `watch_start` 经既有权限系统裁决，`Plan` 模式下拒绝

## 11. 风险

| 风险 | 后果 | 处置 |
|---|---|---|
| 控制记录漏同步 | sidecar 重建丢失监视状态 | W0 逐处断言 + catalog 重建用例 |
| 自动续跑与用户输入竞争 | 双 run 抢写 | 空闲门 + pending 队列 |
| 轮询风暴 | CPU 与事件堆积 | interval 下限 2s、并发上限、每分钟 1 次续跑 |
| Windows 文件时间精度 | 同毫秒内改动漏检 | `size + mtimeMs` 初筛 + 内容哈希兜底 |
| 重启后进程句柄失效 | 监视永久挂起 | 标记 `orphaned` 并显式投递 |
| 无限期监视 | 资源泄漏 | `deadlineAt` 必填 |

## 12. 开放问题

1. 自动续跑默认开启还是需要 `autoResume: true` 显式声明（建议默认开启，否则能力等同无用）。
2. 桌面端是否发系统级通知，还是只更新会话徽标。
3. v2 是否接入 CI/远端状态源，以及是否需要凭据隔离。
4. 监视是否允许绑定到父会话而非当前会话（跨会话唤醒），建议 v1 拒绝。
