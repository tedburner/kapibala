## 1. 什么是沙盒：一句定义

**沙盒 = 一个受控的执行环境，程序可以在里面自由运行，但它对真实世界的副作用被限制在预先声明的边界内。**

拆成三个关键词：

- **执行环境**：程序能跑、能算、能 IO——能力上尽量不打折扣（这是沙盒与"直接禁用"的区别）；
- **边界**：能访问哪些文件、能连哪些网络、能用多少资源，是**事先声明**的，不是运行时临时商量的；
- **副作用**：沙盒约束的不是程序"在想什么"，而是程序"对外部世界做了什么"。程序内部怎么折腾，出了边界就不算数。

一句话记忆：**沙盒 = 给不可信的代码一个"摔不坏的东西"的房间。**

<a id="2"></a>
## 2. 一个直观的类比

把孩子（不可信代码）放进：

- **游戏围栏（playpen）**＝沙盒：孩子可以自由活动，但出不了围栏；
- **全程抱在手里盯每个动作**＝逐条审批制：绝对安全但累死大人（性能/体验成本高）；
- **给孩子建一套小房子独立水电**＝虚拟机/容器：隔离最彻底，但建造成本高；
- **什么都不做**＝裸奔：相信孩子不会拆家——在生产环境这叫"祈祷驱动开发"。

工程实践永远是这几者之间的权衡：**隔离强度 ↔ 建造成本 ↔ 运行开销**。

<a id="3"></a>
## 3. 沙盒的技术演进谱系

沙盒不是新概念，它有一条清晰的演进主线：**每当"运行不可信代码"的需求扩大，沙盒就往下沉一层**（从应用层下沉到操作系统层，再到硬件层）。

| 年代 | 技术 | 隔离发生在哪 | 一句话评价 |
|---|---|---|---|
| 1979 | `chroot` | 文件系统根目录 | 沙盒鼻祖，但只管路径不管系统调用 |
| 2001 | FreeBSD Jail | 文件 + 网络 + 进程 | chroot 的认真补课版 |
| 1995 | Java Applet Sandbox | 语言运行时 | 字节码校验 + 无文件/网络访问，"跑不可信代码"的经典起步 |
| 2005+ | 浏览器沙盒 | 站点/渲染进程级 | 你每天都在用：恶意网页偷不了你别的标签页 |
| 2008 | Chrome 多进程沙盒 | OS + 进程模型 | 渲染进程被内核剥夺了几乎所有权限，漏洞利用的噩梦 |
| 2013 | Docker / 容器 | OS 级（namespace + cgroup） | 把隔离做到工程可用、人手一个 |
| 2015+ | gVisor / Firecracker | 系统调用拦截 / 微虚拟机 | 云厂商跑不可信负载的标配 |
| 2020+ | WebAssembly 沙盒 | 指令级（能力模型） | 代码只能访问"被显式传入的内存和导入函数" |
| 2024+ | **Agent 沙盒** | 工具调用/进程级 | 不可信的不是代码，而是模型的"下一步动作" |

观察这条时间线可以发现规律：**隔离的粒度越来越细，声明的成本越来越低。** chroot 时代你要自己写 root 目录，WASM 时代"没传给你的能力就不存在"。

<a id="4"></a>
## 4. 核心原理：三个支点

无论哪种沙盒，能立起来都靠三个支点。理解了它们，看任何沙盒技术都能迅速定位其强弱点。

### 4.1 最小权限原则（Principle of Least Privilege）

程序只应拥有完成任务所需的最小权限集合。这是沙盒的**目标函数**——所有沙盒设计都在回答同一个问题："这个程序真正需要什么，剩下的怎么收走？"

Chrome 的例子最极端：渲染进程理论上需要解析网页，但被内核剥夺了读文件、装驱动、改注册表的全部能力——**权限不是"没给"，是"物理上不存在"**。

### 4.2 边界的强制点（Enforcement Point）

边界由谁强制执行，直接决定沙盒的强度：

```
强制点层级（上弱下强）：

  应用层自检   ← 程序自己检查参数……它自己可以被攻破
  ─────────────────────────────
  语言运行时   ← JVM / WASM 虚拟机拦截危险操作
  ─────────────────────────────
  操作系统内核 ← 进程权限、namespace、ACL（主流沙盒所在层）
  ─────────────────────────────
  硬件虚拟化   ← CPU/内存管理单元级别的隔离（最强）
```

规律：**强制点离被约束的代码越远，越难被绕过。** 应用层检查（比如"路径前缀判断"）是强度最低的沙盒，因为攻破程序本身就等于攻破检查。

### 4.3 默认拒绝 + 显式授权（Deny by Default）

成熟沙盒的默认姿态是"什么都不允许"，能力靠显式声明获得：

- Android 的权限模型：app 不声明 CAMERA 就用不了摄像头；
- WebAssembly：没被导入（import）的函数，代码里根本调不到；
- 能力模型（capability-based）：持有"能力引用"才能操作，而不是持有"全系统可见的名字"。

与它相反的"默认允许 + 黑名单拦截"模式，历史上反复被证明会漏——黑名单永远列不全。

<a id="5"></a>
## 5. 沙盒的分类：按隔离发生在哪一层

### 5.1 语言级沙盒

- **代表**：Java Sandbox、JavaScript 虚拟机、WebAssembly；
- **机制**：不信任字节码/脚本，在解释执行时拦截危险操作；WASM 更进一步——线性内存 + 显式导入，从指令集层面就没有"系统调用"这个概念；
- **强弱**：实现干净则很强（WASM），但也曾反复被打穿（Java Applet 时代史就是逃逸史）。

### 5.2 操作系统级沙盒

- **代表**：macOS **Seatbelt**（`sandbox-exec`，profile 语言声明文件/网络权限）、Linux **Landlock**（进程"自缚"式访问控制）+ **seccomp**（系统调用过滤）+ **namespaces**、Windows 的 Restricted Token / AppContainer；
- **机制**：由内核强制。进程（或其子进程）被剥夺了声明边界之外的能力，程序自己想越界也做不到；
- **强弱**：主流生产级沙盒都活在这一层。难点在**跨平台**——三大平台原语完全不同，没有一个能通吃的 API。

### 5.3 硬件级沙盒

- **代表**：虚拟机（VMware/KVM）、微虚拟机（Firecracker，AWS Lambda 底层）；
- **机制**：CPU 虚拟化指令（Intel VT-x 等）+ 独立内核，逃逸需要打穿 hypervisor；
- **强弱**：最强，代价是资源开销与启动延迟。云厂商"每会话一个微 VM"跑用户上传的代码，就是这一层的典型应用。

### 5.4 容器：介于 OS 与"伪硬件"之间

容器（Docker 等）本质是 **OS 级沙盒的工程化封装**——namespaces 做视图隔离、cgroup 做资源隔离、联合文件系统做镜像分发。它比"手写 seccomp"易用一百倍，但隔离强度弱于 VM（共享宿主内核，历史上内核漏洞多次导致容器逃逸）。这解释了业界共识：**跑真正恶意的代码用微 VM，跑"不可靠但非恶意"的代码用容器。**

<a id="6"></a>
## 6. 沙盒 vs 虚拟机 vs 容器：别再混淆

三者经常被混用，但定位不同：

| 维度 | 沙盒（OS 级） | 容器 | 虚拟机 |
|---|---|---|---|
| 隔离对象 | **单个进程/操作** | 整个用户态环境 | 整台机器 |
| 共享内核 | ✅ 是 | ✅ 是 | ❌ 否（独立内核） |
| 启动开销 | 毫秒级 | 秒级 | 十秒级 |
| 隔离强度 | 中（依赖内核实现质量） | 中（内核漏洞可逃逸） | 强（要打穿 hypervisor） |
| 典型用途 | 限制某个程序的行为 | 部署/交付一致的环境 | 完全独立的机器 |

一个有用的记忆框架：

- **虚拟机回答"我在哪台机器上"**；
- **容器回答"我的环境长什么样"**；
- **沙盒回答"这个动作被允许做到什么程度"**。

它们不互斥——常见组合是"容器里跑沙盒化的进程"、"微 VM 里跑一次性容器"。

<a id="7"></a>
## 7. 深入：逃逸——沙盒安全的永恒主题

沙盒领域的核心攻防只有一个词：**逃逸（escape）**——被约束的代码获得了边界之外的能力。理解经典逃逸手法，比记住任何产品功能都更有价值。

### 7.1 逃逸的本质：找到一个"边界外的执行通道"

沙盒 = 边界 + 强制点。逃逸 = 让副作用绕过强制点。所有逃逸手法都是这个公式的变体：

**手法一：攻击强制点本身。**
内核是 OS 级沙盒的强制点，所以内核漏洞 = 沙盒漏洞。历史上 Chrome 沙盒的逃逸链几乎都是"渲染进程 RCE → 内核/IPC 漏洞 → 越权"两段式。这也是为什么隔离强度依赖"强制点离代码足够远"。

**手法二：欺骗检查逻辑。**
程序在"检查"与"执行"之间插入变化：

- **符号链接（symlink）攻击**：检查 `~/ws/data` 合法 → 打开前链接被换成 `/etc` → 打开穿墙；
- **TOCTOU（Time-of-check to time-of-use）**：检查与使用之间存在时间窗口，窗口内世界已变。通用解法是**把检查与使用合并成同一个原子操作**（如 Linux `openat2` 的 `RESOLVE_BENEATH`）。

**手法三：滥用被允许的能力。**
边界内的合法能力组合出边界外的效果：

- 允许写工作区 + 允许读任意文件 → 把机密文件内容写进工作区带走（内敛式外泄）；
- 允许网络白名单域名 → 通过 URL 路径参数编码外传数据（侧信道）；
- 允许创建进程 → 子进程继承权限，父进程的边界未必自动传递给孙子进程。

**手法四：攻击"配置边界的人"。**
沙盒边界是配置出来的，配置逻辑本身可被攻击——比如让程序以更高的权限重启、诱导用户在审批对话框里点"允许"。**最坚固的沙盒也防不住疲劳的人类。**

### 7.2 从攻防中学到的设计铁律

1. **默认拒绝**，黑名单永远列不全；
2. **检查与使用必须原子化**，不留 TOCTOU 窗口；
3. **能力要随进程树显式传递**，不能假设"我安全所以我的子进程也安全"；
4. **白名单域名/接口 = 合法化的外泄信道**，要么覆盖侧信道，要么承认这个缺口；
5. **永远假设强制点可能被打穿**，高危操作保留人工确认这道最后防线。

<a id="8"></a>
## 8. AI Agent 时代的沙盒：新问题在哪

传统沙盒的假设是："代码是坏的，但至少**每次执行的是同一段代码**——可以审计、可以签名。" Agent 打破了这个假设：**每一步要执行的"代码"（工具调用）都是模型即时生成的，事先不存在，无法审计。**

这带来三个本质变化：

### 8.1 不可信来源变了：从"陌生程序"到"不可预测的下一步"

```
传统：代码审计 → 签名 → 沙盒执行        （静态可信，动态受限）
Agent：模型生成动作 → 沙盒 + 审批执行    （动态不可信，实时受限）
```

传统流程里"审计"环节消失了，全部安全期望压到沙盒与审批上——所以 Agent 沙盒的强度要求实际上**高于**传统场景。

### 8.2 注入面变了：任何读进来的内容都是指令源

提示注入（prompt injection）是 Agent 特有的攻击入口：模型读取的**每一个文件、网页、工具返回值**都可能藏着恶意指令，诱导它执行"看起来完全合法"的操作。这决定了 Agent 沙盒的一条铁律：

> **网络边界比文件边界更关键。** 文件沙盒拦不住"读进恶意内容 → 在工作区里合法地写出去"，审批可能被疲劳攻击磨穿；只有**断网/严格白名单**能切断"外部注入 → 数据外泄"的完整链路。

### 8.3 防御体系变了：从"一道墙"到"多层分工"

Agent 场景收敛出的共识是**分层防御**，各层互为备份：

```
┌───────────────────────────────────────────────┐
│ 权限策略层：这个动作允许/询问/拒绝？（可被欺骗）  │
├───────────────────────────────────────────────┤
│ 沙盒强制层：即便放行，副作用也有硬边界（骗不过）  │
├───────────────────────────────────────────────┤
│ 人工审批层：高危动作最后由人确认（防疲劳设计）    │
└───────────────────────────────────────────────┘
```

两条经验法则：

- **策略层会被骗（模型被注入），强制层骗不过（内核不认识提示词）**——二者必须分开设计；
- **沙盒管"越界"，审批管"边界内的破坏"**——沙盒不会阻止程序删光它有权删的文件，这类风险只有审批能兜。

<a id="9"></a>
## 9. 小结

- 沙盒 = **预先声明边界的受控执行环境**，约束的是副作用而非能力；
- 演进主线：**"运行不可信代码"的需求每扩大一次，沙盒就下沉一层**——语言运行时 → OS 内核 → 硬件虚拟化；
- 三个支点：**最小权限、强制点离代码足够远、默认拒绝**；
- 逃逸的本质是**找到边界外的执行通道**：打强制点、骗检查逻辑、滥用合法能力、攻击配置者；
- Agent 时代的特殊性：**不可信对象从静态代码变成动态生成的每一步**，因此沙盒强度要求更高、网络边界更关键、必须多层防御。
