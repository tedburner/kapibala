## 问题详情与验收建议

### R01 · P0 · 非法帧直接终止连接，无法返回标准 JSON-RPC 错误

**定位：** `packages/cli/src/transport/jsonl.ts:39-41,47-51`；`packages/cli/src/transport/stdio.ts:72-89`；`packages/cli/src/transport/rpc.ts:137-152`。

**场景与影响：** 客户端发送合法 JSON 之外的帧（语法错误、缺字段、未知方法、参数类型不符）时，连接被直接关闭。所有在途请求以 `RPC closed` 结束，客户端收不到 `-32700` / `-32600` 或稳定 `data.code`，无法区分“请求写错”与“宿主崩溃”。

**原因与证据：** `JsonlDecoder.push()` 对 `parseWireMessage` 的失败直接 `throw`，并在 `catch` 中把 `ended = true`、清空缓冲；`createStdioTransport` 的 `onData` 捕获后调用 `finish(error)`，传输进入失败态；`RpcPeer.read()` 只能从已失败的 transport 读取，`dispatch()` 根本收不到该请求。`parseWireMessage` 本身已经能返回 `-32700`（JSON 解析失败）与 `-32602`（参数不匹配），但 decoder 只保留 message、丢弃了错误码。规格 `openspec/changes/v0-0-9-local-client-contract/specs/local-client-protocol/spec.md:12-15` 明确要求非法消息返回标准 JSON-RPC 错误。

**修复建议：** 区分“帧边界完整但内容非法”和“帧边界失步”：前者保持流可用，由 RPC 层返回 `-32700`（JSON 解析失败）或 `-32600`（schema 不匹配），并带稳定 `data.code`；后者（超帧预算、EOF 半帧、UTF-8 无法解码）才终止连接。`JsonlDecoder` 不应在单帧内容错误时自毁。

**验收：** 在真实 stdio/socket 连接上依次发送：非法 JSON、缺 `jsonrpc`、未知方法、非法参数、超帧预算、半帧 EOF。前四类必须收到标准错误且连接仍可用于后续 `ping`；后两类必须明确关闭并清理在途请求。

### R02 · P0 · 业务错误码白名单不完整，`SESSION_BUSY` 等契约错误退化为 `INTERNAL_ERROR`

**定位：** `packages/cli/src/protocol/errors.ts:2-19`；`packages/cli/src/transport/rpc.ts:145-146`；`packages/core/src/context/session-lock.ts:36,77`；`packages/cli/src/local-host/registry.ts:61,243`。

**场景与影响：** 直接 CLI 已持有目标 conversation 的存储锁时，`session/open` 返回 `INTERNAL_ERROR`，而不是规格要求的 `SESSION_BUSY`。SDK 无法据此提示“关闭另一个进程后重试”，只能报未知错误。相对路径、清理失败等参数/状态错误同样被折叠为内部错误，排障信息丢失。

**原因与证据：** `SessionManager.open` 在锁冲突时抛出的人类可读消息 `Session locked by a live or unknown owner...` 不在 `WIRE_ERROR_CODES` 中；`RpcPeer.dispatch()` 只做 `publicCodes.has(error.message)` 判断，未命中即 `INTERNAL_ERROR`。`WORKSPACE_ROOT_REQUIRED`（`registry.ts:61`）与 `SESSION_CLEANUP_FAILED`（`registry.ts:243`）也不在白名单。规格 `openspec/changes/v0-0-9-local-client-contract/specs/local-host-lifecycle/spec.md:7-10` 明确要求“直接 CLI 已持有目标 conversation 锁 → 返回 SESSION_BUSY，不偷锁”。

**修复建议：** 在资源创建边界把 Core 的锁错误规范化为 `SESSION_BUSY`（不要靠 RPC 层字符串匹配）；白名单补充 `WORKSPACE_ROOT_REQUIRED`、`SESSION_CLEANUP_FAILED` 及通用 `INVALID_PARAMS`；收敛为单一 `toWireError(error)` 映射函数，所有 handler 共用。

**验收：** 用真实 `AgentSession`/`SessionManager` 持有 conversation 锁，再从 local host 执行 `session/open`，断言 `data.code === 'SESSION_BUSY'` 且未发生偷锁；相对路径、非法参数、清理失败分别断言稳定错误码。

### R03 · P0 · `host/shutdown` 失败后进入不可恢复状态，listener 与锁残留

**定位：** `packages/cli/src/local-host/server.ts:124,217-221,229-231`；`packages/cli/src/local-host/daemon.ts:206-214,240-251`。

**场景与影响：** 任一 session 清理失败使 `registry.shutdown()` 抛错后，`stopping` 已经为 `true`：后续除 `ping` 外全部返回 `SHUTTING_DOWN`，包括再次 `host/shutdown`；`onShutdown` 不会触发；`runDaemon` 跳过 `listener.close()`，`daemon.json` / `daemon.lock` 也不会删除。daemon 进入“拒绝服务但不退出”的状态，用户只能按 PID 杀进程。

**原因与证据：** `server.ts:218` 在 `await this.registry.shutdown()` 之前设置 `stopping = true`；`server.ts:124` 的守卫不区分“正在关闭”与“关闭失败可重试”；`server.ts:230` 只在 `responded`（成功响应）后调用 `onShutdown`。`daemon.ts:242` 的 `await host.shutdown()` 抛错后，`listener.close()` 与元数据清理均不执行。

**修复建议：** `stopping` 在清理成功后再置位，或允许 `host/shutdown` 在 `stopping` 状态下重试；`runDaemon` 用 `try/finally` 保证 `listener.close()` 执行；清理失败时保留可诊断元数据但释放监听端点；`stopDaemon` 等到 `daemon.json` 消失或健康检查失败（带超时）。

**验收：** 注入 `resources.dispose()` 失败，执行 `host/shutdown` → 收到错误；再次执行 `host/shutdown` → 仍可重试并最终成功；断言 listener 已关闭、端点可重新绑定、元数据被清理或保留为可诊断状态。

### R04 · P1 · 一次性 `connect -p` 每次新建并泄漏 idle 会话，8 次后 `RESOURCE_LIMIT`

**定位：** `packages/cli/src/local-host/connect.ts:74-82,166-172`；`packages/cli/src/local-host/registry.ts:68-77`；`packages/cli/src/protocol/version.ts:12`；`docs/local-host.md:20`。

**场景与影响：** 每次无 `--resume` 的 `kpbl connect -p "..."` 都调用 `session/create`，退出时明确不 `session/close`。由于 `session/create` 的 `conversationId` 为 `undefined`，而 registry 中已有 entry 的 `conversationId` 是真实 ID，existing 查找永远匹配不到，每次都新建。累计 8 个 idle 会话后，后续连接直接收到 `RESOURCE_LIMIT`。CLI 没有 `/close`，用户不知道需要 `daemon stop`。

**原因与证据：** `connect.ts:77` 选择 `session/create`；`connect.ts:170-171` 注释“保留 idle 会话供重连，不自动 session/close”；`registry.ts:68-76` 按 `entry.resources.conversationId === conversationId` 比较；`maxOpenSessions = 8`（`version.ts:12`）。`docs/local-host.md:20` 仅说明 SDK 可用 `session/close` 显式回收，未提供 CLI 路径。

**修复建议：** 非交互一次性运行结束后自动 `session/close`；或为同一 workspace 复用固定的 ephemeral 会话；交互模式增加 `/close`，并在 `/status` 展示打开会话数与配额；若坚持保留，应在接近配额时主动提示。

**验收：** 连续执行 9 次 `connect -p`，前 8 次成功且第 9 次仍成功（自动回收或复用）；`/status` 显示当前打开会话数；`/close` 后配额立即释放。

### R05 · P1 · 子代理与 MCP 工具缺少审批描述，能力装配与默认拒绝策略冲突

**定位：** `packages/cli/src/local-host/server.ts:46-67`；`packages/cli/src/local-host/approval.ts:42`；`packages/cli/src/local-host/resources.ts:83-95,124-155`；`docs/local-host.md:26`。

**场景与影响：** `describe` 只处理 `write_file`、`edit_file`、`run_command`、`mcp_start`，其余工具返回 `undefined`，审批通道随即 `resolve('cancel')`。但 local host 同时装配了 `AgentRuntime` 与 `createCliSubagentRunner`，`spawn_agent` / `wait_agent` / `cancel_agent` 已注册；MCP 工具适配器声明 `external:call` 且默认 `dangerous: true`，调用也会进入审批。结果是“工具存在但必然被拒”，用户会误以为是模型或服务故障。

**原因与证据：** `server.ts:67` 的兜底 `return undefined`；`approval.ts:42` 的 `if (!target || !identity) return Promise.resolve('cancel')`；`resources.ts:83-95` 装配 runtime；`packages/mcp/src/tools/adapter.ts:61` 声明 `external:call`；`docs/local-host.md:26` 又称“无法安全说明的未知工具会拒绝”，与“装配子代理/MCP 能力”在语义上冲突。

**修复建议：** 二选一并写入文档：① 为四个 agent 工具与 MCP 工具提供脱敏后的通用描述（工具名、目标、关键参数摘要），继续拒绝含敏感信息的输入；② local host 不注册不可审批的子代理 runtime / MCP 工具，明确声明连接模式不支持。禁止“注册了但审批必败”的中间态。

**验收：** 在 Approval 模式下分别调用 `spawn_agent`、`wait_agent`、`cancel_agent` 和至少一个 MCP 工具：要么弹出可读审批并可批准执行，要么工具根本不可见且在文档中明确不支持；不得出现“可见、可调用、必失败”。

### R06 · P1 · 运行清理失败后 `active` 永不清除，close/disconnect/shutdown 全部被阻断

**定位：** `packages/cli/src/local-host/registry.ts:242-249,261-303`；`packages/cli/tests/local-host-session.test.ts:56-70`。

**场景与影响：** `resources.run()` 迭代结束但 `isBusy()` 仍为 true 时，`start()` 在 `entry.active = undefined` 之前抛 `SESSION_CLEANUP_FAILED`，`active.done` 以 rejected 结束。此后 `close()` 看到 `active` 仍存在抛 `SESSION_BUSY`；`disconnect()` 与 `shutdown()` `await active.done` 直接收到 rejection，控制者无法撤销、daemon 无法干净停止。与 R03 组合即“daemon 停不下来”的完整路径。

**原因与证据：** `registry.ts:243-244` 抛错发生在清空 `active` 之前；`registry.ts:247` 的 `finally(remember)` 不会吞掉 rejection；`registry.ts:282` 的 `if (entry.active) throw SESSION_BUSY`；`registry.ts:271-274,297-302` 直接 `await` rejected Promise。现有测试 `local-host-session.test.ts:56-70` 只断言“保留围栏、后续 start 报 SESSION_BUSY”，没有覆盖 close/disconnect/shutdown 的恢复路径，等于把不可恢复状态固化为期望。

**修复建议：** 无论清理是否成功，都清空 `entry.active` 并发布 `run_settled` / `diagnostic`；把“Core 仍 busy”作为终态错误信息，而不是让 `done` 永久 rejected。若必须保留围栏，提供显式 `force close`/重试路径，且 `shutdown` 用 `allSettled` 继续处理其他会话后统一上报。

**验收：** 注入 `isBusy() === true`，分别执行 `session/close`、控制连接断开、`host/shutdown`：三者都应完成资源释放或给出可重试错误，不能永久 `SESSION_BUSY`；恢复后再次打开同一 conversation 不应命中残留锁。

### R07 · P1 · 资源释放未用嵌套 `finally`，destroy/close 失败会跳过 release

**定位：** `packages/cli/src/subagent-runner.ts:159-162`；`packages/cli/src/local-host/resources.ts:204-217`。

**场景与影响：** 子代理 runner 的 `finally` 先 `await subSession?.destroy()`，再 `await handle.release()`；destroy 抛错则 release 跳过。`resources.dispose()` 先 `runtime.close()`，再 `session.destroy()`，最后 `handle.release()`；任一步失败后续全部跳过，且 `disposed` 仍为 `false`。结果是存储锁/写租约泄漏，下一次打开同一 conversation 可能被判定为仍被占用。

**原因与证据：** `subagent-runner.ts:160-161` 顺序 await；`resources.ts:206-209` 顺序 await；创建失败路径 `resources.ts:213-215` 同样顺序 await，前一步失败会掩盖后一步。

**修复建议：** 每个资源都用独立 `try/catch` 或 `Promise.allSettled` 尝试释放，聚合首个错误后继续；`disposed` 在进入 dispose 时置位或使用共享 Promise，避免重复进入；release 必须在 destroy 失败时仍执行。

**验收：** 分别注入 `runtime.close()`、`session.destroy()`、`handle.release()` 失败：其余资源仍被调用释放；锁/租约可被下一次打开获取；错误以诊断形式上报而非静默吞掉。

### R08 · P1 · 快照契约与设计不一致：pending approval 缺失、`historyPageSize` 空转、`limit` 被忽略

**定位：** `docs/design/002-v0.0.9-local-client-contract.md:68,94`；`packages/cli/src/local-host/registry.ts:31-37,141`；`packages/cli/src/local-host/server.ts:132-145,172-188`。

**场景与影响：** 设计称 `session/snapshot` 返回“运行状态、待审批与高水位”，`SessionSnapshot` 没有 pending approval 字段；设计称“历史默认每页 50 条”，`registry.snapshot()` 确实取了最后 50 条，但 `server.ts:176,188` 又把 `history` 覆盖为 `[]`，改由 `SnapshotPager` 把完整历史编码后按 64Ki 分块，`historyPageSize` 在 wire 上没有实际作用；`session/list` 的 `limit` 在 schema 中允许（1–50），handler 完全忽略。SDK 按文档实现会拿不到待审批状态，按 50 条/页实现分页会与宿主行为不符。

**原因与证据：** `registry.ts:141` 的 50 条预览被 `server.ts:176` 的 `history: []` 丢弃；`server.ts:172-175` 将 `entry.resources.history()` 全量交给 pager；`server.ts:137-145` 只使用 `cursor`，未读取 `limit`；`protocol/schema.ts:44-46` 允许 `limit`。

**修复建议：** 统一“逻辑快照”的唯一语义：要么“最近 50 条 + live 尾部”，要么“完整历史按 64Ki 分块”；删除另一套死代码。若设计上审批随控制连接销毁，则删除 pending approval 承诺并在文档说明“新 attach 不会有 pending approval”；`session/list` 要么实现 `limit`，要么从 schema 删除。

**验收：** 构造超过 50 条历史的会话，断言 attach/snapshot 返回的条数、游标分页与文档一致；构造 pending approval，断言快照包含该字段（或文档明确不包含）；`session/list` 传 `limit=1` 时只返回 1 条，传非法 `limit` 时返回参数错误。

### R09 · P2 · `close` 与 `shutdown` 可并发 dispose 同一会话

**定位：** `packages/cli/src/local-host/registry.ts:279-303`；`packages/cli/src/local-host/resources.ts:204-210`。

**场景与影响：** `session/close` 正在 `await resources.dispose()` 时，daemon 收到 `host/shutdown`，`shutdown()` 会再次遍历仍留在 `sessions` 中的同一 entry 并调用 `dispose()`。`disposed` 只在最后置位，两个调用都能通过检查，可能双重 `runtime.close()` / `session.destroy()` / `handle.release()`，引发重复释放或未定义行为。

**原因与证据：** `close()` 在 dispose 成功后才 `sessions.delete()`；`shutdown()` 不排除正在 close 的 entry；`resources.dispose()` 的 `if (disposed) return` 无法阻止并发进入。

**修复建议：** 为每个 session 持有共享 dispose Promise（首次创建，后续复用），或引入 `closing` 状态让 shutdown 等待/跳过；`disposed` 在进入时置位并保存 Promise。

**验收：** 并发触发 `session/close` 与 `host/shutdown`，断言每个资源的 close/destroy/release 只被调用一次，且两端都得到一致结果。

### R10 · P2 · `open` 可能返回正在 `closing` 的会话

**定位：** `packages/cli/src/local-host/registry.ts:68-76`。

**场景与影响：** `session/close` 将 `entry.closing = true` 后进入异步 dispose；此时并发的 `session/create` / `session/open` 仍可能在 existing 查找中命中该 entry，返回一个即将销毁的 sessionId，随后 `attach` 才因 `closing` 抛 `SHUTTING_DOWN`。客户端会经历“打开成功 → 立即失败”的竞态。

**原因与证据：** existing 查找只比较 workspaceRoot 与 conversationId，未排除 `entry.closing`；`open` 的串行队列只串行 open，不与 close 互斥。

**修复建议：** existing 查找过滤 `!entry.closing && !this.shuttingDown`；或让 close 先从 map 移除/标记不可见，再异步释放。

**验收：** 在 close 的 dispose 延迟期间并发 open 同一 conversation，断言不会返回 closing 的 sessionId；要么等待后新建，要么返回 `SESSION_BUSY`。

### R11 · P2 · 缺少 `run_finish` 时默认发布 `completed`

**定位：** `packages/cli/src/local-host/registry.ts:202,233-241`。

**场景与影响：** `outcome` 初始为 `'completed'`，只有 `run_finish` 才会改成 metrics 状态。若 `resources.run()` 提前正常结束但没有终态事件（Provider 提前 EOF、适配器 bug、未来新增执行器漏发），宿主会向客户端发布“成功”，而实际任务可能未完成。

**原因与证据：** `registry.ts:202` 默认值；`registry.ts:233-236` 仅在收到 `run_finish` 时设置 `terminal`；循环结束后没有 `if (!terminal) outcome = 'failed'`。

**修复建议：** 默认 `failed`，或要求终止事件；缺失 `run_finish` 时发布 `failed` 并附 `diagnostic`，不要静默成功。

**验收：** 构造 `run()` 只产出 `text_delta` 就返回的 fake 资源，断言 `run_settled.outcome === 'failed'`；正常路径仍为 `completed`。

### R12 · P2 · 工具事件投影丢失真实目标、结果与诊断

**定位：** `packages/cli/src/local-host/registry.ts:215-231`。

**场景与影响：** `tool_start.payload.target` 填的是 `event.name`（工具名），不是文件路径/命令；`tool_finish.payload.result` 永远是固定文案，`truncated` 永远为 `true`，与是否截断无关；`tool_progress`、`error`、`diagnostic` 未投影，模型失败时客户端只看到 `run_settled failed`，缺少可操作的诊断信息。

**原因与证据：** `registry.ts:219` `target: event.name`；`registry.ts:227-229` 固定 `result` 与 `truncated: true`；分支只处理 `text_delta`、`thinking_delta`、`tool_start`、`tool_finish`、`error`、`run_finish`。

**修复建议：** 从工具事件中提取可公开的目标摘要与结果摘要（脱敏、限长），按实际截断状态设置 `truncated`；至少把 `error`/`diagnostic` 投影为事件，避免只剩终态。

**验收：** 执行一次写文件、一次失败命令：`tool_start.target` 应包含路径/命令摘要；`tool_finish.truncated` 与实际截断一致；失败时客户端能收到诊断文本。

### R13 · P2 · 连接展示忽略工具事件，attach 期间缓冲事件被丢弃

**定位：** `packages/cli/src/local-host/presentation.ts:45-79`；`packages/cli/src/local-host/connect.ts:65-100`；`packages/cli/src/client/local-client.ts:199-203`。

**场景与影响：** `ConnectedPresentation.consume()` 只处理 `run_started`、文本/思考增量、`run_settled`、`diagnostic`，`tool_start` / `tool_finish` 不进入展示状态，连接模式看不到工具调用。`connect.ts` 在 `presentation` 赋值前就订阅；`LocalClient` 在 attach 响应返回前同步重放缓冲事件，此时 `presentation?.consume` 为 `undefined`，这些事件被丢弃（`text_delta` 仍直接打印，造成文本先于历史恢复出现）。

**修复建议：** 补齐工具事件归约；先创建 presentation 再订阅，或在 `presentation` 就绪后补放 attach 期间缓存的事件；文本输出也应经过展示状态，避免顺序错乱。

**验收：** attach 期间产生 `tool_start`/`tool_finish`，断言展示状态包含工具条目且顺序正确；历史恢复前不应先打印增量正文。

### R14 · P2 · `stop` 在完整清理前返回，立即重启可能撞残留锁

**定位：** `packages/cli/src/local-host/daemon.ts:206-214,240-251`。

**场景与影响：** `stopDaemon()` 在收到 `host/shutdown` 响应后立即返回，但 `runDaemon()` 还要执行 `listener.close()`、删除 `daemon.json`、`rmdir daemon.lock`。用户紧接着执行 `daemon start`，可能因锁目录仍存在而失败，或读到即将删除的元数据。

**原因与证据：** `stopDaemon` 的 `finally` 只关闭客户端；`runDaemon` 的清理在响应之后；`startDaemon` 使用 `mkdir` 锁并 `wx` 写元数据。

**修复建议：** `stopDaemon` 等待 `daemon.json` 消失或健康检查连续失败，设置超时；daemon 在响应前完成关键清理，或提供 `stopping` 状态供 start 识别并等待。

**验收：** `stop` 返回后立即 `start`，连续 20 次不得因残留锁失败；`stop` 超时时应报告残留路径。

### R15 · P2 · daemon 启动诊断不可观测

**定位：** `packages/cli/src/local-host/daemon.ts:175-204`。

**场景与影响：** 子进程 `stdio: 'ignore'`，启动失败只报 `Daemon failed to become healthy; runtime metadata retained for diagnosis`，没有 stderr/日志。陈旧锁或损坏元数据时，`status` 仍只报 `{running:false}`，用户无法判断是残留、配置错误还是子进程崩溃。

**原因与证据：** `daemon.ts:180` `stdio: 'ignore'`；健康循环只轮询 `getDaemonStatus().running`；失败分支不读取子进程退出码/信号。

**修复建议：** 将子进程 stderr 落到私有日志文件（0600），错误信息附日志路径；`status` 区分“无实例 / 锁残留 / 元数据损坏 / 子进程已退出”；启动失败时报告退出码/信号。

**验收：** 模拟子进程立即退出、锁目录残留、元数据损坏三种情况，`daemon start/status` 输出可区分的原因与可操作路径。

### R16 · P2 · 能力协商未生效，客户端也不校验 capabilities/limits

**定位：** `packages/cli/src/protocol/version.ts:24-42`；`packages/cli/src/local-host/server.ts:111-121`；`packages/cli/src/client/local-client.ts:100-111`。

**场景与影响：** `negotiateProtocol()` 忽略 `offer.capabilities`，固定返回 `capabilities: []`；server 又硬编码覆盖为 `['sessions','approval','cancel','replay']`；客户端只检查 major/minor，不校验 capabilities 或 limits。设计称“能力不支持明确失败”，实际没有任何能力失败路径。未来新增能力时，旧客户端会误以为自己可用，或新客户端无法判断服务端是否支持。

**原因与证据：** `version.ts:41` `capabilities: []`；`server.ts:119` 硬编码数组；`local-client.ts:102-110` 只比较 `major/minor` 与 `serverInstanceId`。

**修复建议：** 要么实现交集与失败路径（客户端声明所需能力，服务端返回交集，缺失即 `PROTOCOL_MISMATCH`），要么删除能力字段并明确“v1 能力固定”，避免假协商；limits 至少校验关键上下界。

**验收：** 客户端声明一个服务端不支持的能力，断言初始化明确失败；服务端返回的 limits 与 `DEFAULT_LIMITS` 一致；旧/新 minor 组合按文档行为工作。

### R17 · P2 · `session/list` 游标未校验，非法值退化为 `INTERNAL_ERROR`

**定位：** `packages/cli/src/local-host/server.ts:132-145`；`packages/core/src/context/session-manager.ts:212`。

**场景与影响：** `cursor` 直接 `Number(request.params.cursor)`；`Number('abc') === NaN`，传入 `SessionManager.list(NaN)` 后抛 `History page must be a positive integer`，最终映射为 `INTERNAL_ERROR`。客户端无法区分“游标过期/非法”和“宿主内部错误”。

**修复建议：** 显式校验游标为正整数，非法时返回 `INVALID_PARAMS`（或 `RESYNC_REQUIRED`）；`limit` 同样校验范围；避免把用户输入错误送进 Core 再折叠成内部错误。

### R18 · P2 · `attach` 失败不回滚控制权

**定位：** `packages/cli/src/local-host/server.ts:147-177`。

**场景与影响：** `registry.attach()` 先授予 controller（`registry.ts:118`），随后 `pager.capture()` 可能因超过 8MiB 预算抛 `RESOURCE_LIMIT`。此时 controller 已绑定到 clientId，但订阅尚未建立、快照未返回；同一会话的其他控制者会被 `SESSION_BUSY` 拒绝，直到该连接断开。

**原因与证据：** `server.ts:160-164` 先 attach；`server.ts:172-175` 才 capture；失败路径没有撤销 controller 或 subscriptions。

**修复建议：** 捕获 attach 后续失败并回滚本次授予的 controller（仅当仍是本次 clientId/epoch）、取消已建立的订阅、释放 pager 缓存；或先完成快照捕获再授予控制权（需保证原子性）。

**验收：** 构造超预算快照使 `pager.capture` 失败，断言 controller 未被占用，另一个客户端可立即 attach 成功。

### R19 · P2 · 脱敏边界仅覆盖模型密钥

### R20 · P2 · `attach` 同时返回 replay 与完整快照，客户端不消费 replay

**定位：** `packages/cli/src/local-host/server.ts:147-176`；`packages/cli/src/client/local-client.ts:139-203`。

**场景与影响：** `session/attach` 在客户端传 `afterSeq` 时计算 `replay`，同时又返回包含完整历史与 live 尾部的快照分页。`LocalClient` 完全不消费 `replay`，只按快照 `seq` 设置游标，`replay` 成为死负载并计入帧预算；外部客户端若先应用 replay 再应用快照，可能重复正文。设计注释称“客户端以水位重建而非再追加重复正文”，但未规定 replay 与快照的优先级。

**原因与证据：** `server.ts:149-152` 计算 replay；`server.ts:176` 同时返回 `replay` 与 `page`；`local-client.ts:193-197` 只设置快照游标；`local-client.ts:139-178` 只处理 `chunk`，未读取 `replay`。

**修复建议：** 明确二选一：要么 attach 只返回快照，replay 仅用于纯事件流客户端；要么规定“先应用 replay，再以快照覆盖/去重”，并在协议文档与测试中固定。若当前客户端不需要 replay，删除该字段以减小帧预算。

**验收：** 带 `afterSeq` attach 时，客户端状态与不带 `afterSeq` 的结果一致且无重复正文；若保留 replay，第三方客户端按文档应用两次不得产生重复消息。

## 测试覆盖缺口

现有新增测试（14 个文件）覆盖了协议校验、JSONL 分帧、RPC 双向调用、审批五选一、快照分块、事件重放、daemon 生命周期、presentation、redaction 等，单元/集成层质量较好，但以下场景缺失，恰好对应本轮 P0/P1：

1. 真实 `AgentSession` 持有 conversation 锁时，local host 返回 `SESSION_BUSY`（R02）。
2. `host/shutdown` 首次失败后可重试，且 listener/元数据最终清理（R03）。
3. 连续 8 次以上 `connect -p` 的配额与回收行为（R04）。
4. `spawn_agent` / `wait_agent` / `cancel_agent` 与 MCP 工具的审批路径（R05）。
5. `isBusy() === true` 后 `session/close`、断线、shutdown 的恢复路径（R06）。
6. 非法 JSON 帧返回标准错误并保持连接可用（R01）。
7. pending approval 快照、50 条分页、`limit` 生效（R08）。
8. Node 20、Linux、真实 Windows named pipe/ACL、真实 TTY 审批、MCP 完整生命周期（平台门禁）。

## 修复与复审顺序建议

1. **先收错误契约（R01、R02、R17）**：统一 `toWireError`，区分可恢复/不可恢复帧错误；这是后续所有客户端行为的基础。
2. **再收控制面生命周期（R03、R06、R07、R09、R10、R14）**：shutdown 可重试、清理失败不砖化、释放用 `finally`、并发 dispose 串行化、open 排除 closing、stop 等清理。建议先用故障注入测试锁住这些路径，再改实现。
3. **修资源回收（R04、R18）**：一次性连接自动 close 或复用；attach 失败回滚控制权。
4. **明确审批能力边界（R05、R16）**：要么补齐描述器并实现能力协商，要么删除不可用能力并降级文档；不要保留“可见但必败”。
5. **统一快照/replay 语义（R08、R20）**：删除死代码，固定客户端应用顺序。
6. **补可观测性与投影（R12、R13、R15、R19）**：工具目标/结果/诊断、attach 缓冲、daemon 日志、脱敏边界。
7. **校准验收记录（R21）**，并完成 Linux/Windows/Node 20/真实 TTY/MCP/压测门禁后再判断发布。

维护建议：本轮问题集中在“接口存在但语义不闭合”和“失败路径未设计”两类。修复时优先收敛到共享契约（单一错误映射、单一 dispose 所有权、单一快照语义、单一审批描述入口），避免在 server/registry/resources 各写一套补丁。
