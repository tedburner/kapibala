## 2. 逐项对照

### 3.1 watch / 补投：用「看到哪了」而不是「通知过没有」

初版建议给通知加 `watchId` 幂等键。jcode 的做法更好，也更简单：**记水位**。

`crates/jcode-app-core/src/catchup.rs`：

```rust
const CATCHUP_STATE_FILE: &str = "catchup_seen.json";

pub fn needs_catchup(session_id: &str, updated_at: DateTime<Utc>, status: &SessionStatus) -> bool {
    if !is_attention_status(status) { return false; }
    let seen = load_seen_state().seen_at_ms_by_session.get(session_id).copied();
    needs_catchup_with_seen(updated_at.timestamp_millis(), seen, status)
}

pub(crate) fn needs_catchup_with_seen(updated_at_ms: i64, seen_at_ms: Option<i64>, status: &SessionStatus) -> bool {
    is_attention_status(status) && seen_at_ms.unwrap_or_default() < updated_at_ms
}
```

三件事值得照搬：

1. **判定是时间比较，不是布尔标记**。`seen_at < updated_at` 就欠一次投递。崩溃、断电、切宿主之后，只要没确认过就还会欠着；确认过就自然不欠。布尔标记表达不了「错过了两次更新」。
2. **状态文件独立于会话正文**（`catchup_seen.json`），且提供 `CatchupSeenSnapshot` 批量预读——列会话列表时不必每个 session 读一次盘。watch 面板正好是这个访问模式。
3. **补投给的是简报，不是重放**。`build_brief` 只抽：最后一条用户提示、最新 agent 回复、触碰过的文件、工具调用计数、验证备注、`needs_from_user`。这也是「watch 一个长会话」唯一合理的呈现方式——没人想看两百条历史。

Lody 提供另一半：ACP 通知通过 `appendAutonomousACPNotifications` 直接写进会话历史（`apps/cli/tests/e2e/claude-code-notifications.e2e.test.ts:28`），历史是 Loro CRDT 文档，多端合并靠 CRDT 而不是锁。

**落点（R1）**：

- `watch_state` 存 `{lastSeenAt, lastNotifiedAt}`，**不存 `delivered: boolean`**；
- 判定 `needsCatchup = lastSeenAt < session.updatedAt && status ∈ attention`；
- 补投写一条带 `watchId` 的 brief 消息进目标会话历史（既是通知、也是幂等锚点）；
- 全局上限与租约仍然要做（§5），水位机制不解决跨进程归属。

### 3.2 行差事实：从已持久化的 patch 数，而不是重算 diff

opencode 把 patch 当**数据**而不是渲染中间产物（`packages/core/src/vcs/patch.ts`）：

```ts
export const PATCH_CONTEXT_LINES = 2_147_483_647
export const MAX_PATCH_BYTES = 10_000_000
export const MAX_TOTAL_PATCH_BYTES = 10_000_000

/** Count changed lines in a unified diff, ignoring `+++`/`---` file headers. */
export const countPatch = (patch: string) => {
  let additions = 0, deletions = 0
  for (const line of patch.split("\n")) {
    if (line.startsWith("+") && !line.startsWith("+++")) additions++
    else if (line.startsWith("-") && !line.startsWith("---")) deletions++
  }
  return { additions, deletions }
}
```

要点：行数是**数**，不是**算**。patch 文本已经在手（工具执行时生成并落盘），统计是 O(行数) 的字符串扫描，没有 LCS、没有二次比较、没有「历史重放时再猜一遍」。两个字节上限 + `Patch.truncated` 处理超大文件。

初版说「不改 Core 协议就做不到 diff-first」，在 A 级证据下更确定是假矛盾：patch 属于 canonical 结果，wire 只需要一句话。kapibala 已有 `ToolResultBlock.execution`（`packages/core/src/types/index.ts:145-150`，注释明确「随 canonical 结果持久化；不直接上 Provider wire」），加同型的 `facts` 即可，不需要新机制。

**落点（R3/R4）**：

```ts
facts?: {
  version: 1;
  diff?: { additions: number; deletions: number; truncated?: boolean };
}
```

`write_file` 在写之前读旧内容生成 patch；`edit_file` 本来有 target/replacement，直接 `structuredPatch`。**单文件超上限就只记 truncated，不记数字**——比记一个错的好。

### 3.3 任务面板：从历史重算，但别指望它解决并发

opencode 的 todo 是**四态**（`packages/tui/src/util/todo.ts:8`）：`pending | in_progress | completed | cancelled`。比三态多一个 `cancelled`——被撤销的任务和「还没开始」是两件事，混在一起会让面板永远显示一堆「未完成」。

当前状态的来源（同文件 32-43 行）：

```ts
/** The current list is the input of the latest completed `todowrite` call before the revert boundary. */
export function sessionTodos(messages, boundary?) {
  const tool = messages
    .slice(0, boundaryIndex === -1 ? messages.length : boundaryIndex)
    .flatMap((message) => (message.type === "assistant" ? message.content : []))
    .findLast((item) => item.type === "tool" && item.name === "todowrite" && item.state.status === "completed")
  return parseTodos(tool?.state.input.todos)
}
```

三个设计含义：

1. **不落盘独立任务状态**，当前列表 = 历史里最后一次**成功**的 `todowrite` 输入。天然满足历史闭合，revert 到边界之前自动得到当时的状态，不需要 sidecar 重建。这比「每任务一个文件 + 锁 + ID 高水位」更契合 kapibala 的「历史是唯一事实源」。
2. **只认 `completed`**。失败或中断的 `todowrite` 不改变视图，否则一次失败写入会让面板闪成空。
3. ⚠️ **它没解决并发覆盖**。`input.todos` 仍是全量数组，两个并发写者依然后者覆盖前者。opencode 靠的是单写者会话模型；kapibala 有委派子代理，这个前提不成立。

**落点（R8）**：读取路径采用「从历史重算」，**写入必须加互斥**（会话内锁 + 读-改-写），否则重算只是让覆盖结果变得"看起来一致"。四态照搬，`cancelled` 单独建模。

初版建议的「拆成 add/update/list 三件套」在 A 级证据里没有对应物，撤回；保留单一 `todo_write` + 互斥更小。

### 3.4 技能 / 插件导入：隔离比字段白名单更根本

deepseek-harness 的插件抓取器开篇就把安全模型写清楚了（`apps/plugin-market-generator/src/fetchers.ts:1-8`）：

> Download package files **without running their code**. npm tarballs are streamed under a size limit, verified against the registry integrity, and unpacked in memory. Git objects are fetched into a private temporary **bare repository** with hooks, the file-system monitor, submodules, and all but the allowed transports disabled, and files are read as blobs: **no working tree is created**, so no checkout filter, LFS download, or symbolic link takes effect.

逐条对到 009 的风险面：

| 做法 | 挡住什么 |
|---|---|
| 下载但不执行 | npm `postinstall`、git hook、任意构建脚本 |
| bare repo 只读 blob，不 checkout | `.gitattributes` filter、LFS 指针、`core.symlinks` 造成的目录穿越 |
| 私有临时仓库 + 禁用 hooks/子模块/传输 | 克隆过程中被来源仓库反向影响本机配置 |
| 流式 + 字节上限 + registry integrity | 超大包、截断包、传输损坏 |
| 内存解包 / 临时目录 | 落地半成品被后续扫描器误认 |

这比 009 现在的「自定字段白名单」强一个量级：字段白名单管的是**装进来之后**的配置面，上面这些管的是**装进来的过程**。kapibala 的导入来自本地目录和压缩包，没有 npm/git 那么复杂，但三条可以直接用：**不执行**、**不建工作树（按条目读）**、**先落临时目录再原子改指针**。

配套仍是初版那两条：`sourceRef` / `installedDigest` 分离；备份移出技能根。后者在 A 级仓里没找到反例——活跃仓要么用版本化缓存目录，要么根本不把运行态写进被扫描的树。

### 3.5 协议升级：整数版本 + capability 集合，比 minor 同版配对更耐演进

初版把「wire 1.1 同版配对」列为「抄不到、只能自己定」。这轮找到了更好的范式，建议改设计。

**opencode**（`packages/process-daemon/src/protocol.rs:12-19`）：

```rust
pub const PROTOCOL_VERSION: u32 = 9;
/// Additive capabilities of this daemon. Breaking changes bump
/// `PROTOCOL_VERSION`; everything in protocol 9 needs no feature.
pub const FEATURES: &[&str] = &[];
```

客户端做**严格相等**校验（`client.rs:134-136`：`registration.protocol != PROTOCOL_VERSION` 直接报 mismatch 并带上双方版本号）。规则是：**破坏性变更才动大版本号，新增能力走 feature 字符串**，所以多数新功能不需要客户端升级。

**CodeWhale**（`crates/app-server-protocol/src/lifecycle.rs:8-36`）是同一思路的另一种编码：`InitializeParams { clientInfo{name,version}, capabilities{...bool}, extensions? }`——版本给日志和诊断，能力位决定行为分支，`extensions` 留给未定型的实验面。

对 `014` 的具体建议：

- 把 `major.minor` 的「minor 必须同版」降级为：**整数 `protocolVersion` + `capabilities: string[]`**；
- 客户端上报自己支持的能力，宿主只启用交集；缺失的能力走显式降级或拒绝，而不是版本号一刀切；
- 破坏性变更才 +1，并保留「旧客户端握手失败」的行为（这条初版判断仍成立）。

理由很实际：v0.1.4 一次要落 6 个主题，看板、预览、任务面板都会加新事件/新字段。如果每次靠 minor 同版配对，用户升级桌面端就得同步升级 CLI——成本会立刻反噬，而 capability 协商能把它摊平。

### 3.6 预览路径：结论不变，Lody 仍是最好的一份实现

`packages/shared/src/node/file-preview-path-policy.ts`（2026-11-17 仍在维护）的六条做法初版已列，这里只强调两条最容易漏的：

- **目标不存在时也要先判边界**，否则 `file_not_found` 与 `path_not_allowed` 的差异会变成「边界外是否存在」的预言机（434-455 行）；
- **数据目录不整目录放行**：`.lody` 根里有 `credentials.json`，所以白名单只列具体子目录（18-20 行）。kapibala 的 `~/.kapibala` 同样有 `settings.json`（含密钥），不能整体设成允许根。

kapibala 现状缺口不变：`preview-file.ts:44` 对绝对路径直接 `resolve`，`main/index.ts:614-629` 只校验调用来源、不校验读取范围。R9 保持。

### 3.7 MCP 信任：这轮没有更好的答案，如实标注

活跃仓里能查到的只有「disabled 状态」（opencode `packages/core/src/mcp/index.ts:702-703`）和一句注释（CodeWhale `crates/mcp/src/config.rs:189`：`only the trusted plugin merge adapter may attach it`），**没有任何一个活跃仓实现了 per-server 审批的完整闭环**。

初版引用的 per-server approval 来自 Claude-Code 快照（`mcpServerApproval.tsx` + `enabledMcpjsonServers` 名单）。它解决的是真问题，但依据是 C 级，不能当「业界做法」用。

处理方式：**降级为「需要自己定」**，但在定之前先回答一个问题——项目级 MCP 配置的写入，是否等价于「允许一个未审计的进程被自动拉起」。我的判断是不等价，理由与仓无关：项目信任回答的是「这个仓库的代码我可以跑」，MCP server 是**配置驱动**的常驻进程，可在任意时刻联网。两条权限的爆炸半径不同，不该共用一把钥匙。

R7 保留，但文档里不要写「参考业界实现」，写「本项目的权限模型要求」。

### 3.8 发布真实性：签名进发布门禁，不是文案问题

deepseek-harness 的桌面发布器把签名状态建成**枚举**并**硬性拦截**（`apps/desktop-publisher/src/desktop-publish-route.ts:17,57`）：

```ts
qualification: z.enum(['signed', 'notarized', 'unsigned', 'unnotarized']),
// ...
|| source.qualification !== (source.target === 'win-x64' ? 'signed' : 'notarized')
```

Windows 必须 `signed`，macOS 必须 `notarized`，否则发布路由直接拒绝（`desktop-website-installer.ts:39` 同一判据）。注意它把 `unsigned` 和 `unnotarized` 分开建模，并在失败文案里给出补救动作（`desktop-publish-qualification.mjs:9-12`）——不是笼统的「签名失败」。

这正好回应 011 的 `SHA256SUMS.txt`：**摘要和包同源，只能防损坏**；真实性的位置在平台签名，而且应该在门禁里拦，不是在文档里提醒。

kapibala 的对应做法：`011` 文案降级为完整性校验；`v0.1.4` 若不引入签名，就在 release 文档里明确「Unsigned / 未公证」，并且**不得**宣称可防替换。这与既有的「跳过不等于通过」口径一致（`docs/release-evidence.md`）。

## 5. 仍需自己定的三件事

1. **MCP 审批粒度**（§3.7）。活跃仓没有答案，快照有实现但不可作为现状。按权限爆炸半径论证，不要按「别人都这么做」论证。
2. **跨宿主 watch 租约**。jcode 是单机单进程的 `catchup_seen.json`，没有多宿主归属问题；kapibala 有 CLI + 桌面两个宿主可以同时恢复同一会话。最小可行：只有持会话锁的宿主能恢复监视。
3. **历史闭合**。kapibala 独有硬约束（`tool_use` 后必须有 `tool_result`，且循环内任何退出都要在满足之后）。所有「从历史重算」的逻辑（R8 的 todo、R4 的行数）都要额外过一遍闭合检查，这一点没有参照可抄。

## 术语表

- **catchup / 补投**：会话在你离开期间产生了需要关注的变化，回来时补一份简报。判定依据是「已看到的时间水位」，不是「是否通知过」。
- **watermark / 水位**：单调递增的确认点（这里是 `lastSeenAt` 毫秒时间戳），用来表达「处理到哪了」。
- **canonical result**：工具执行的完整结构化结果，落盘、可重放；与发给 provider 的 wire 投影分离。
- **capability 协商**：双方各自声明支持的能力集合，按交集启用；与「版本号必须相等」是两种不同的兼容策略。
- **qualification（签名状态）**：`signed / notarized / unsigned / unnotarized` 的显式建模，用于发布门禁判定，而不是一句「已签名」。
- **存在性预言机**：通过「不存在」与「不允许」两种错误码的差异，探测边界外文件是否存在。
- **lost update**：两个写者各自读旧值再整体写回，后写覆盖先写；全量数组提交最易触发。
- **bare repository**：无工作树的 git 仓库，只能读对象/blob，不会触发 checkout、filter、LFS 与符号链接。
