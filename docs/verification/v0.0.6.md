## 三协议与安全边界集成

- **多协议适配**：在 `packages/mcp/tests/` 体系中，真实 Provider 适配器分别针对 Anthropic Messages、OpenAI Responses 和 Chat Completions 进行了工具事务闭合、原生受保护前缀（`thought_signature` / 不透明 Responses 状态）与取消状态回归，断言来源元数据不向 wire 泄露。
- **网络与传输防御**：Streamable HTTP 针对显式回环、RFC 1918 私网网段、CGNAT、链路本地、组播及保留地址实施了全量拦截，白名单解析通过底层 Socket Remote IP 二次复核抵御 DNS Rebinding；重定向时隔离鉴权凭据。
- **历史恢复不变量**：旧历史（无 `mcpSource`）加载兼容；新会话历史仅保留事实，恢复会话与切换项目绝不隐式继承服务启动权限或工具调用授权。

## 未验证项与发布前置说明

1. **外部 npm Trusted Publisher 配置与新包首次发布**：
   新增公共包 `@kiturone/kapibala-mcp` 的首次发布无法由 OIDC 完成 —— npmjs 要求包先存在才能为其配置 Trusted Publisher。引导方式为手工认证发布一个低位占位版本登记包名（实际采用 `0.0.0-stage` / `0.0.0-placeholder.0` 这类预发布号），再在 npmjs.com 后台为该包配置 GitHub Actions Trusted Publisher，最后把占位版本标记为弃用。硬约束：
   - 占位版本号必须**低于**正式发布版本。`scripts/release.ts` 对 registry 上已存在的同版本会逐字节比对 tarball integrity，不一致即中止发布且不允许覆盖，用正式版本占位会永久卡死该次发布。
   - 占位版本号必须是合法 semver 形态；`dist-tags.latest` 指向带预发布段的占位号时，发布预检按 semver 规则将其视为**低于同号稳定版**放行，正式版本发布后 latest 由 registry 正常前移。非法形态（如 `garbage~1`）仍会在**任何包写入 registry 之前**中止流水线；该预检对 Core、MCP、CLI 三包整体生效，因此失败不产生部分发布，重跑无需回退版本号。
   - 占位清单的 `repository.url` 必须与 `github.com/tedburner/kapibala` 完全一致，否则后续 CI 侧发布被 registry 拒绝。
   - Trusted Publisher 的 Allowed actions 必须显式勾选 `npm publish`；新建配置默认只允许 `npm stage publish`，漏勾会在发布步骤表现为鉴权失败，且 npmjs 保存配置时不做任何校验。
2. **外部付费模型真实消费限制**：
   本地回归均通过确定性本地回环 HTTP/SSE 与受控本地 Stdio 进程完成，未向外部付费模型（Anthropic/OpenAI/DeepSeek 等）发起真实网络扣费请求；小样本验证不作为通用模型质量保证。

## 远端发布验收（2026-10-15）

v0.0.6 已于 2026-10-15 发布到 npm 与 GitHub Release：`@kiturone/kapibala@0.0.6`、`@kiturone/kapibala-mcp@0.0.6`、`@kiturone/kapibala-cli@0.0.6` 三包 `latest` 均为 0.0.6，[Release v0.0.6](https://github.com/tedburner/kapibala/releases/tag/v0.0.6) 附三包 tarball 与 `SHA256SUMS.txt` 并标记 Latest。发布源提交为标签 `v0.0.6`（b8c4cb8，**不是**发布提交 ad9e731，原因见下），成功的 Actions 运行为 [Release #38729315247](https://github.com/tedburner/kapibala/actions/runs/38729315247)。

发布过程共四轮运行、两类失败，均如实记录：

**其一，新包占位版本被发布预检拦停（#38725555978 与 #38728727237 连续两轮同因失败）。** `@kiturone/kapibala-mcp` 引导期实际发布的占位版是 `0.0.0-placeholder.0`（而非本文档先前计划的 `0.0.1`），它把该包的 `dist-tags.latest` 挂成了带字面段的号；`planPublication` 只接受三段纯数字，于是在**任何包写入 registry 之前**抛出 `Unexpected latest version` 并中止 —— 两轮均无部分发布，无需回退版本号。修复为预检按 semver 解析 `latest`，带预发布段的占位号视为低于同号稳定版放行，非法形态仍然拦停，并补四条回归用例（b8c4cb8，本地 `pnpm verify` 全绿）。

**其二，修复必须靠移动标签才能生效。** publish 任务检出的是 `prepare` 输出的 tag 提交，因此 ad9e731 上永远跑不到 b8c4cb8 的修复 —— 第二轮失败正是对这一点的实测确认。据此把 `v0.0.6` 标签 force-push 前移到 b8c4cb8。这是本仓库首次移动已发布的版本标签，其安全性来自失败发生的时机：GitHub Release 尚未创建（该步骤在 publish 之后）、npm 上不存在任何 0.0.6 产物，标签指向的 ad9e731 从未产出过可交付内容，前移不回收任何已分发资产。

**其三，registry 冒烟安装撞上 CDN 传播延迟（#38729299631）。** 标签前移的 force-push 自身触发了一轮发布：三包均通过 Trusted Publisher 成功上传，但冒烟安装的 npm CDN 传播延迟超出 10 次 × 30 秒重试窗（`ETARGET`）而中止 —— 与 v0.0.5 发布时同一模式。随后手动 dispatch 的运行（#38729315247）因与它共用 `kapibala-release` 并发组而排队约 9 分钟；拿到锁后按 SHA512 与 `latest` 校验跳过三个已发布同版本包，冒烟安装、GitHub Release 创建与资产上传全部完成。本地不重复隔离安装冒烟，以 CI 的 registry 安装为准。

**未闭合项（截至本记录）**：引导占位版本 `0.0.0-stage` 与 `0.0.0-placeholder.0` 既未标记弃用、`placeholder` 这一 dist-tag 也仍指向 `0.0.0-placeholder.0`，与本文「引导后把占位版本标记为弃用」的口径不符。它们不影响后续发布（预检只读 `latest`，而 latest 已前移到 0.0.6；integrity 比对只查目标版本自身；预发布号与本仓库十进制位进位产生的稳定号永不碰撞），但会长期留在可安装面之上。两版发布于 2026-10-15T11:07/11:09Z，npm 的 72 小时自助 unpublish 窗口内可直接删除，超窗后只能走 npm 人工申诉；弃用与 `dist-tag rm` 需要登录态，CI 的 Trusted Publisher 只覆盖 `npm publish`，无法代做。
