## 2. 逐项整改核验结论

### 2.1 已闭环（5 项）

- **R05 cwd 包含方向**：`runtime.ts:199`、`subagent-policy.ts:302` 均为 `isPathInside(workspaceRoot, executionCwd)` 正确方向；测试覆盖同根/子/兄弟/反向父与 `../../` 拒绝。缺口仅为跨盘负向用例（P2）。
- **R09 分支切换内存重载**：`reloadCurrent()`（`active-session.ts:71-101`）重建 AgentSession、重放 history、restore ContextManager/checkpoint；真实控制器取证复现原缺陷已消除（切换后内存=Store 投影，Fake Provider 收到正确消息集）。残余：`reloadCurrent` 自身不参与执行门（见 §4 N4）。
- **R10 fork 借用锁**：`session-manager.ts:688,817-819` 以 `wasAlreadyOpen` 区分借用/自持，finally 只释放自持；两条路径（持锁 fork、fork 失败）实测句柄完好。
- **R15 branchWithSummary 原子性**：写序改为「新分支 summary/usage 全部落盘 → 最后 selectBranch」（`session-store.ts:494-530`）；注入写失败后内存与重启重放游标均保持原分支，`branch_selected` 不可能先行。残余：失败留下 `branch_created` 孤儿分支；**该 API 无任何生产调用方**（`/branch create` 不走摘要路径），能力仍属死代码。
- **R16 fork 费用隔离**：`session/index.ts:371-395` primary/summary 两账本统一过滤 `importedFromFork`；真实链路实测新会话 `totalTokens=0`、首次请求只计自身。

### 2.2 部分修复（7 项）

- **R01 CLI 真实 runner（部分）**：`index.ts:254-262` 确已注入 `createCliSubagentRunner`，独立 Store、真实子会话、真实 summary/modelId。遗留：① 默认假 runner 仍在 `runtime.ts:92-98`，无「缺执行器显式拒绝」，SDK/headless 用户直接命中伪成功；② `modelOverride` 只做 id 改名不校验 profile（`subagent-runner.ts:93-96`）；③ role→场景路由未落地，explore 实际用默认模型；④ 工具表按原始请求而非 `effectivePolicy` 过滤（见 §4 N6）；⑤ 子会话不注册管理工具，递归 spawn/`waiting_children`/级联取消在生产不可达。
- **R02 提交后激活（部分）**：`onCommitted/onRollback` 机制真实（`capabilities/tools/index.ts:75-78`、`executor/index.ts:150-171`），`AgentSession` 在耐久落盘后、yield 前 commit（`session/index.ts:1258-1268`），正常路径成立。遗留：① 消费者提前 break 既不 commit 也不 rollback（`session/index.ts:1301-1308`），任务永驻 preparing 且 4/16 额度泄漏（§4 N9）；② `commit()` 先清空 rollbackActions 再执行动作，半途抛错则同批后续动作两个通道皆失（§4 N9）；③ 无 onCommitted 时仍回退 `queueMicrotask` 激活（`tools.ts:111-116`），且 `agent-runtime.test.ts:39-97` 第一个用例断言的正是这条回退路径——把缺陷固化为期望。
- **R03 ChildGrant 快照（部分）**：`deriveChildPolicy` 已接入且结果冻结为 `effectivePolicy`（`runtime.ts:221-271`）；custom 无白名单被拒。但求交输入是**伪造父策略**（见 §4 N5）；无效 modelOverride 与 worktree 仍静默受理；`AgentApprovalQueue`/`AgentTokenLedger` 零生产实例化。
- **R04 身份注入（部分）**：Executor→Session→runner 身份链已接通且模型输入不可覆盖，每树 4/16 限额基于 ctx 生效，`maxSteps` 有真实执行入口。遗留：`rootTaskId` 每会话一次而非每用户任务一次（`session/index.ts:987`），累计额度跨轮次消耗；spawn 幂等（parentSessionId+toolCallId）未实现；`generation` 恒 1（`tools.ts:94-104` 从不赋值）。
- **R06 跨树隔离（部分）**：list/wait/cancel 均以 `ctx.rootTaskId` 钉住并抛 `PERMISSION_DENIED`（`tools.ts:171-180,234-244,284-295`）。但校验是条件性的——ctx 缺 rootTaskId 时**整体跳过归属校验**、list 退化为全 Runtime 列举；缺省应拒绝而非放行。同树内祖先/旁支仍可被后代 cancel/wait。
- **R07 取消收口（部分）**：`runningPromises` 登记、`cancelling` 状态防覆写、cancel 等待在途 runner 后才写终态、槽位释放幂等、close 等级联等待——主干真实成立且无 cancelled→completed 反转。遗留：对不响应 abort 的 runner 无宽限超时与「清理中/失败」诊断，`/agents cancel` 与退出路径可被悬挂；超时归因漂移（abort 后 runner 正常返回记 `cancelled`、抛错记 `failed`）；`close()` 后无 closed 守卫仍可受理新任务。
- **R14 分支闭合校验（部分，引入新问题）**：`assertClosedToolTransaction`（`session-store.ts:181-249`）已接入 createBranch/forkSession/branchWithSummary，原始 c1/c2 部分回填复现场景三条路径均正确拒绝。但：① 不识别 `history_repair`，崩溃修复过的会话**永久无法再分叉**（§4 N2）；② 切点可为全局控制记录（title/usage，parentId=null），产生空历史孤儿分支（§4 N3）。

### 2.3 核心主张不成立（4 项）

- **R08 可靠通知（未闭环，差距最大）**：Runtime 终态确实写 outbox、`/agents collect` 真实经 SessionStore.append 落盘并拒绝异分支——比上轮是实质进步。但 `SubagentOutbox` 依旧纯内存 Map/Set（`outbox.ts:101-157`），§7 所称「持久化发件箱日志」「SessionInbox 恢复时自动重放未确认通知」**不存在**（无 replay/restore API）；`SessionCoordinator` 全库无生产实例化（仅测试构造），REPL 无空闲唤醒/自动投递接线；任务记录与 pending 通知随进程退出全丢；`interrupted` 状态全链路不可达，崩溃对账无入口。发布说明的「后台可靠通知」仍不成立。
- **R11 v1 升级（半接线，发布阻断级残留）**：只读原件字节不变已达标（`session-store.ts:1066-1071`、`:921-927` 实测 v1 全程字节保持、无 `.corrupt-` 副产物）；`--continue` 路径 autoUpgrade 成立。但**所有显式恢复入口未传 `autoUpgradeLegacy`**：`session-startup.ts:17`、`active-session.ts:65`、`history.ts:188`（`/resume` 与历史选择器），实测 `manager.open(v1Id)` 后首条追加仍抛 `LEGACY_SESSION_READ_ONLY`——「升级前用户无法无感续答」在显式恢复路径原样保留。另：升级只拿 `upgrade-<identity>.lock`，未按 spec 持源会话写锁（写后字节复核兜底，存在竞态窗口）；尾部残片 v1 永久不可 open/升级；已存在只读句柄时 autoUpgrade 被提前返回短路（`session-manager.ts:341-342`）。
- **R13 Worktree（危险回退半修复 + 零接线）**：`fs.rmSync` 强删兜底确已移除、remove 失败保守保留产物（实测 ✅）、`WORKTREE_DIRTY_BASE` 成立。但删除前**无写入者等待、无清理租约、无路径/worktree 身份复核**：故障注入实测「rev-list 检查后落盘的文件」仍被 `git worktree remove --force` 连目录删除（§7「检查后新增文件保留」声明不实）；`teardown` 对丢失映射的 agentId 谎报 `clean_removed` 而实际未删（目录/分支/条目成永久孤儿）；`WorkspaceIsolationAdapter` 全库零生产调用方，worktree 隔离整模块仍是死组件。
- **R17 Inbox 并发（单实例闭合、跨实例仍洞）**：同实例 `Promise.all` 双 consume 实测单条写入（`inFlightConsumes` 合并真实成立）；重启对账经 `readRecords` 扫 `subagentSource.eventId` 有真实测试。但 `/agents collect` 每次 `new SessionInbox`（`agents.ts:141`，且 `store as any` 绕过类型面），跨实例并发实测**两条重复消息**；唯一持有持久 inbox 的 `SessionCoordinator` 无人构造。当前 REPL 串行下为潜伏洞，但 §7「杜绝重复写入」不实；`agent-notification.test.ts` 4 项全为串行 consume，无任何并发用例。

### 2.4 R12（修复真实，新回归）

worker 熔断实测成立：`(a+)+$` × 40 个 a，timeoutMs=300 → 304ms 返回 `timedOut:true`，期间主线程定时器正常 tick；`session-search-archive.test.ts:270-306` 用病态正则真实断言。但：① **每次匹配新建 Worker（实测 ~93ms/次）**，无池化，默认 10s 超时下正则搜索实际只能扫约 100 条记录，大历史库几乎必返 partial——覆盖了 ReDoS 却把正常吞吐砍了一个量级；② worker 超时固定 1000ms 不随剩余 deadline 收缩；③ worker `error` 分支静默返回未匹配（`catalog.ts:200-206`），异常表现为「无结果」而非失败标记。
