## 问题详情与验收建议

### R01 · P1 · 正确读取否定形式的 MCP 开关

**定位：** `packages/cli/src/index.ts:255`，`main()` 的 `resolveCliMcpOptions()` 调用。

**场景与影响：** 用户传入 `--no-mcp`，期望完全禁用 MCP，CLI 仍会解析配置并进入服务启动流程。

**原因与证据：** minimist 将该参数解析为 `mcp: false`，而当前代码读取 `Boolean(args['no-mcp'])`。复现输出为 `{ _: [], 'no-mcp': false, mcp: false }`，最终传入 `noMcp: false`。

**修复建议：** 声明并读取 `mcp` 布尔选项，以 `args.mcp === false` 判断禁用。

**验收：** 从实际 argv 入口传入 `--no-mcp`；即使存在合法全局和项目配置，进程创建、网络连接及启动审批次数也应为零。

### R02 · P1 · 缺少授权通道时默认拒绝启动

**定位：** `packages/mcp/src/manager.ts:128–135`，`McpServerManager` 构造函数。

**场景与影响：** SDK 宿主未配置授权回调时，外部进程或连接未经批准即可启动。

**原因与证据：** 仅在提供 `authorizer`、`startupCache` 或 `startupCoordinator` 时创建协调器；否则 `startSingleServer()` 跳过整个授权流程。已复现 `new McpServerManager()` 直接启动 stdio 服务并达到 `ready`。

**修复建议：** 始终创建启动协调器，缺少可用授权通道及显式预授权时拒绝启动。

**验收：** 覆盖未配置授权器、空缓存及非交互宿主，确认零进程创建、零网络连接；显式批准路径仍可正常启动。

### R03 · P1 · 回滚前取消并等待所有启动任务

**定位：** `packages/mcp/src/manager.ts:226–231`，`startupAll()`。

**场景与影响：** 用户审批等待超过总体截止时间，启动流程已经失败并销毁；迟到的批准仍会创建新进程，失去有效清理所有者。

**原因与证据：** `Promise.race()` 超时不会取消 `executionPromise`，审批返回后也未再次复核管理器是否销毁。已复现 `startupAll()` 超时并 `teardown()` 后，状态仍变成 `{ tornDown: true, state: 'ready', pid: <新进程> }`。后续幂等销毁不会重新扫描新资源。

**修复建议：** 使用内部取消信号，在审批返回和创建资源前复核取消及销毁状态；取消并等待所有启动 worker 收口后再完成回滚。避免将用户审批等待误算为技术连接超时。

**验收：** 用延迟审批分别覆盖总体超时、取消与销毁；批准迟到后不得创建任何新资源，既有资源必须清理完成。

### R04 · P1 · 保留自动上下文压缩机会

**定位：** `packages/core/src/context/session/index.ts:824–832`，`AgentSession.runOperation()`。

**场景与影响：** 历史累计较大或切换至较小模型窗口后，普通 `run()` 在现有自动剪裁和摘要流程之前就抛出超限错误。

**原因与证据：** 新增预检对所有运行生效，并将未压缩历史全部计入预算。已复现包含长历史的普通调用直接报 `Prepared task content exceeds context input budget`；后续 `ContextManager.prepare()` 原本有机会进入压缩流程。

**修复建议：** 通过现有上下文准备流程判断压缩后的实际输入预算；保留完整模板超限时零 user append 的要求，避免以未压缩总历史直接否决普通运行。

**验收：** 构造包含可压缩旧轮次的超限历史，确认普通运行可以压缩后继续；仅当前任务本身无法容纳时，才在模型调用前拒绝。

### R05 · P1 · stdio 重连成功后重新发布工具

**定位：** `packages/mcp/src/manager.ts:548–554`，`reconnectServer()` 的 stdio 分支。

**场景与影响：** 执行 `/mcp reconnect <server>` 后服务显示 `ready`，模型调用该服务工具却持续失败；从禁用状态启用 stdio 服务也无法正常发布工具。

**原因与证据：** stdio 分支仅重新发布 Prompts，缺少 HTTP 分支已有的 `discoverAndPublishTools()`。注册表仍持有闭包引用旧 session 的适配器。已复现重连前后适配器对象相同，执行返回 `MCP_SERVER_UNAVAILABLE`，旧 session 状态为 `disconnected`。

**修复建议：** 在新连接代次就绪后，原子替换该来源的工具集合；处理重连失败时旧目录的失效状态。

**验收：** 对 stdio 服务执行重连及禁用后启用，确认工具绑定新代次且能调用；旧运行快照不得转调新实例。

### R06 · P1 · 将目录刷新发布到宿主注册表

**定位：** `packages/mcp/src/client.ts:153–160`，`registerNotificationHandlers()`；Prompts 通知存在对应路径。

**场景与影响：** 服务端发送目录变更通知后，工具即使仍存在，也持续因 epoch 不匹配被拒绝；模板搜索仍显示旧目录。

**原因与证据：** 处理器只更新 `_discoveredTools` / `_discoveredPrompts` 和状态，没有驱动宿主注册表更新。触发工具通知后，已观察到 session epoch 为 2，注册表版本不变，适配器仍绑定 epoch 1。

**修复建议：** 通知到达时立即失效对应能力的可用资格，完整刷新成功后通过管理器原子发布；维持 Tools 与 Prompts 的独立状态和过期回调防护。

**验收：** 覆盖新增、删除、同名定义更新、刷新失败和连续通知；新运行使用新目录，旧运行拒绝漂移工具，另一类能力不受影响。

### R07 · P1 · 将调用异常转换为正确的执行事实

**定位：** `packages/mcp/src/tools/adapter.ts:152–161`，`createMcpToolAdapter().execute()`。

**场景与影响：** 工具已发送，远端可能已完成写入，但连接在返回前中断；宿主却将其记为确定失败，无法按结果未知暂停。

**原因与证据：** `callTool()` 的 rejection 直接抛至 Core；`toExecutionResult()` 只处理成功返回值，因此 converter 中的 Error 分支不会处理真实调用异常。受控连接中断复现结果为 `TOOL_FAILED`、`retryPolicy: 'never'`、`dispatchOutcome: 'failed'`。

**修复建议：** 在适配器边界捕获并规范化异常，区分发送前拒绝与发送后结果未知；后者使用 `OUTCOME_UNKNOWN`、`dispatchOutcome: 'unknown'` 和 `after_user_action`。

**验收：** 模拟服务端完成副作用后断开连接，确认暂停且不自动重放；发送前身份拒绝必须保持 `not_sent`。

### R08 · P1 · 正确转换无响应体的 HTTP 状态

**定位：** `packages/mcp/src/transports/http.ts:204–208`，`executeSecureHttpRequest()`。

**场景与影响：** 服务端返回 204 等无响应体状态时，整个 Node 进程退出，无法按单服务错误处理。

**原因与证据：** 无条件执行 `new Response(webStream, ...)`，而 204、205、304 禁止携带响应体。已通过本地回环 204 服务复现未捕获的 `TypeError: Response constructor: Invalid response status code 204`；异常发生在异步 HTTP 回调内。

**修复建议：** 对禁止响应体的状态传入 `null`，并将回调内转换异常交给 Promise 的 `reject`。

**验收：** 覆盖 204、205、304 以及普通 JSON、SSE 响应；客户端不得产生未捕获异常或退出进程。

### R09 · P1 · 获取远端模板前应用权限策略

**定位：** `packages/cli/src/commands/prompts.ts:84–103`，`promptCommand`。

**场景与影响：** Plan 模式或宿主拒绝规则生效时，`/prompt` 仍可发起外部请求并追加任务。

**原因：** 当前路径仅检查忙碌状态、插件、连接存在性及参数，然后直接通过准备函数调用 `getPrompt()`；没有获取阶段的模式与权限裁决。对照依据为本次变更规格 `openspec/changes/v0-0-6-mcp-ecosystem/specs/mcp-user-prompts/spec.md` 中的 “Explicit invocation does not override hard policy”。

**修复建议：** 在远端获取前应用 Plan、宿主硬限制和 deny 规则；模板获取许可不能传递给后续工具执行。

**验收：** Plan 及显式 deny 下正文请求和 user append 次数均为零；允许获取后，模板建议的写入或执行工具仍逐次审批。

### R10 · P1 · 复核活动连接的 Prompt 身份

**定位：** `packages/mcp/src/prompts/runner.ts:163–172`，`prepareMcpPromptTask()` 的 `verifyIdentity()`。

**场景与影响：** 模板获取期间收到目录变更通知，过期准备结果仍可提交到历史并发给模型。

**原因与证据：** 只比较 `getCurrentPrompt()` 返回的缓存项，没有复核活动 session 的连接、能力状态与实时 epoch。通知先改变 session epoch 时，旧注册表项仍与自身匹配。受控复现中 epoch 从 1 变成 2 后，`verifyIdentity()` 仍返回 `true`。

**修复建议：** 获取前及最终提交前核对当前连接身份、`promptsState`、generation 和实时 epoch，并保留定义摘要校验。

**验收：** 获取期间和获取完成后提交前分别注入通知、断连与重连；本次准备均应零 append、零加载事件、零模型请求，即使刷新后定义摘要相同也不能恢复旧准备资格。

### R11 · P2 · 接入 HTTP 请求头环境变量解析

**定位：** `packages/mcp/src/transports/http.ts:284–290`，`createManagedHttpTransport()`。

**场景与影响：** 按文档使用 `Authorization: Bearer ${TOKEN}` 配置认证时，服务端收到占位符而认证失败。

**原因与证据：** headers 被直接复制给传输，已有 `resolveHttpHeaders()` 未进入实际调用链。回环 HTTP 服务观察到认证头为字面量 `Bearer ${REVIEW_TOKEN}`，缺失变量也未在启动前阻断。

**修复建议：** 接入环境变量解析，并处理缺失变量及凭据告警；解析后的凭据不得进入日志和来源元数据。

**验收：** 设置临时测试变量并捕获请求头，确认发送展开后的值；变量缺失时零请求，多服务之间不串用认证头。

### R12 · P2 · 将任务取消信号传入 Prompt 获取

**定位：** `packages/mcp/src/prompts/runner.ts:118–121`，以及 `packages/cli/src/commands/prompts.ts:97–103`。

**场景与影响：** 远端模板迟迟不返回时，Ctrl+C 或消费者结束不能及时取消获取，会话与控制器持续忙碌到原请求超时。

**原因：** CLI 丢弃 `PreparedTaskContext.signal`，`PreparePromptTaskOptions` 没有 signal 字段，`getPrompt()` 调用也未传请求取消选项。

**修复建议：** 从受控任务上下文贯通取消信号，设置有界请求与清理期限，等待收口后再释放执行门。

**验收：** 阻塞 `getPrompt()`，在准备期间触发取消及消费者结束；确认请求收到取消、在约定期限内释放 busy 状态，并保持零 user append。

### R13 · P2 · 对整个工具结果应用共享字节预算

**定位：** `packages/mcp/src/results/converter.ts:80–81`，`convertMcpToolResponse()`。

**场景与影响：** 多个合法内容块拼接成远超 20 KiB 的结果，进入模型与历史，放大上下文和存储占用。

**原因与证据：** 每块独立截断后直接拼接，没有整体结果预算。已复现十个各 20,000 字节文本块生成 200,018 字节结果。

**修复建议：** 让所有 content 块和 structuredContent 共用单结果 20 KiB 预算；对整体传输负载实施 4 MiB 硬上限，保持截断标识和结构安全。

**验收：** 覆盖多文本块、文本加结构化结果及多字节字符，确认最终保留结果满足整体预算；超传输硬界明确拒绝。

### R14 · P2 · 为音频补充二进制净化分支

**定位：** `packages/mcp/src/results/sanitizer.ts:92–94`，`sanitizeMcpContentBlock()`。

**场景与影响：** 合法 audio 内容块的裸 Base64 进入模型及持久历史，违反多媒体仅保留元数据的约定并浪费上下文。

**原因与证据：** 当前仅特殊处理 image 和 resource，audio 落入 `JSON.stringify()` 兜底。已复现 audio 的 `data` 字段原样保留在转换结果中。

**修复建议：** 对 audio 输出仅包含类型、mimeType 和大小的占位符，不保留二进制正文。

**验收：** 使用带唯一标记的音频数据，确认模型输入与落盘历史不含原始 data，仍保留可解释的媒体元数据。

### 1. 业务改动一览

- **R01（`--no-mcp` 否定开关）**：`packages/cli/src/index.ts` 中配置 minimist 布尔选项 `default: { mcp: true }`，读取改为 `args.mcp === false || Boolean(args['no-mcp'])`，彻底规避 minimist 生成 `{ mcp: false, 'no-mcp': false }` 的边界。
- **R02（缺少授权通道默认阻断）**：`packages/mcp/src/manager.ts` 构造函数始终创建 `ServerStartupCoordinator`，在未配置授权器且无会话缓存的非交互环境中默认判定 `permitted: false`，杜绝未审批外部进程静默启动。

## 第二轮问题详情

### R15 · P0 · 发送前撤销被误标为已执行失败

**定位：** `packages/mcp/src/tools/adapter.ts` execute 的发送前资格复核（约 134–150 行）与 `packages/core/src/runtime/executor/index.ts` 通用 catch（约 702–713 行）。

**场景与影响：** 工具在审批/审计完成后、发送前发生目录撤销或身份漂移时，适配器抛出 `MCP_TOOL_CHANGED` / `MCP_SERVER_UNAVAILABLE` 异常；该异常落入 Executor 通用 catch，被记为 `dispatchOutcome: 'failed'`——即"远端已执行且失败"。违反设计 §7"发送前失败必须为 not_sent、不得伪装已执行"，模型与审计会基于错误的执行事实决策。

**原因与证据：** 适配器内的 `__isMcpPreDispatchError` 哨兵（adapter.ts 约 177 行）与 `results/converter.ts` 的 not_sent 分支（约 35 行）互不衔接，均为从未生效的死代码；`review-fixes-regression.test.ts` 对 R07 的用例绕过 Executor 直测适配器，掩盖了 Core 侧的真实落点。第一轮 R07 修复声明"发送前状态检查失败立即抛出错误"恰恰构成本缺陷。

**修复建议：** 发送前复核失败不得以裸异常出栈；应返回 `toExecutionResult` 可识别的结构化结果（`dispatchOutcome: 'not_sent'`、`retryPolicy: 'never'` 或 `after_user_action`），或在 Executor 通用 catch 中识别哨兵并保留 not_sent 事实。补一条贯穿 Executor 全管线的回归测试。

**验收：** 审批通过后注入目录撤销，断言最终 tool_result 的 execution 为 `{version:1, dispatchOutcome:'not_sent'}`、transport 发送计数为 0。

### R16 · P0 · 并发启动回滚孤儿竞态

**定位：** `packages/mcp/src/manager.ts` startupAll（约 297 行）与 runWithConcurrencyLimit（约 969–983 行）。

**场景与影响：** 多服务并发启动时首个 worker 失败，`allSettled` 包装立即返回并进入回滚/teardown；其余仍在启动中的 worker（可能正在等待审批或正在 spawn）成为无所有者的孤儿进程/连接。违反设计 §5"setup 失败释放全部失败资源、禁止遗留未受管的启动 Promise"。

**原因与证据：** runWithConcurrencyLimit 在首个 rejection 时短路返回，未等待兄弟 worker 收口；第一轮 R03 修复声明的 `await Promise.allSettled([executionPromise])` 只覆盖单 promise 包装，未覆盖并发 worker 集合本身。

**修复建议：** 首个失败仅触发共享 AbortSignal，函数返回前必须 `allSettled` 全部 worker；每个 worker 在审批返回后、spawn 前、connect 后三级复核取消状态（与 R03 既有机制合流）。

**验收：** 三个并发服务，其一立即失败、其二延迟审批、其三正常启动；断言失败后零孤儿进程（真实 PID 核对）、全部资源有清理所有者。

### R17 · P1 · 请求级超时未实现

**定位：** `packages/mcp/src/manager.ts`（约 462、699 行，requestTimeoutMs 被覆写为 startupTimeoutMs）、`transports/http.ts`（不消费该值）、`tools/adapter.ts`（execute 无计时器）、`packages/core/src/runtime/executor/index.ts`（`managesTimeout=true` 时跳过通用 race）。

**场景与影响：** 远端 `tools/call` 挂死不响应时，调用永不收口：Session 永久 busy，用户只能杀进程。设计 §5 明确 request 60s 默认期限，且 `managesTimeout=true` 的前提就是适配器自管期限——现在两层都没有计时器。

**修复建议：** 在 adapter.execute 内实现单次调用期限（含本地有界收口），期限值从服务配置 requestTimeoutMs 传入，不得复用 startupTimeoutMs。

**验收：** 受控 Server 接受请求后永不响应；断言约 requestTimeoutMs 后返回 `unknown`/`OUTCOME_UNKNOWN`、`after_user_action`，Session 释放 busy，且不自动重放。

### R18 · P1 · 目录刷新无有界周期

**定位：** `packages/mcp/src/client.ts` registerNotificationHandlers 及刷新路径（约 138–270 行）。

**场景与影响：** 服务端连续发送目录变更通知时，每次通知都触发独立刷新，无"单刷新 + dirty 合并 + 每周期最多三轮共享 catalogTimeoutMs"机制；恶意或异常 Server 可致无限刷新循环，违反设计 §3.1。

**修复建议：** 实现每能力至多一个在途刷新与一个 dirty 标记；周期内最多三轮，共享 catalogTimeoutMs 总截止；耗尽后保持 stale/unavailable，仅新通知或显式重连开启新周期。

**验收：** 注入持续高频通知，断言刷新轮次 ≤3、总耗时受 catalogTimeoutMs 约束、终态为 stale/unavailable 而非自旋。

**场景与影响：** `entry.config.enabled` 直接赋值，而 config 对象按引用来自宿主解析结果；同进程多会话（切换/并存）时，一个会话的 `/mcp disable` 泄漏到其他会话，违反"enable/disable 只改变当前 Session"。回滚把 disabled 条目标为 'failed'，状态展示失真。

**验收：** 两会话共享同一解析配置，会话 A disable 后断言会话 B 状态与 config 原值不变。

### R25 · P2 · Socket 复核晚于数据 flush

**定位：** `packages/mcp/src/transports/http.ts` executeSecureHttpRequest（约 225–248 行复核，255–267 行写体）。

**场景与影响：** 复核在 `connect` 事件回调中执行，而 `req.end()` 已把含 Authorization 的头/体写入内核缓冲；DNS Rebinding 命中时存在"数据先出、destroy 后到"的窄竞态，凭据可能已送达攻击者 IP。设计承诺"Socket 建立后复核底层 IP"应保证复核先于任何应用数据可达。

**修复建议：** 将连接 pin 到 `resolveAndValidateHostIps` 已校验的 IP（`lookup` 钩子返回白名单 IP 并设 servername/host 头），或在复核通过前不写入头/体。

**验收：** 模拟首答公网 IP、次答内网 IP 的 rebinding DNS，断言含凭据字节零到达内网目标。

### R26 · P2 · 4 MiB 上限在完整缓冲后检查

**定位：** `packages/mcp/src/results/converter.ts`（约 74 行 wire 上限检查）。

**场景与影响：** 检查发生在响应已被 SDK/转换器完整读入内存之后；恶意 Server 返回超大响应仍可造成内存放大。设计 §7 要求"必须在传输或有界解码处限制，不能先无限累积再检查"。第一轮 R13 修复声明的"传输负载硬界"实际落点在转换阶段。

**修复建议：** 在 secureFetch 响应流上包一层计数 TransformStream，超限即中断流并销毁连接；converter 保留现有检查作兜底。

**验收：** 回环服务返回 >4 MiB 流式响应，断言进程内存增量有界且错误为 MCP_RESULT_TOO_LARGE。

### R27 · P2 · 非 TTY 输出 ANSI
