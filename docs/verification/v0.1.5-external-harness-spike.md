## 2. 关键实测证据与架构定案

### 2.1 Windows 无 Shell 启动与 `.cmd` 静态解包（实证通过）
- **修正原假设**：原 015 草稿假设 npm `.cmd` 一律指向 `.js` 脚本。实测 `opencode.cmd` 指向 `node_modules\opencode-ai\bin\opencode.exe`（原生二进制包），`dsh.cmd` 指向 `node_modules\@deepseek-ai\dsh\lib\bin.js`（Node 脚本包），而 `codex` 同目录并存 `codex.exe` 与 `codex.cmd`。
- **定案规则**：探测扩展名顺序固定为 `[".exe", ".cmd"]`（优先命中原生 `.exe`）；命中 `.cmd` 时仅解析含 `%*` 的执行行，经 `fs.realpathSync.native` 校验目标位于受管 `node_modules` 内后，按后缀/shebang 分流至「直接执行 `.exe`」或「`node.exe` 执行脚本」，全程 `shell: false`，子进程环境白名单已验证不含 `NODE_OPTIONS` 与 `ELECTRON_RUN_AS_NODE`。

### 2.2 ACP 客户端能力边界与 `session/load` 时序（实证通过）
- **零客户端 `fs/*` 依赖**：在显式声明 `clientCapabilities: { fs: { readTextFile: false, writeTextFile: false }, terminal: false }` 与 `mcpServers: []` 下，`opencode 1.19.3` 完整完成思考与回复，`incomingRequests` 为空数组；v0.1.5 维持 `fs/*` 与 `terminal/*` 全关。
- **`session/load` 无 `sessionId` 回包且通知先行**：`opencode 1.19.3` 的 `session/load` 响应体仅含 `{"configOptions":[...]}`（无 `sessionId` 键），且在响应返回前先推送了 `user_message_chunk`、`agent_thought_chunk`、`agent_message_chunk`、`available_commands_update` 共 4 条重放通知。证实适配器必须在发送 `session/load` 请求**之前**预绑 `nativeSessionId` 路由。
- **`loadSession` 与 `sessionCapabilities.resume` 双形态**：`opencode` 声明顶层 `loadSession: true`，而 `dsh 0.2.0-rc.2` 仅声明 `sessionCapabilities.resume: {}`。`AcpStdioDriver` 需同时解析这两个能力位。

### 2.3 `stdin.end()` 优雅退出 + `taskkill /T /F` 两段式回收（实证通过）
- 空闲态下，`opencode`（118ms）、`dsh`（95ms）、`codex app-server`（556ms）均在收到 `stdin.end()` 后 600ms 内自行退出且退出码为 `0`。
- 当 `claude.exe` 处于上游网络重试阻塞态时，单纯 `stdin.end()` 在 2000ms 宽限期内不会退出，自动升级 `taskkill /pid <pid> /T /F` 后于 692ms 内完成整树回收。证明「先关 stdin 给优雅收尾窗口 → 超时强杀进程树」两段式停机缺一不可。

### 2.4 凭据透传（`envFrom`）与图形化诊断必要性
- `dsh --profile acp` 在未注入 `DEEPSEEK_API_KEY` 时握手与建会话均成功，首轮 Prompt 返回明确的英文缺 Key 错误；证实设置页「外部代理」图形界面提供 **`envFrom` 环境变量名白名单转发**与 **Flavor 中文故障翻译**的直接价值。
