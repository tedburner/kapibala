## 3. P1：发布阻断问题

### R01：CLI 子代理没有执行真实 AgentSession，却返回完成

**位置**：[CLI index.ts:249](../../packages/cli/src/index.ts#L249)、[runtime.ts:88](../../packages/core/src/runtime/agent/runtime.ts#L88)。

CLI 直接 `new AgentRuntime()`，没有注入 runner。默认 runner 无条件返回 `{ summary: 'Completed successfully' }`。生产源码中没有 `setRunner` 调用，也没有把任务转换为标准子 `AgentSession.run()` 的工厂。

**触发与影响**：正常调用 `spawn_agent` 即可得到 `completed` 和固定成功摘要，但没有任何子模型请求、任务执行或产物。这是当前发布说明核心能力的功能缺失。

**证据**：本地使用默认 Runtime 启动 explore 任务，记录立即进入 `completed`，`summary` 为固定英文文本，`modelId` 缺失。

**建议**：由宿主注入真实子会话工厂，绑定独立 Store、工具集合、模型、取消与统计；没有执行器时显式拒绝启动。加入通过 CLI 工厂、Fake Provider 和真实 Store 的集成测试，验证 prompt 到达子会话并产生真实结果。

### R02：子任务通过微任务激活，没有等待父工具事务耐久提交

**位置**：[tools.ts:105](../../packages/core/src/runtime/agent/tools.ts#L105)、[runtime.ts:260](../../packages/core/src/runtime/agent/runtime.ts#L260)。

`spawn_agent.execute` 在返回回执前安排 `queueMicrotask(runtime.activateSpawn)`。微任务只控制 JavaScript 调度顺序，不能证明 assistant、同批所有 tool_result 已经完成 `MessageStore.append` 与 fsync。Session / Executor 也没有对应的 transaction-committed 回调或待提交资源守卫。

**触发与影响**：父消息落盘缓慢、落盘失败或消费者提前结束时，子 runner 可以先开始；接入真实执行器后可能产生没有已提交父回执的副作用。与详细设计 §7.1 明确禁止的“通过工具返回推测落盘”相冲突。

**证据**：注入 runner、延迟模拟调用方的回执提交，runner 已运行而提交确认仍为 false。现有启动测试只断言工具返回 accepted，未经过父 Store 提交流程。

**建议**：准备阶段仅预留资源并持久化启动意图；由 Session 在整批工具事务提交成功后显式激活。提交失败/受理前取消应撤销准备资源并等待清理。测试覆盖延迟 append、append 失败、同批部分成功和消费者提前 return。

### R03：ChildGrant、模型覆盖和 Worktree 请求被受理后丢弃

**位置**：[runtime.ts:122](../../packages/core/src/runtime/agent/runtime.ts#L122)、[runtime.ts:214](../../packages/core/src/runtime/agent/runtime.ts#L214)、[subagent-policy.ts:274](../../packages/core/src/capabilities/security/subagent-policy.ts#L274)。

工具 schema 接受 `allowedTools`、`isolation`、`modelOverride`，但 `prepareSpawn` 没有调用 `deriveChildPolicy`，任务记录也不保存这些参数或有效授权。生产链路未使用 `AgentApprovalQueue`、`AgentTokenLedger`、`WorkspaceIsolationAdapter`；回执中的 `modelRole` 只是角色名称，未解析真实模型与可用凭据。

**触发与影响**：`custom` 不带必需白名单、`modelOverride` 指向不存在模型、或请求 `worktree`，均仍会被 accepted。调用方无法依靠受理结果确认权限收紧、模型选择与物理隔离已落实。当前假 runner 不产生实际工具越权，但把它替换成真实 runner 不能自动补全安全契约。

**证据**：本地向 custom 角色传入无白名单、无效模型和 worktree 请求，仍受理成功；全源码搜索只找到上述组件定义/导出，没有生产实例化或策略派生调用。

**建议**：受理前解析模型和有效 ChildGrant，保存不可扩大快照；按所选隔离创建并复核工作区，构造受限子工具目录，在最终执行处再次校验撤销/代次。把 FIFO 审批和请求前预算预留接入真实调用链。未支持的参数应明确拒绝。

### R04：Executor 没有传递来源身份，任务树限额和归属失效

**位置**：[executor/index.ts:662](../../packages/core/src/runtime/executor/index.ts#L662)、[tools.ts:93](../../packages/core/src/runtime/agent/tools.ts#L93)、[runtime.ts:149](../../packages/core/src/runtime/agent/runtime.ts#L149)。

Executor 构造的 `ToolContext` 没有 `sessionId`、`runId`、`branchId`、`toolCallId`、`rootTaskId`、`depth`、`agentId`。工具因此退化为 `session-default` / `run-default` / `call-default` / `main` / 深度 0；缺失 rootTaskId 时，每次 spawn 又生成一个新根任务 ID。

**触发与影响**：同一用户任务的多个子任务被拆成不同任务树，绕过每树活动上限 4 和累计上限 16；非 main 分支归属错误，取消也无法对应真实来源 run。`parentSessionId + spawnToolCallId` 的受理幂等没有实现。`maxSteps` 目前只写入记录，没有步骤执行/计账入口。

**证据**：用缺失 rootTaskId 的相同父上下文连续准备 5 个任务，全部成功，得到 5 个不同根 ID。真实 Executor 恰好没有传入这些身份字段。

**建议**：在可信 Session/Executor 边界注入完整身份，不允许模型输入覆盖；根用户任务创建一次 rootTaskId，通知轮次延用；启动幂等和限额均基于该身份持久管理。增加从 `AgentSession.run` 发起多次 spawn 的限额、分支与重试测试。

### R05：子任务 cwd 包含关系参数写反，允许父目录并拒绝合法子目录

**位置**：[runtime.ts:188](../../packages/core/src/runtime/agent/runtime.ts#L188)、[workspace.ts:98](../../packages/core/src/context/workspace.ts#L98)。

`isPathInside` 的签名是 `(base, target)`，Runtime 却传入 `(nativeExecutionCwd, nativeWorkspaceRoot)`。其检查结果变成“工作区是否位于执行目录内”。

**触发与影响**：`cwd: 'sub'` 被拒绝，`cwd: '..'` 被接受并写入任务记录，违反工作区边界。虽然尚未接入真实子会话，当前受理边界已经错误。

**证据**：本地真实目录复现：合法子目录返回 `SUBAGENT_WORKSPACE_VIOLATION`；父目录成功受理。

**建议**：使用 `isPathInside(nativeWorkspaceRoot, nativeExecutionCwd)`；分别覆盖同根、子目录、父目录、兄弟目录、跨盘与链接逃逸。

### R06：模型管理工具没有验证调用方任务树成员关系

**位置**：[tools.ts:156](../../packages/core/src/runtime/agent/tools.ts#L156)、[tools.ts:213](../../packages/core/src/runtime/agent/tools.ts#L213)、[tools.ts:252](../../packages/core/src/runtime/agent/tools.ts#L252)。

`list_agents` 接受模型提供的 rootTaskId，缺失时可能列出整个 Runtime；`wait_agent` 和 `cancel_agent` 直接使用任意 agentId，没有校验调用方是否有权访问该后代。`agent:spawn` 只证明调用能力，不能证明目标归属。

**触发与影响**：共享 Runtime 中，一个会话/任务树可读取或取消另一棵树。即使修复 R04 的身份传递，显式指定其它 rootTaskId / agentId 仍可以绕过默认过滤。

**证据**：用 `sessionId: 'unrelated'` 调用 list 得到其它上下文的 5 个任务；用同一不相关上下文取消其中一个，状态变成 cancelled。

**建议**：模型工具必须从可信上下文计算可访问后代，过滤参数只能收窄；目标不属于当前授权树时拒绝。CLI 显式用户管理可走独立宿主入口。测试同树、兄弟树、父节点和不存在 ID。

### R07：取消与 close 未等待 runner 清理，取消终态还能被覆盖

**位置**：[runtime.ts:304](../../packages/core/src/runtime/agent/runtime.ts#L304)、[runtime.ts:414](../../packages/core/src/runtime/agent/runtime.ts#L414)、[runtime.ts:532](../../packages/core/src/runtime/agent/runtime.ts#L532)。

Runtime 没有保存可等待的在途 runTask Promise。`cancelTask` 发出 abort 后就清除 controller、释放槽位、写 cancelled 并返回，没有等待 runner 的工具/进程清理。runner 随后正常返回时，`runTask` 又无条件写 completed。`close` 等待的是这种提前返回的 cancelTask。

**触发与影响**：工具还在执行或清理时，新任务已可占用槽位；宿主可能随后释放会话锁和连接，形成后台副作用与资源所有权失配。取消结果也会从 cancelled 反转为 completed。

**证据**：注入延迟结束的 runner，cancel 返回时 `runnerExited=false`、`slotReleased=true`；释放 runner 后任务状态由 cancelled 变为 completed。

**建议**：保存每项任务执行/清理 Promise；先进入 cancelling，再 abort 并级联等待，确认全部退出后才写终态、发通知和退槽。对不响应取消的执行器保留清理中/失败诊断。增加延迟清理、清理失败、超时和 close 顺序测试。

### R08：可靠通知只有独立内存组件，没有耐久投递与生产接线

**位置**：[outbox.ts:101](../../packages/core/src/runtime/agent/outbox.ts#L101)、[runtime.ts:340](../../packages/core/src/runtime/agent/runtime.ts#L340)、[agents.ts:108](../../packages/cli/src/commands/agents.ts#L108)。

`SubagentOutbox` 只有 Map/Set，没有 Store、落盘或恢复入口；Runtime 终态路径未写 outbox。生产代码没有构造 SessionInbox / SessionCoordinator 并接入任务终态、父轮次或 REPL 调度。`/agents collect` 只是打印“终态结果已提交至收件箱”，没有实际消费调用。

**触发与影响**：子结果无法自动进入父会话；退出/崩溃后任务状态、未确认通知与 ACK 丢失。已运行任务也没有恢复为 interrupted 的对账链路。发布说明中的后台可靠通知不成立。

**证据**：登记通知后重新构造 Outbox，待投递数量为 0；源码调用链中没有终态到发件箱、收件、ACK、消费和父 Session 的连接。现有通知测试手动拼装组件，没有走生产 Runtime。

**建议**：实现终态/outbox 的耐久提交或可验证重建、inbox_received/ACK、消息/消费确认与重启补偿；由单一协调器在正确分支和事务安全边界更新存储及内存历史。`collect` 必须以实际持久化消费结果为成功依据。覆盖三个崩溃窗口及重投。

### R09：CLI 切换同一会话分支后，内存仍是旧分支

**位置**：[branch.ts:64](../../packages/cli/src/commands/branch.ts#L64)、[branch.ts:103](../../packages/cli/src/commands/branch.ts#L103)、[active-session.ts:138](../../packages/cli/src/active-session.ts#L138)。

分支命令在 `selectBranch` 后调用 `active.resume(当前 conversationId)` 重载，但控制器发现目标 ID 与当前 ID 相等就直接 return。它既没有重建 Session，也没有刷新 history、checkpoint 和 ContextManager。

**触发与影响**：下一次模型请求看到旧分支历史，新消息却追加到新分支。用户看到“切换成功”，持久日志和实际推理上下文已经不一致。

**证据**：建立两条消息后从第一条分叉并调用相同恢复路径，Store 投影为 1 条，`session.getHistory()` 仍为 2 条。

**建议**：新增受执行门保护的分支切换/重载 API，使持久游标与内存状态共同更新；不能依赖同 ID resume。用真实 ActiveSessionController 验证切换后 Fake Provider 接收到的消息及重启投影。

### R10：forkSession 释放了调用方仍持有的源会话写锁

**位置**：[session-manager.ts:665](../../packages/core/src/context/session-manager.ts#L665)、[session-manager.ts:801](../../packages/core/src/context/session-manager.ts#L801)。

`open(sourceSessionId)` 对 Manager 已持有的源会话返回同一个 handle。`forkSession` 的 finally 却无条件 `source.release()`，等于释放借用的调用方资源。

**触发与影响**：CLI 当前源 Session 仍绑定原 Store，锁却已经释放；尤其在 fork 后重命名或切换失败时，源 Session 会继续使用无锁写者。其它打开者可进入，破坏单写者保证。

**证据**：持有源 handle 调用 fork，再 `manager.open(sourceId)` 返回新 handle，而原 Session 仍存在，说明原句柄已被移出管理并释放。

**建议**：区分借用与拥有的句柄；只释放 fork 自己新取得的读/写资源，或给句柄明确引用计数。覆盖当前活动会话 fork、导出失败、导出后切换失败和第二写者竞争。

### R11：v1 首写不会自动升级，打开还可能改写只读原件

**位置**：[session-manager.ts:333](../../packages/core/src/context/session-manager.ts#L333)、[session-manager.ts:486](../../packages/core/src/context/session-manager.ts#L486)、[session-store.ts:239](../../packages/core/src/context/session-store.ts#L239)、[session-store.ts:988](../../packages/core/src/context/session-store.ts#L988)。

`upgradeLegacyV1Session` 没有被正常 open/续答/写操作调用，旧会话直接获得 read-only Store，首次追加抛 `LEGACY_SESSION_READ_ONLY`。同时 `SessionStore.open` 对所有 schema 都调用 `readFile(true)`：无末尾换行会补写换行，残片恢复还会隔离并截断源文件。升级函数也通过这一打开路径读取源 v1。

**触发与影响**：升级前正常使用 v0.0.6 的用户无法无感续答；对未换行或残片结尾的 v1，所谓只读打开会改变原文件，违反原件字节不变的迁移承诺。

**证据**：Manager 打开合法 v1 后追加得到 `LEGACY_SESSION_READ_ONLY`；对无末尾换行的合法 v1 执行 open，前后 bytes 不相等。

**建议**：v1 发现/浏览使用真正只读解析；首个变更入口在源锁保护下创建、验证并安装 v2 副本，再切换后续写入目标。尾部修复应写入副本。覆盖普通续答、rename/branch 等写入口和异常尾部的原件字节不变。

### R12：正则在主线程同步执行，搜索超时无法阻断灾难性回溯

**位置**：[catalog.ts:251](../../packages/core/src/context/catalog.ts#L251)、[catalog.ts:379](../../packages/core/src/context/catalog.ts#L379)、[catalog.ts:510](../../packages/core/src/context/catalog.ts#L510)。

`RegExp.exec` 直接在主线程执行，仅截断到 65,536 字符；总超时只在会话之间检查，扫描单文件没有传入 deadline，也没有 worker 隔离。短输入就足以造成指数回溯，文本长度上限不能代替可中断执行。

**触发与影响**：`/history --search re:(a+)+$` 遇到少量连续 a 加 `!` 即可长时间阻塞 CLI；取消信号、定时器和后台清理无法在同步匹配期间执行。

**证据**：真实 Catalog 中写入 `"a".repeat(40) + "!"`，设置 `timeoutMs: 10`；独立复现进程打印开始后 5 秒仍未返回，由外部 `spawnSync` 超时终止。不是向当前审查进程直接执行不可控正则。

**建议**：按规范在可 terminate 的 worker 中运行正则，使用搜索全程 deadline，并在单文件扫描中检查取消/期限。增加合法但病态正则的超时与取消测试；现有测试只检查无效语法和结果数量。

### R13：Worktree 清理失败后退回强制物理删除，可能删除新增产物

**位置**：[worktree.ts:247](../../packages/core/src/context/worktree.ts#L247)、[worktree.ts:301](../../packages/core/src/context/worktree.ts#L301)。

检查 status/rev-list 后直接执行 `git worktree remove --force`；命令失败又 `fs.rmSync(..., { recursive: true, force: true })`。没有撤销后续写入并持有清理租约，也没有在删除前复核目录身份与最终状态。

**触发与影响**：干净检查之后若仍在清理的工具/进程写出产物，或 Git remove 因新状态/锁等原因失败，强删分支会直接移除目录。R07 使“终态但仍有执行”的窗口更容易出现。这里确认的是危险回退存在，未在用户目录执行删除复现。

**建议**：等待所有写入者退出并取得独占清理租约；复核物理路径、worktree 身份、tracked/untracked/commit。删除失败返回 `check_failed_preserved`，移除物理强删回退。以临时仓库故障注入验证检查后新增文件、remove 失败均保留产物。

### R14：分支边界只检查 assistant 类型，没有验证完整工具事务

**位置**：[session-store.ts:294](../../packages/core/src/context/session-store.ts#L294)、[session-manager.ts:693](../../packages/core/src/context/session-manager.ts#L693)。

createBranch / forkSession 仅在切点本身为含 tool_use 的 assistant 时拒绝。切点若是只回填了部分工具的 tool 消息、运行中的用户消息或其它状态记录，不会验证整段前缀是否已闭合。selectBranch 也没有检查目标分支完整边界。

**触发与影响**：一个 assistant 同时发出 c1/c2，在只记录 c1 结果时从该 tool 消息分叉会成功；新投影仍缺 c2。后续 normalizeHistory 自动补 OUTCOME_UNKNOWN 是恢复语义，不能代替用户分支操作的非法切点拒绝。

**证据**：按上述三条消息建立真实 SessionStore，在只包含 c1 结果的记录处 `createBranch` 成功。现有测试只覆盖直接在 assistant tool_use 记录上分叉。

**建议**：复用完整交互索引与工具事务校验器，沿目标因果路径判定闭合边界；在分支/导出写任何控制记录前拒绝。增加多工具部分回填、进行中 run、终态失败轮次和有效完整结果边界用例。

### R15：branchWithSummary 在摘要写入失败后只回滚内存，重启仍切到失败分支

**位置**：[session-store.ts:425](../../packages/core/src/context/session-store.ts#L425)、[session-store.ts:455](../../packages/core/src/context/session-store.ts#L455)。

操作先持久化 branch_created、branch_selected，再追加摘要。摘要或后续 usage 写入失败时，catch 只赋值 `this.activeBranchId = sourceBranchId`；日志中的 branch_selected 没有撤销。读记录/重启重放会重新选中失败的新分支。

**触发与影响**：用户收到失败并以为仍在原分支，但重启后游标变化，违反“失败不移动游标”的明确承诺；摘要和费用事实也可能部分提交。

**证据**：对 branch_summary 追加注入失败，当前内存分支为 main，重新打开同一文件后为 broken-summary。

**建议**：先把摘要及所需状态完整准备并写入未激活分支，最后以一次成功的持久选择作为发布点；若要求整组原子可恢复，增加操作意图/提交标记。不能依靠失败后再次写日志来假定一定能回滚。覆盖每个追加边界的故障与重启重放。

### R17：Inbox 的并发重投可绕过去重

**位置**：[outbox.ts:183](../../packages/core/src/runtime/agent/outbox.ts#L183)。

**建议**：让消息查重、追加和消费确认受同一写者队列/事务保护，或以 eventId 维护在途 Promise，再结合重启对账。补并发重投、写后确认前崩溃与 poisoned writer 测试。
