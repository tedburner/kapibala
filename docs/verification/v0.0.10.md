### 1.5 分档资源验收（`pnpm verify:soak`）

## 2. CI 通道

- `.github/workflows/verify.yml`：`cross-platform`（ubuntu/macos/windows × Node 24）跑 `pnpm dev --no-start` 后执行 `pnpm verify:platform --no-build --allow-pending`，Windows 额外用 Git Bash 强制跑 shell 用例并上传证据；`minimum-runtime`（ubuntu × Node 20）在同一提交执行平台自动化检查并显式延期独立人工项；`compatibility` 必跑旧新产物的四组合和两类传输；`soak-pr` 在 PR/push 跑 10 轮，`workflow_call` 可选择 `soak_tier`。正式 release soak 使用 Ubuntu 24.04 / Node 24。
- `.github/workflows/soak.yml`：每晚 18:00 UTC 跑 nightly，`workflow_dispatch` 可选 pr/nightly/release，另有 `collect-baseline` 串行采集三份完整 release 候选；`codex/**` 分支 push 的提交说明显式包含 `[collect-baseline]` 时，也可直接为该 SHA 启动三次采集。普通 push、main 和 tag 不走此长跑入口。统一使用 Ubuntu 24.04 / Node 24 并上传证据。
- `.github/workflows/release.yml`：调用 verify 时传入 `soak_tier: release`，准备和发布前都检查六类专项的同 SHA 审核清单；格式和传入方式见 [发布证据说明](../release-evidence.md)。
- 上述通道**尚未在远端针对本版提交执行**，其配置存在不等于对应门禁通过。

## 3. 尚不能替代的门禁

发布阻断项，全部保持 pending，不允许用其他提交的证据替代：

1. **Node 20 实际通道**：本机为 Node 26.12.0；需要 `minimum-runtime` 工作流在同一 SHA 上产出真实 Node 20 平台门禁证据。
2. **Windows ACL 与 ConPTY**：`windows-acl` / `windows-conpty` 在非 Windows 宿主为 not-applicable，必须由 Windows runner 出具；进程树取消还需在 Git Bash 与 PowerShell 两种 shell 下分别确认。
3. **POSIX 交互式 PTY**：粘贴、审批、断线恢复的终端证据未采集。
4. **release 档长时验收**：1000 轮且 ≥30 分钟的报告尚未生成；冻结增长阈值（RSS/heap 每轮字节数）尚未由人工审阅确定，缺基线时结论只能是 pending。
5. **干净提交证据**：当前所有本机证据都是 dirty 工作区产物，发布候选必须在干净提交上重跑并把证据与 SHA 绑定。
6. **人工审核项**：真实模型小规模质量对比、费用与体验判断不属于自动化门禁，需人工执行并单独记录。

## 4. 实施裁决

- OpenSpec CLI 与共享执行辅助脚本在当前环境缺失，按项目惯例直接把证据记录在工作日志（`.workbuddy/v0.0.10-execution/progress.md`），不创建伪 change、不安装无关工具。
- MCP teardown 语义：管理器关闭会话但保留已关闭句柄引用，因此资源释放证据取「会话不再 ready + 进程退出」，不写"引用必须为 null"这种与实现无关的断言。
- soak 与 platform 采用同一架构：TS 编排器负责断言与证据，`.mjs` 探针负责真实进程并只输出原始事实，避免在编排层伪造环境结论。
- 本版不引入版本号开关或全局 flag 掩盖部署/迁移边界，公共面差异全部登记在 [SDK 兼容性说明](../sdk-compatibility.md)。

## 5. 发布前执行顺序

1. 由用户审核并提交、推送采集工作流和候选源码，Git 操作默认手动执行，代理需获得本次明确授权。可在 `codex/**` 准备分支提交说明中加入 `[collect-baseline]` 后推送，直接为该 SHA 启动三次完整采集；也可在工作流已存在于默认分支后，在 Actions → Soak 选择目标分支与 `collect-baseline`。人工审核后提交冻结阈值；准备并提交发布说明、迁移说明等发布文档，补全占位内容。准备性源码推送不属于版本发布，不推送版本标签。
2. 经用户审核，在干净且不落后远端的 main 执行 `pnpm release 0.0.10`，创建最终升版提交及本地标签；基线必须已经包含在该提交中。
3. 手动推送 main，确认同一最终候选 SHA 的跨平台 Verify 与 Node 20 通道通过，标签暂不推送。
4. 在该 SHA 上补齐 `verify:compat`、`verify:platform`、正式 release soak 和 Windows ACL/ConPTY、各平台 PTY 等人工专项。审核原始日志，在工作区外或忽略目录整理清单，运行 `verify:release-evidence`，再手动更新仓库变量 `KPBL_RELEASE_EVIDENCE`。不能提交自引用 SHA 的清单，也不能回填旧报告冒充新候选证据。
5. 所有必需证据齐备后，手动推送同一 SHA 的版本标签。Release 在准备和发布前检查清单，并复跑发布自动门禁；任一项失败均不执行 npm 发布。
